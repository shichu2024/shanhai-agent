## 1. 问题理解

**背景**：四个阶段交付后，系统的「知道自己在做什么」由三层承担：Spec 声明（agent_version 快照）、行为留痕（trace/failure/task）、记忆可信度（memory_record 状态机）。但「知道自己做得怎么样、边界在哪、随时间如何演变」没有统一表达——能力信息散落在 report 聚合、evolution 候选证据、memory 状态里，不可引用、不可组合、不可生成制品。

**表面需求**：四个功能件（登记 / 证据 / 趋势 / 报告）。
**核心问题**：把散落的证据流收敛为**可引用、可组合、可审计**的结构化自我认知层，且不引入第二真相源、不绕过既有脱敏口径。
**潜在问题**：① 与 memory/evolution/report 三个既有模块的语义边界不清将产生「三张清单说三件事」的治理混乱；② eval 缺口被静默掩盖会让 Evidence Store 宣称「五源整合」名不符实；③ 新增登记面若引入新的注入通道（statement 文本进上下文）会破坏既有注入防护格局。

## 2. 目标与非目标

**目标**：
1. Evidence Store：统一证据引用与解析（只读存取层，零新存储）；
2. Capability/Limitation Registry：能力与限制的结构化断言登记（人工确认制，唯一新表）；
3. 能力趋势：基于证据流的时间桶聚合派生（纯只读现算）；
4. 自我认知报告：组合制品（Card + Registry + 趋势），CLI 可导出。

**非目标（本期不做清单）**：
- 不做 evaluationPolicy 断言执行与 evaluation 落盘（D-36，留第六阶段与女娲合并评估）；
- 不做门户 UI / 女娲 Builder（维持延后）；
- 不做 Registry 条目向任务上下文的自动注入（首期仅 CLI 制品——避免新注入面，见 §9）；
- 不做能力趋势的快照落盘 / 时序表（现算，不落第二真相源）；
- 不做 A2A / 网络发布 / 跨库证据交换；
- 不做与原文 §9.2 污染段的对齐还原（字段集重新设计）。

**成功定义**：A-23~A-31 全绿 + 273 存量零回退 + 行覆盖 ≥93.28% 单调不降。
**失败定义**：任何新增写入面绕过 redaction / T1/T2/T3 任一回退 / Registry 与 memory 语义混写。

## 3. 总体思路与设计原则

1. **只读派生优先**（D-33 外推）：能现算的不落库——Evidence Store / 趋势 / 报告三件全部零存储；唯一例外是 Registry（断言是治理资产，须人工确认制留痕，参照 EvolutionCandidate 先例）。
2. **单一真相源**：能力断言的「证据」永远是回链引用（evidenceRefs），不是复制粘贴；通过率口径与 report 共用 subclassRegistry 单一常量源。
3. **读已脱敏面**：证据回读读的是落盘体（落盘前已过 redaction），不改写、不二次脱敏、不开原始数据新通道。
4. **人工确认制**（D-14 先例）：系统上限 = 生成带证据链接的 derived 候选；激活/退役由人决定。
5. **A0 纪律**：白泽字段集重新设计；原文污染段仅索引不引用。

## 4. 方案组成：四件设计

### 4.1 Evidence Store（证据存取层）

**定位**：统一证据引用格式 + 解析 API + CLI，把「某断言的证据在哪」变成单查询可回答的问题（T1/T2 同款「库内单查询」纪律）。

**统一引用格式（封闭枚举，D-35）**：`<kind>:<id>`，kind ∈ `task` / `trace_event` / `failure` / `memory` / `eval`（**eval 为预留位**——D-36 的成文载体：格式留位、解析返回 structured `not_implemented` 错误，不静默失败）。

**能力面**：
- `evidence show <ref>` → 单条解析：返回结构元数据 + 摘要（digest / 状态 / 时间戳 / 信封四字段），payload 仅在已脱敏落盘体存在时按原文返回（逐字节一致断言锚点）；
- `evidence task <taskId>` → 任务全链证据链：trace_index 行数 = JSONL 事件数一致性、关联 failure_record 行、关联 memory 行（taskId 回链）、委托链（parentTaskId/childTask 单查询沿树）；

**边界**：纯只读派生——零表、零迁移、零新事件、零写入（dbDump 全库快照断言，Agent Card 先例复用）。

### 4.2 Capability/Limitation Registry（能力与限制登记）

**定位**：从第一阶段「只读能力快照」（无独立载体的报告口径）升级为**结构化断言登记形态**——每条断言带证据引用、带状态、带确认留痕。

**与 memory 的分权（边界成文）**：memory_record = episodic **内容**记忆（注入上下文用，可信度状态机管「内容可信度」）；capability_registry = 结构化**断言**（不注入上下文，管「能力边界陈述的有效性」）。互链不互改：memory 行可作为 Registry 条目的证据引用；Registry 永不修改 memory 状态机。

**与 EvolutionCandidate 的分权**：evolution 指向**变更建议**（proposedChange / derivedVersionIds，回答「该改什么」）；capability 指向**状态断言**（statement，回答「现在是什么样」）。同一失败聚类允许两表各自引用同源证据——分权成文 + CLI 输出互见（§6 流程 4）。

**表结构（唯一新表，零回填迁移）**：

```sql
CREATE TABLE capability_registry (
  capabilityId   TEXT PRIMARY KEY,
  agentId        TEXT NOT NULL,             -- 聚合键 = agentId（跨版本——能力边界是 Agent 级资产，D-14 同款）
  kind           TEXT NOT NULL CHECK (kind IN ('capability','limitation')),
  statement      TEXT NOT NULL,             -- 断言文本（机械模板 or 人工撰写；进制品不进上下文）
  origin         TEXT NOT NULL CHECK (origin IN ('derived','manual')),
  evidenceRefs   TEXT NOT NULL,             -- JSON [{kind,id,occurredAt}]；add 时允许空（evidencePending 草稿），confirm 时强制 ≥1 且全部可解析（D-38 修订：强制力在 confirm，V0.2 P2-1）
  statementDigest TEXT NOT NULL,            -- 规范化摘要 = sha256(NFC + trim + 内部连续空白折叠单空格 + 小写化)；单一导出函数 manual/derived 共用（V0.2 P3-3，防双算漂移）
  status         TEXT NOT NULL CHECK (status IN ('candidate','active','retired')),
  createdAt      TEXT NOT NULL,
  lastUpdatedAt  TEXT NOT NULL,
  decidedAt      TEXT, decidedBy            TEXT                -- confirm/retire 留痕
);
CREATE INDEX idx_capability_agent ON capability_registry(agentId, status);
-- 部分唯一索引（V0.2，P1-2）：retired 行不阻挡人工重加同义断言；derived 幂等判重同口径（仅对非 retired 行）
CREATE UNIQUE INDEX idx_capability_dedup ON capability_registry(agentId, kind, statementDigest) WHERE status != 'retired';
```

**状态机（最小三态）**：candidate --confirm--> active --retire--> retired（无出边）；dismiss = retired + decidedAt/decidedBy 留痕。**去重仅对非 retired 行生效（V0.2 部分唯一索引，P1-2）**：retired 只表示「本条断言已退场」——同义新断言（人工重加，或未来证据再触发 derived）按新行登记不被阻挡；derived 重算不复活 retired 行（防误 dismiss 后自动回潮）。

**derived 候选生成（惰性、幂等、机械判据）**：
- R1 失败集中度：窗口（默认 30 天）内某 agentId 某非 infra 失败 subClass 计数 ≥3 且占该期失败总数 ≥50% → limitation candidate（**「失败总数」分母与 trend/report 同谓词**：countedInContractRate=1 AND status!='cancelled'——V0.2 P3-2，杜绝第三口径）；
- R2 工具失败集中：窗口内某 toolId 调用失败率 ≥50% 且样本 ≥3 → limitation candidate；
- 生成时机：`capability list` / `agent insight` 时惰性重算（A3 §6 / memory reconcile 同模式）；statement 用冻结模板（常量导出 + 测试断言，防 digest 漂移）；重算遇同义**非 retired** 行 → 跳过（幂等）；遇同义 retired 行 → 不复活、不阻挡（人工可重加，P1-2）。

**审计增补（A6 封闭集增补提案，载体=本节）**：AuditEventType 增 `capability_registered`（载荷含 origin）/ `capability_decided`（载荷 decision=confirm/retire/dismiss）。derived 生成亦留审计（系统机械动作无任务上下文，审计流是正确落点）。

**CLI 族**：`capability list [--agent] [--kind] [--status]` / `capability add <agentId> --kind --statement <text|--file> [--evidence <ref,...>] [--by]` / `capability confirm <id> [--by]` / `capability retire <id> [--by]`。`add` 允许证据为空（candidate 落库并标注 `evidencePending: true`——「人类知道但暂无运行证据」的草稿形态）；`add` 提供了 ref 但不可解析 → 整单拒绝（草稿可以无证据，不可以假证据）；**`confirm` 时强制证据 ≥1 且全部可解析，否则结构化拒绝**（D-38 修订，V0.2 P2-1：无证据不**激活**——真正要保的不变量在 confirm 端，与「derived 只生成不激活」对称）。

### 4.3 能力趋势（Capability Trend）

**定位**：可信度状态机的历史维度扩展——从「当前状态」到「状态如何演变」。

**纯只读现算（零存储）**：时间桶（day/week，缺省 day）× agentId 聚合：
- 任务面：任务量 / 契约通过率——**分母口径与 report 逐字相同 SQL 谓词**（`countedInContractRate = 1 AND status != 'cancelled'`，V0.2 P1-1 修订）：常量（EXCLUDED_FROM_CONTRACT_RATE）维持**写侧**单一源地位（recorders 写 countedInContractRate 标志，消费点②不动），trend 与 report 两个读侧消费同一落盘谓词——常量任何变更后，历史桶与新算桶共享同一落盘事实，两读侧永不分叉；空桶/样本不足 → null（「无分母不假装」，report 先例）；
- 失败面：failure subClass 分布（同排除口径）；
- 记忆面：memory_state_changed 事件按桶计数（从 trace_index 按 eventType 定位 + 定向文件读取，**不整库扫描 JSONL**）；
- 断言面：capability_registry 各状态条目数按桶（**取 createdAt 列**——登记即事实，V0.2 P3-4 钉死）。

**CLI**：`capability trend <agentId> [--since] [--until] [--bucket day|week]`。

**诚实边界（coverage 按面标注，V0.2 P3-5）**：任务面/失败面自第一阶段有全史；memory_state_changed 事件自第二阶段批次起才存在。不使用整体单一 coverage-from——记忆面单独标注 `coverage-from-memory`（首个该类事件时间戳），任务/失败面不标注（全史），不低报亦不假装。

### 4.4 自我认知报告（Self-Awareness Report）

**定位**：组合制品——四层拼合的单一 CLI 输出：

1. **声明面**：Agent Card 派生**冻结字段子集**（V0.2 P2-2，防不可证伪）：`INSIGHT_CARD_FIELD_KEYS = [agentId, versionId, specVersion, contentHash, mission, nonGoals, tools]`（常量导出 + 测试断言消费，D-41 纪律同款）——直接取 buildAgentCard 输出对应字段；
2. **断言面**：capability_registry active 条目 + open candidates 摘要计数；
3. **行为面**：§4.3 趋势（缺省近 30 天窗）；
4. **限制与证据摘要**：limitation 条目 + 各面证据引用计数（不展开 payload）。

**CLI**：`agent insight <agentId> [--version] [--since] [--json]`。**只读现算、永不存储**（D-40）；导出 JSON 供人工归档（归档是人动作，非系统行为——与 Agent Card 同款）。

## 6. 关键流程（正常 / 异常 / 边界）

1. **证据解析（正常）**：`evidence show trace_event:<eventId>` → trace_index 定位 taskId → 定向读 JSONL → 返回信封+payload。**异常**：ref 不存在 / kind=eval → 结构化错误（`not_found` / `not_implemented`），不静默、不猜测。
2. **人工登记 limitation（正常）**：`capability add --kind limitation --statement ... [--evidence failure:<id>]` → 解析提供的 ref（解析失败整单拒绝——草稿可以无证据，不可以假证据）→ 入表 candidate（无证据时标注 evidencePending）+ audit。**边界**：statement 超 2000 字符 → **fail-fast 结构化拒绝**（不截断——截断腐蚀去重键：两条同前缀长断言 digest 碰撞被误并；V0.2 P3-1，resultMaxChars P3-2 先例）。**确认（正常）**：`capability confirm` → 证据 ≥1 且全解析 → active + audit；证据缺失 → 结构化拒绝（草稿形态保留，证据到达后再 confirm）。
3. **derived 重算（正常）**：`capability list` → 惰性重算 → 新候选 INSERT + audit；已存在（任何状态）→ 跳过。**异常**：重算中途崩溃 → 下次重算幂等补齐（无状态迁移未遂窗口——INSERT 前无前置写）。
4. **双清单互见（边界）**：`capability list` 输出含同 evidenceRefs 的 evolution 候选计数提示；`evolution list` 反向同理（只读交叉提示，不互相写）。
5. **insight 生成（正常）**：Card 现算 + Registry 查询 + 趋势现算 + 拼合输出。**异常**：无任务数据 → 行为面输出 insufficient-sample（不假装）；无 Registry 条目 → 断言面输出空清单 + 提示（不是错误）。

## 7. 输入、输出、状态、依赖与交互关系

**削减顺序**：不可削底线 = 批次一（证据地基本体）+ 批次二手工登记与确认语义（无登记则白泽空壳）+ 全批 A-31。可削序列：insight 组合制品（Card+Registry+trend 各自可用，拼合是增益）→ 趋势的记忆面/断言面桶（保任务面+失败面）→ derived R2（保 R1）→ derived 全部（保手工登记）→ 不可再削。

**规模扩大瓶颈**：趋势现算无快照（大库查询延迟——OTel 触发线已有，趋势查询是新增触发面）；trace_index 单表增长（既有瓶颈继承）；Registry 行数无清理策略（retired 永留——审计资产定位，接受）。

## 9. 安全边界专节

1. **脱敏读边界（成文）**：证据回读 = 读已脱敏落盘体，逐字节一致返回；不二次脱敏（二次处理破坏 digest 对账且暗示存在未脱敏面）；不存在「原始面」可绕——落盘即脱敏是写侧不可削依赖，读侧零责任但须零加工；
2. **statement 文本 = 新文本面**：Registry statement（人工或模板）只进 CLI 制品与审计载荷，**首期不进任何任务上下文**——避免重开注入通道；若未来注入，必须走 D-13 边界标记同款（延后登记）；
3. **T3 面**：insight 导出 JSON 与 Registry statement 均为新扫描对象——T3 规则族不削弱 + 新面零命中断言（A-30）；statement 模板冻结常量防注入漂移；
4. **证据完整性**：confirm 时 evidenceRefs ≥1 且全部可解析，否则拒绝（D-38 修订）——防止「引用不存在的证据」的空头断言进入 active；add 时提供的 ref 不可解析仍整单拒绝（无证据可以，假证据不可以）。

## 13. 取舍说明

1. **只读优先于登记完备**：三件零存储 + 一件新表——牺牲「历史断言快照」的查询速度（趋势现算），换零一致性维护与零 T3 新面（D-33 外推）；
2. **不补 eval 执行面**：牺牲 Evidence Store「五源整合」的名义完整度，换本期范围纪律与契约口径的单一真相（评估与契约校验在现行系统本就同构——见 §0-2）；若反方/决策官裁定补齐，批次一增 evaluation_record 最小落盘面（预留列回填路径已在），成本约半批；
3. **Registry 独立新表而非 memory 扩展 kind**：牺牲一张新表，换两个状态机语义不混写（memory 四态管内容可信度 / capability 三态管断言有效性——迁移语义、注入行为、审计类型全不同）；
4. **retired 不阻挡同义重加、derived 不复活（V0.2 部分唯一索引，P1-2）**：牺牲「同义断言历史单行化」（同义多行不同状态并存），换「人工重加出路真实存在」（全状态唯一索引会把 §13-4 原辩护依据堵死——反方 P1-2 指出的自相矛盾修正）+ derived 不复活误 dismiss 行；
5. **首期不注入上下文**：牺牲自我认知对任务执行的即时反馈价值，换不重开注入通道（制品先于人机回路——先让断言可信，再谈让 Agent 自用）。

## 14. 特别要求清单

**14.1 最容易被忽略的三个问题：**
1. **「读已脱敏面」口径必须成文**——不写清楚会有人在读侧加二次脱敏（破坏 digest 对账）或误以为存在原始面可读（违规预期）；
2. **capability 与 evolution 的同源双生**——同一失败聚类两表各生一条候选，操作者面对两张清单；分权表 + CLI 互见提示（§6-4）不做则治理混乱必然发生；
3. **趋势分母的同谓词机制（V0.2 P1-1 修正）**——「同常量现算」≠「同口径」：常量变更后历史行落盘标志与新算现算必然分叉（正是本条原稿宣称要防止的事故）；正确机制 = trend/report 两读侧消费同一落盘谓词（countedInContractRate），常量单一源只在写侧。

**14.2 最可能失败的三个场景：**
1. 趋势查询在全量任务库上耗时/内存超预期（假设 #1 探针不过 → 降采样/窗口上限降级路径已备）；
2. derived statement 模板无意间混入计数值 → digest 漂移 → 重复候选泛滥（A-27 幂等断言是唯一防线，模板常量冻结须在批次二首轮落实）；
3. Windows CLI 长 statement 参数转义/编码问题（--file 变体首日就做，不留后手）。

**14.3 当前方案最依赖的三个假设：** §12 之 #1（索引可达不整库扫）、#2（模板冻结）、#6（组合延迟可接受）。

**14.4 最值得被反方挑战的三个设计点：**
1. **D-36 不补 eval 执行面**——反方可主张 Evidence Store 宣称五源而实为四源+预留，名实不符应补齐（我的立场：契约校验即现行评估承担者，补齐是第六阶段与女娲合并的事，本期补则范围膨胀约半批）；
2. ~~D-38 人工登记无证据豁免~~（**已结清，V0.2 P2-1**：按反方建议证据强制力移至 confirm——candidate 草稿形态（evidencePending）可行，「人类知道但暂无运行证据」场景可录入，无证据不激活的不变量保留）；
3. **D-39 趋势不落快照**——大库现算延迟是可预见的代价（我的立场：先现算拿零一致性维护，OTel 触发线与降级路径已备；快照层是触发后的事）。

**14.5 资源/时间/人员减少时：** §8 削减顺序（insight → 趋势窄面 → derived R2 → derived 全部 → 底线止）。不可削内核 = Evidence Store + Registry 手工登记与确认。

**14.6 规模扩大时：** 趋势快照投影层（OTel 触发后）、Registry 行清理策略（retired 归档）、跨库证据交换（ref 格式已封闭枚举，扩展为外部 ref 是加法）、insight 增量缓存。
