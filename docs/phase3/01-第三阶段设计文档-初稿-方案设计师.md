## 1. 问题理解

**背景：** 第二阶段收官（main `3476850`），终验收通过、无 P0；移交 1 项 P1 口径登记项（DB 第二原文落盘面）、4 组 P2（B~E）、既有五项 + 新增 P3 清单。决策官已逐项裁决归属，本设计把裁决清单转化为可实施、可验收的批次计划。

**真实目标：** 不是「修完一张缺陷清单」，而是**把两道防线单一的隐式约定转化为成文口径 + 机制防线，并消除声明面与执行面之间的缝隙**——① DB 原文落盘面「人人以为对方管」的死角（无条款认领、无测试断言）；② T3「命中即拒绝发布」的执行接线 fail-open 叠加（手动脚本 + 无 CI + exit 码无测试 + 扫描根短路零发现）。其余各项（清单漂移、判据污染、测试缝、P3）都是同一病理的不同切面：**机制存在，但接线/口径/清单未闭环**。

**表面需求 vs 核心问题 vs 潜在问题：**
- 表面需求：落地派发清单 7 项；
- 核心问题：几乎每项修复都**触碰已验收行为**（`task_record.input` 原文入库是第一阶段已验收行为；report 分母口径、policiesOf 回溯均有既有消费者）——收口阶段最大的风险不是修不动，而是修的时候引入回归或制造新的口径漂移。因此本设计的主轴是**断言先行 + 成文先行 + 变更即注记**；
- 潜在问题：批次三多项子项（跨轮混叠、dismiss 冷却）若做成「自动切窗/自动静默」会违背 D-12/D-14「决定权留人」的冻结精神——修复的边界必须是**可见性与护栏**，不是自动决策。

## 2. 目标与非目标

**目标：**
1. 派发清单 7 项全部落地为批次计划，每批 DoD 机械可断言；
2. 三条改进断言（记忆端到端无密钥 / 终态 approve 结构化拒绝 / T3 CLI 级 exit 码）以「红灯现状 → 修复转绿」格式成为验收面；
3. 规格修订成文（A6 §8 v1.3 辖区冻结 + 相关口径注记），全部为文档版本演进 + 可选列扩展，零数据回填；
4. 139 存量测试 + walkthrough + 覆盖率口径（89.81% 行覆盖，vitest.config.ts 排除口径）零回退。

**非目标：**
- 不做 V1.1 宏观第三阶段大项（沙箱 / 鲲鹏 / 多实例 / OTel 实接 / PostgreSQL，见 §0）；
- 不改任何 D-8～D-18 冻结决策的行为语义（幂等键、聚合键、requireReviewed、直发保留等一律维持）；
- 不做 CI 强制接线（T3 收口止于「exit 码可测 + fail-closed」，是否挂 CI 属平台运维决策，随交付建议输出）；
- 不引入后台进程（惰性判定模式沿用）。

**成功定义：** 三票齐备（设计冻结）→ WP-3B 四批次逐批交付并通过反方验收 → WP-3C 终验收（改进断言全绿 + 全量回归）。
**失败定义：** 任一修复破坏 T1/T2/T3 可断言性、139 回退，或 DB 脱敏破坏 inputHash 原文对账。

## 3. 总体思路与设计原则

1. **断言先行（红灯→绿灯）：** 反方 §七-3 三条改进断言先写、先跑出红灯，修复转绿即改进证明——本阶段验收方法论的基座；
2. **成文优先于改码：** 口径冻结（批次一）先于 DB 脱敏实现（批次二）——先定义辖区，再在辖区内施工；未成文的边界不动已验收行为；
3. **同源化优于就地补丁：** 清单漂移（C 项）的修复方向是单一常量源 + 多处消费，不是三处同步修改（决策官裁决方向）；
4. **默认 fail-closed：** T3 收口方向 = 「未扫描」与「干净」必须可区分（exit 码三元组），豁免宁可误拒不可静默放过；
5. **变更即注记：** 所有触碰已验收行为的修复（report 分母、policiesOf）必须同步落规格修订注记，行为变更与文档漂移不允许再分离——这是对第二阶段「声明面与执行面有缝」病理的直接对策；
6. **可见性而非自动化：** 治理判据修复止步于互斥护栏 + 警示单列 + 冷却窗，裁决权恒在人（D-12/D-14 精神外推）。

### 4.3 T3 执行接线 fail-open 收口（P2-B，批次一，四子项）

1. **exit 码 CLI 级测试：** 扫描入口（`releaseScan.ts:193-199` 的 argv 正则 + `process.exit` 分支）重构为可测函数（argv 参数化），vitest 新增 CLI 级用例断言三元组：**命中=1 / 干净=0 / 未扫描=2**。覆盖率口径注意：vitest.config.ts 现排除 scripts 入口层——本项以「入口函数化 + 纳入 include」最小调整实现，不放宽既有排除面（设计注记：口径调整本身进 DoD 报告）；
2. **扫描根短路防护：** 扫描根本身位于豁免路径内（现 `return findings` 静默零发现、exit 0）→ 改为 stderr 显式警告 + **exit 2（未扫描 ≠ 干净）**；**扫描根路径不存在 → 同属 exit 2（应扫而未扫，V0.2 补）**；确需以豁免目录为根的场景（如夹具自检）加 `--allow-exempted-root` 显式放行，放行动作进输出日志，**且必须落为真实用例（V0.2 补，反方补强：无用例即死代码）**；
3. **豁免锚定：** 豁免段序列匹配从「绝对路径任意嵌套位置命中」收窄为**锚定扫描根的相对前缀匹配**（豁免必须位于扫描根内、从扫描根起算）——任意嵌套命中不再豁免；
4. **扩展名补齐（V0.2 扩大）+ 残余口径成文：** `TEXT_EXTENSIONS` 增 `.pem` / `.key` / `.log` / `.env` / `.p12` / `.pfx` / `.crt` / `.ini` / `.cfg` / `.conf` / `.env.local`（+ 每族阳性对照用例随批）；**成文「白名单外扩展名 = 已知未扫描残余」**（A6 §8 注记）——残余不属 exit 2「未扫描」语义：exit 2 只覆盖「应扫而未扫」（短路根 / 根不存在），枚举外文件是显式声明的接受面。**批次一择项：** 未知扩展名尝试 UTF-8 宽松解码 + 二进制探测后扫描（真 fail-closed 收敛，成本低则随批做，否则残余口径兜底）。

**DoD：** 改进断言③转绿；四族既有阳性对照全过 + 扩展名扩面（11 项）对照；仓库根真实扫描 `npm run release-scan` exit 0；**新增用例：短路根场景 exit 2 + 扫描根不存在 exit 2 + 嵌套豁免不生效 + `--allow-exempted-root` 放行（夹具自检真实场景）**。

2. **幂等键口径注释修正：** 行为不改（D-14 冻结：聚合键=agentId，幂等键=agentId+trigger），修正 `evolution.ts` 内 per-subClass 分组循环的注释口径，并**成文**「多 subClass 同超阈值时第二个子类证据回填进既有候选」为设计语义而非缺陷；

### 4.5 治理判据污染面（P2-D，批次三，按分子优先级）

1. **rollback×canary 互斥（最优先）：** `rollback` 增校验目标 ≠ `canaryVersionId`（`registry.ts:370` 现无此检查，可回滚至 canary 目标制造 current==canary 非法态）——与 deprecate 的 P2-6 防护完全对称（消息口径同款：先 clear 或换目标）+ 结构化拒绝测试；
2. **report 分母排除 cancelled：** `contractPassRate` 分母 = tasks − cancelled（`report.ts:100-135` 现含 cancelled 稀释通过率）——cancelled 是治理决策非质量信号。**分母零基线（V0.2 增，P2-1 采纳）：** 排除后分母为 0（小组全为治理性取消）→ 输出 `insufficient-sample`（「不假装给答案」原则沿用），A-8 断言含此分支。**口径变更成文**（A5 report 语义注记），输出增 `excludedCancelled` 计数字段（口径可见、可复算），分母变更回归断言随批；
3. **跨轮灰度混叠（可见性方案）：** 不自动切窗——report 旁挂「canary 轮次」警示列：按 `canary_configured` / `version_promoted` / `version_rollback` 审计事件序列切轮，当前判据窗口若跨轮则输出 `window-straddles-rounds` 警示 + 轮次边界时间戳（操作者自行 `--since` 收窗，决定留人）；

## 8. 取舍说明

1. **成文与机制分两批而非一批：** 牺牲交付速度，换「辖区先定义、施工不越界」——直接在未成文辖区上改已验收行为（input 原文入库）会重演「口径未定义即动工」的病理；
2. **存量 DB 不回填脱敏：** 牺牲存量数据的绝对干净，换零迁移成本与「本地数据域」成文口径的自洽（回填需原文重放，违背脱敏单向性，技术上不可能）；
3. **跨轮混叠止于警示、dismiss 止于冷却：** 牺牲自动化程度，换 D-12/D-14「决定权留人」不破——判据窗口的裁剪权恒在操作者；
4. **候选关联显式回填：** 牺牲关联完备性，换「系统永不自动注册/发布」边界外推的一致性；
5. **P3 多数项成文不改码：** 牺牲形式上的「全修复」，换行为稳定——已知接受项写进注记后不再重复登记，登记面收敛本身就是交付。

## 9. 特别要求清单

**9.1 最容易被忽略的三个问题：**
1. **「未扫描 ≠ 干净」的语义区分**——T3 收口若只补 exit 码测试而不引入第三态，短路场景仍然 fail-open（exit 0 两种含义并存，脚本化消费方无法区分）；
2. **DB 脱敏的 digest 排除表外推**——管道现有排除表是按 Trace 事件载荷设计的，DB 行（failure/audit 明细字段）的 `*Digest`/`*Hash` 字段面不完全重合，需逐一比对（`inputHash` 后缀即 P3 实例）；
3. **批次二的 Trace/DB 双写一致性**——同一 input 在 Trace（已脱敏）与 DB（新脱敏）若改写结果不一致（规则执行次序/作用域差异），跨面对账将出现新漂移；「同一实例」断言同时防实例分裂与结果分裂。

**9.2 最可能失败的三个场景：**
1. DB 脱敏误伤结构化字段破坏 T1/T2 对账（inputHash 之外另有隐式原文消费点未枚举）——缓解：批次二 DoD 全量对账回归硬条款，不过即设计失败；
2. T3 入口函数化重构后真实 CLI 行为漂移（npm script 路径/相对根解析变化）——缓解：真实命令冒烟随批；
3. report 分母变更引发验收口径争议（新口径下既有判据样本数变化）——缓解：`excludedCancelled` 计数显式输出，口径可复算，A5 注记随批成文。

**9.3 当前方案最依赖的三个假设：** §7 之 #1（inputHash 兜底充分）、#3（同实例可断言）、#5（exit 2 无既有消费者）。

**9.4 最值得被反方挑战的三个设计点：**
1. **D-21 exit 2 新语义**——三态退出码是否过度设计？反方可挑战「短路场景直接 fail（exit 1）是否更简单」；
2. **D-24 policiesOf 维持回溯**——备选方案（仅当前指针版本）在「指针回滚后策略突变更可预期」上有论证优势；
3. **D-26 config.ts:33**——V0.1 曾主张恢复回退（微偏离报审）；V0.2 经 git 史核实（回退从未生效）接受反方意见，改判按裁定字面执行，此点已结清。

**9.5 资源/时间/人员减少时：** §5 削减顺序（批次四择项 → 批次三之 3/4/5 → 不可削底线前止）。

**9.6 规模扩大时：** DB 写路径脱敏开销（PostgreSQL 路径重估）、T3 豁免清单治理流程、report 轮次切分的数据量（审计事件全表扫描）。
