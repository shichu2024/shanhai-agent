## 1. 问题理解

### 1.1 背景与真实目标

用户于 2026-09-26 在 TASK-42 选型裁定 **选项 B：完整交互门户**。原始 V1.1 分层架构中的「山海门户」层自此进入实施范围。真实目标有三层：

1. **表面需求**：一个能看的界面——任务、Trace、审批、证据、趋势、Insight、Agent Card、Evolution 一屏可见。
2. **核心问题**：当前全部人机交互收敛于 `shanhai` CLI（JSON 输出、手敲命令、`--by` 手填），操作成本高且审批等待期间无观测入口；门户要把「读」与「高频写操作」从命令行搬到一个常驻的本机操作台。
3. **潜在问题**：门户是本平台第一个**常驻进程 + 网络监听 + 面向浏览器**的组件，与既有的「短命 CLI 进程 + SQLite WAL 多进程 CAS」运行模型存在结构性张力（详见 §7 风险）。设计的主要难度不在页面，而在进程模型与写操作语义的正确接线。

### 1.2 已知事实（代码级核实）

- 全库无任何 HTTP 服务代码；既有网络面只有出站 Anthropic fetch 与 MCP stdio（`src/mcp/client.ts`，D-28 零依赖自实现先例）。
- 运行时依赖仅 2 项：`better-sqlite3`、`zod`。
- 写操作全部收敛于 Manager 层并带 CAS/Trace/Audit 副作用：`rt.approvals.approve/deny`（approval.ts:142/:172）、`rt.tasks.cancel`（taskManager.ts:661）、`rt.tasks.runTask({resume})`（taskManager.ts:261）。
- `approve` 只写 `decision`，任务保持 Paused；续跑由独立子进程 `task run --resume --resumed-by approve-spawn` 完成（cli.ts:266-285）。
- `StateManager.recover()`（stateManager.ts:29）把**所有** Running 遗留标记为 Failed(CrashRecovery)，无法区分「崩溃遗留」与「另一进程正在执行」——每次 CLI 调用 `rt.startup()` 都会触发该扫描。
- 优雅取消（graceful cancel）仅在执行进程内生效；跨进程只能走持久化 `abortRequested=1`（force 路径）。
- 审批超时是惰性判定（`applyLazyTimeouts`，读时触发），全库无后台定时器。
- Evidence Store 契约：零表零迁移零写入，payload 字节原样返回、禁止二次脱敏（§9-1）。
- `cli.ts` 的 resume spawn 以 `path.resolve(process.argv[1])` 解析 CLI 入口（cli.ts:275）——天然兼容 dist 安装态与 ts 直跑开发态。
- 跨进程 graceful cancel 抛出的是普通 Error（非结构化 TaskError），服务端无法按错误码分类（taskManager.ts cancel 的 running 分支末段）。
- `recover()` 是两段耦合：①trace_index 对账（幂等、安全、无误杀）+ ②Running 崩溃标记（有误杀面），无单独调用入口（stateManager.ts:29）。
- 覆盖率门：行覆盖 93.87% 单调不降；`vitest.config.ts` include 为 `src/**/*.ts`（前端非 TS 资产不入分母；前端纯逻辑以可测 TS 模块形态入分母，见 §7 假设 5 修订）。

## 1.3 表面需求 vs 核心问题 vs 潜在问题

| 层 | 内容 |
|---|---|
| 表面需求 | 读面八视图 + 审批 approve/deny + 任务 cancel/resume |
| 核心问题 | 常驻门户进程与短命 CLI 进程在**同一 SQLite 上的共存协议**；写操作经既有状态机而非旁路 |
| 潜在问题 | 门户 boot 误杀正在执行的任务（recover 语义）；resume 长阻塞请求；跨进程 cancel 的用户预期管理；零依赖原则与前端可维护性的平衡 |

## 2. 目标与非目标

### 2.1 目标

1. 本机单用户操作台：`shanhai portal` 一键启动，浏览器访问，覆盖 TASK-80 列出的读面八视图。
2. 写面最小集：审批决议（approve/deny）+ 任务控制（cancel/resume），**全部经既有 Manager**，门户自身零旁路写。
3. 纯增量层：不改 Runtime 内核模块既有行为；增量仅限（a）新目录 `src/portal/`，（b）CLI 新子命令，（c）config 新可选节，（d）至多两个**只读增量方法**（见 D-48）。
4. 工程门继承：T1/T2/T3 零回退、行覆盖 ≥93.87% 单调不降、tsc 0、walkthrough 不回退、TDD 红阶段证据。

### 2.2 非目标

- 多用户、RBAC、远程暴露（本阶段明确不做，见 D-44 论证）。
- 版本治理写操作（promote/rollback/canary/review）——**建议延后**（D-45，待决策官裁决）。
- 女娲 Builder（维持延后，D-45 附建议）。
- WebSocket/SSE 实时推送（轮询足够，见削减顺序）。
- 任务创建与启动（`task create/run` 写面）——**延后**：任务输入是 JSON 契约校验面（`TaskCreationRejected.issues`），表单化的收益/风险比低于审批/取消，且 CLI 已可用。列为候选扩展。

### 2.3 成功与失败定义

- 成功：walkthrough 能在浏览器完成「看到 Paused 任务 → 查看审批详情 → approve → 触发 resume → 观测至终态」全链路，且过程中每一步的库内状态与走 CLI 完全一致（逐事件对账）。
- 失败：任何门户路径产生的库写入绕过了 Manager（直连 SQL 写）、或门户 boot/请求导致运行中任务被误标 CrashRecovery、或 T3/覆盖率门回退。

## 3. 总体思路与设计原则

**门户 = 一个常驻的 node:http 进程 + 一组纯函数 API handler + 无构建步骤的静态前端。** 它是 Runtime 的一个「视图控制器」，不是新的运行时：

1. **借用而非重建**：读面 100% 调用既有只读函数；写面 100% 调用既有 Manager 方法。门户层只做 HTTP 编解码、错误码映射和页面组装。
2. **不驻留执行**：门户进程不执行任务主体。resume 走 detached 子 CLI 进程（复用既有 approve-spawn/manual-resume 契约），任务执行、模型调用、崩溃恢复语义与 CLI 完全同构（D-46）。
3. **零新依赖**（D-43）：`node:http` + 原生 ESM 前端，无框架、无构建器。承袭 D-28 先例（官方 MCP SDK 因 17 个传递依赖被拒，自实现 ndjson 三方法）。
4. **宁可小而正确**：写面只收高频操作；治理操作、任务创建延后。
5. **脱敏纪律不动摇**：展示存储字节原样（写时已脱敏）；门户自身新增的持久化只有 resume 子进程日志与门户 Token 文件（`data/portal/token`，0600，P1-2），均不落业务数据；日志内容为子进程 stdout/stderr（已过既有脱敏面的 JSON 输出）。

### 4.3 API 面（写，选项 B 增量）

**通用硬性要求（P1-2-②）**：所有 POST 端点强制 `Content-Type: application/json`（允许 charset 参数），否则 **415**——跨站简单请求（`text/plain` 等）由此在协议层被拒，与 Token 头（预检拦截）构成双保险。

**CLI 旗标映射基准表（P2-4，A-33 判定基准）**——「门户操作 ≡ CLI 命令 X（含旗标）」逐端点钉死：

| 端点 | 语义 | ≡ CLI 命令 | 接线 |
|---|---|---|---|
| `POST /api/approvals/:id/approve` | 只写 decision，任务保持 Paused | `approval approve <id> --detach` | `rt.approvals.approve(id, by)`；响应含 `{taskId, decision:'approved', taskStatus:'paused'}` |
| `POST /api/approvals/:id/deny` | 拒绝→任务终态 cancelled(approval_denied) | `approval deny <id> [--reason <t>]` | `rt.approvals.deny(id, by, reason)` |
| `POST /api/tasks/:id/resume` | **不阻塞请求**：detached spawn 续跑子进程 | `task run --resume <id> --resumed-by manual-resume` | D-46；入口=`path.resolve(process.argv[1])`（复用 cli.ts:275 先例，P2-2）；响应即返回 `{spawned:true, logFile}` |
| `GET /api/tasks/:id/resume-log` | 最近一次 resume 子进程日志 | — | 内存索引；重启后回落文件系统：taskId 白名单字符集校验 + resolve 后目录前缀断言 + 按 mtime 取最新（P2-3/P3-3） |
| `POST /api/tasks/:id/cancel` | body `{mode:'graceful'\|'force'}`；**running + graceful 由服务端前置校验直接 409（不调用 Manager）**——规避跨进程 graceful 的非结构化 Error 路径（P3-1） | graceful≡`task cancel <id>`；force≡`task cancel <id> --force` | queued/paused：立即（Manager CAS 语义）；running：仅 force（`abortRequested=1`），UI 显式确认 |
| `POST /api/portal/crash-recovery` | **显式崩溃恢复**（P1-1 修复）：确认对话框后调用既有 `rt.startup('portal')`（内含 recover 全段：Running→Failed(CrashRecovery)、孤儿快照清理、pending superseded、索引对账） | ≡ 任一 CLI 命令触发的 `startup()` | 纯既有机制编排，零旁路；响应回传 RecoveryReport 四列表 |

**approve-and-resume 组合端点已按反方建议移除**（不必要复杂度）：两步操作 + 前端状态明示（「已批准，待续跑」）替代；CLI 缺省的前台 spawn 行为不进门户（门户 resume 恒为 detached manual-resume 语义，UI 如实标注 resumedBy）。

写操作 `by` 取值：`portal`（缺省）或 config `portal.operatorId`；Trace/Audit 事件中来源可辨识（既有事件 payload 不改，`who` 字段本身即来源标记）。

## 5. 关键流程

### 5.1 门户启动（正常流程）

1. `shanhai portal` → `Runtime.fromConfig(dataDir, repoRoot)`（构造 Manager，**不自动 startup**）。
2. **条件化 startup（D-42 核心）**：查 `SELECT COUNT(*) FROM task_record WHERE status='running'`——
   - `=0`：调用 `rt.startup('portal')`（内含 builtin 工具登记 + recover，清掉崩溃遗留）；
   - `>0`：**跳过 startup**，日志警示「检测到 Running 任务（可能正由其他进程执行），本次启动不执行崩溃恢复扫描；请确认该任务进程存活」。recover 责任留给下一次无 Running 遗留的 CLI/门户启动。
   - 理由：recover 无法区分「崩溃遗留」与「活进程正在执行」；CLI 短命进程误杀面小，常驻门户若每次 boot 无条件扫描，与 CLI 并行使用时必然误杀。此为纯调用编排，不改 stateManager 任何行为。
   - **附带代价知悉（P2-6，部分接受）**：跳过 startup 连带跳过 recover ①段 trace_index 对账（幂等安全段）——门户-only 长驻期间的索引漂移只能靠显式崩溃恢复操作或下次 CLI 修复，而 insight/trend 恰消费 trace_index。零内核改动下 recover 无法拆半调用；「对账/标记拆分」列为**内核微增量候选**，交决策官终审裁量，本稿缺省不做。补偿：显式崩溃恢复操作（下条）触发的是 recover 全段（含对账）。
   - **Running 僵尸行逃生路径（P1-1 修复）**：条件化 startup 不得形成自锁——boot 跳过 ≠ 永久搁置。任务列表对 Running 行常驻警示入口 + 确认对话框（明示「将把所有 Running 任务标记为 Failed(CrashRecovery)」），确认后走 `POST /api/portal/crash-recovery`（§4.3）。纯门户使用者由此获得与 CLI 等价的恢复能力。
3. 绑定监听（缺省 `127.0.0.1:7780`，config/env 可覆盖）→ 打印访问 URL（首次生成 Token 时同步打印，见 §6）。
4. 常驻；SIGINT/SIGTERM → `rt.close()` 退出。

### 5.2 审批决议 → 续跑（写面主链路）

1. 前端轮询发现 pending 审批 → `GET /api/approvals/:id`（show 内已跑惰性超时判定，过期请求自动 deny+cancel，前端下次轮询看到终态）。
2. 操作者点 approve → `POST /approve`：Manager 内 CAS `pending→approved`（first-write-wins，重复点击/与 CLI 竞争得 `already_decided`，映射 409）。
3. 任务仍 Paused。前端呈现「已批准，待续跑」+ **Resume 按钮**（两步操作，V0.2：组合键已移除）。
4. `POST /resume`：resume.ts spawn `node dist/cli.js task run --resume <taskId> --resumed-by manual-resume`，detached、stdio 重定向到 `data/portal/logs/resume-<taskId>-<nowNs>.log`；**HTTP 立即返回**。
5. 子进程自行 `startup`（此时该任务为 Paused，不在 Running 扫描受害集）→ CAS `paused→running` → 按 snapshot.nextCallRef 锚点放行（P1-1 既有语义）→ 执行至终态或再次 Paused。
6. 前端轮询 `GET /api/tasks/:id` 观测状态迁移；需要细节时读 resume-log 端点。

**失败路径**：approve 的 `ApprovalError`（not_found/already_decided/task_not_paused/version_mismatch/timeout_applied）逐码映射 HTTP（§4.3）；resume spawn 失败（如 dist 未构建）→ 500 + 明示「approve 已生效，请用 CLI `task run --resume` 兜底」（与 CLI 同样的兜底话术）；子进程 exit≠0 → 日志端点可见，任务状态以库为准。

### 5.3 取消（异常流程）

- queued：立即 cancelled。
- paused：立即 cancelled + supersedePending + 快照清理 + 委托链下溯（全部为 cancel 内既有语义）。
- running：服务端**前置校验**——`getTask().status === 'running'` 且 mode=graceful → 直接 409 + 提示「该任务运行于独立进程，仅支持强制中止（下一个原子调用边界生效，模型调用不打断）」，**不进入 Manager**（跨进程 graceful 在 Manager 内抛普通 Error，非结构化错误码，前置校验规避之，P3-1）；确认后 force 写 `abortRequested=1`。**不做进程信号杀死**——persist-then-continue 纪律不允许 kill 落在持久化窗口内。

### 5.4 边界情况

| 情况 | 处理 |
|---|---|
| 门户 boot 时另一 CLI 任务在跑 | D-42 条件化 startup 跳过 recover，警示 |
| 门户-only 使用中执行进程崩溃 → Running 僵尸行 | **确定逃生路径（P1-1）**：任务列表警示 + 显式崩溃恢复操作（确认后 `rt.startup()` 全段 recover：标记 Failed、清孤儿快照、supersede pending、索引对账）；force cancel 对无人消费的 abortRequested 不再是唯一出口 |
| resume 子进程执行中门户重启 | 无影响：子进程 detached，状态全在库；门户重启后按 D-42 检测到 Running → 跳过 recover，轮询可见 |
| resume-log 请求在门户重启后（内存 map 为空） | 回落文件系统：`data/portal/logs/resume-<taskId>-*.log`，taskId 白名单字符集校验 + resolve 后目录前缀断言 + mtime 取最新（P2-3/P3-3） |
| 同一审批在 CLI 与门户同时决议 | CAS first-write-wins，后到方得 already_decided(409)；两端语义同构 |
| resume 被点击两次 | 第二次 spawn 的子进程在 CAS `paused→running` 处失败退出（expectFrom=paused），无害；日志可查 |
| 审批已超时但未有人读 | 首次 list/show/approve 触发惰性判定；approve 得 timeout_applied(409) |
| 开发态（ts 直跑）/安装态（dist）入口解析 | spawn 复用 `path.resolve(process.argv[1])`（P2-2），两形态同构；启动时探测形态并在 resume 不可用时明示（读面不受影响）——批次一以 dist 形态冒烟断言（P2-1） |
| 浏览器直连非本机地址 | 缺省绑定 127.0.0.1；非回环绑定允许但 Token 仍强制（D-44，Token 已无关闭项） |
| 跨站 `text/plain` POST 打写端点 | 415（P1-2-②，协议层拒绝） |

## 6. 输入、输出、状态、依赖与交互

- **输入**：HTTP 请求（读=查询参数；写=JSON body）；config `portal` 节 + env `SHANHAI_PORTAL_TOKEN`/`SHANHAI_PORTAL_PORT`。
- **输出**：JSON API 响应（结构对齐 CLI 输出形状，`ok:true/…` 或结构化错误 `{ok:false, code, message, detail?}`）；静态前端资产。
- **状态**：门户进程内**无业务状态**（无缓存、无会话）；唯一运行时登记 = resume 子进程日志文件索引（内存 map + 文件系统真源）。全部业务状态在 SQLite/JSONL——门户随时可杀可重启。
- **依赖**：Runtime 单例（进程内复用，`rt.db` 经既有非枚举暴露面取用，仅读）；既有只读函数清单见 §4.2；新增只读方法见 D-48。
- **配置兼容（硬约束 4）**：`config.portal` 为可选节，缺省视为禁用（不启动、不影响任何既有行为）；`parsePortalSection` 非法值 fail-fast（对齐 parseMcpSection 先例）。V1→V1.1：纯增量节，无数据迁移。

### 安全边界论证（D-44 展开）

1. **监听面**：缺省 `127.0.0.1`——不暴露局域网。非回环绑定允许（合法即放行）；Token 无关闭项（见下）。
2. **Token（P1-2-① 修复：缺省启用，无关闭项）**：所有 `/api/*` 请求要求 `Authorization: Bearer <token>`（静态资产豁免——不含数据面）；`crypto.timingSafeEqual` 比对。取值解析序：config `portal.token` > env `SHANHAI_PORTAL_TOKEN` > **首次启动自动生成**（`crypto.randomBytes(32)` hex，落 `data/portal/token`，0600；非 POSIX 平台权限降级为警示）并打印控制台。「可选」仅保留「显式配置覆盖」，不存在「无 Token 运行」状态。
3. **跨站请求面（P1-2-② 修复：成文为硬性要求）**：不使用 Cookie → 经典 CSRF 不成立；但任意网页可向 `http://127.0.0.1:7780` 发 fetch——两道独立封堵：① **所有 POST 端点强制 `Content-Type: application/json`（否则 415）**，跨站简单请求（`text/plain` 等）在协议层被拒；② Token 为自定义头，触发 CORS 预检，门户不向跨域预签发放行 → 恶意页无法同时满足两者。
4. **DNS rebinding**：校验 `Host` 头必须为 `127.0.0.1[:port]`/`localhost[:port]`（或配置地址），否则 403。
5. **静态文件**：路径归一化防穿越；按扩展名设 Content-Type；`X-Content-Type-Options: nosniff`。
6. **展示纪律**：所有 payload 展示存储字节原样（已脱敏）；门户层零正则二次处理（Evidence §9-1 同款纪律）；T3 扫描自动覆盖新增文件（root 级扫描；Token 文件位于 `data/`——T3 既有跳过目录且不入库，内容为运行期生成凭据而非源码泄漏面）。

## 8. 取舍说明

- **轮询 vs WebSocket**：选轮询。5s 粒度对审批场景足够；WebSocket 引入连接状态管理与依赖诱惑，违反零依赖纪律。代价：状态变更最高 5s 延迟。
- **进程内 resume vs 子进程 resume**：选子进程。进程内 `runTask` 阻塞事件循环数分钟、abort race 只在进程内有效、崩溃会连带门户——三者皆不可接受。代价：spawn 开销 + 日志间接观测。
- **治理操作延后**：见 §4.5。代价：本期门户对治理仍只读。
- **`listTasks` 放 taskManager vs portal 层直连 SQL**：选前者（schema 知识留在模块层、可测、覆盖率高）。代价：内核文件 +1 方法（增量口径见假设 7）。

### 削减顺序（资源收紧时从后往前砍）

1. UI 美化（原生样式即可用）→ 2. trend/report/evolution 视图（CLI 已有输出）→ 3. resume-log 端点（可直接看文件）→ 4. 轮询降频/手动刷新 → **不可再砍**：tasks/approvals 视图 + approve/deny/cancel/resume 四写操作 + 认证边界（= 选项 B 的定义域 + 安全底线；Token 缺省启用后不再属可削减项）。approve-and-resume 组合键已按反方建议直接移除（不进削减序）。

### 规模扩大时的瓶颈

前端无框架在视图数 >15 时将失控（届时引入构建步骤需新裁决）；轮询在多观察者/低延迟需求下到顶；单 Runtime 单进程在并发写多时受 SQLite 写锁串行——均属「第七阶段再议」。

## 12. 特别要求清单（角色规定）

**最容易被忽略的三个问题**：
1. 门户 boot 的 recover 误杀（D-42）——不做条件化，门户与 CLI 并行使用的第一天就会踩；V0.2 补：条件化之后还须补主动逃生（P1-1），否则跳过=永久搁置。
2. `Host` 头校验——开发者记得绑 127.0.0.1 却常忘 DNS rebinding 让「localhost 配置」形同虚设。
3. resume 子进程的入口解析——ts 源码直跑（开发态）与 dist（安装态）两种形态，V0.2 已统一复用 `process.argv[1]` 先例（P2-2）；Windows 下 spawn `.cmd` 不可解析是既有平台事实（批次四 P3 教训），必须 node 直启。

**最可能失败的三个场景**：
1. approve→resume 链路中子进程 spawn 失败，操作者以为「批准即续跑」而任务滞留 Paused——需 UI 状态明示 + 兜底话术（V0.2：approve 恒为 --detach 语义并明示「待续跑」，组合键已移除，歧义面收窄）。
2. force cancel 后模型长调用迟迟不回原子边界，操作者反复点 force——`abortRequested` 幂等但 UI 必须呈现「已请求中止，等待边界」而非无响应。
3. 前端在审批 payload 大 JSON（snapshot messages）时渲染卡顿——递归渲染器需折叠长字段（>2KB 摘要展示）。

**最依赖的三个假设**：§7 假设 1（Manager 面充分）、假设 2（同步 SQLite 单用户够用）、假设 4（无框架前端可维护）。

**最值得被反方挑战的三个设计点**（V0.1 自陈，反方已裁定，V0.2 均已采纳）：
1. D-42 条件化 startup——反方裁定：方向正确、不引入 PID/心跳，缺口在逃生路径 → 已补显式崩溃恢复操作（P1-1）。
2. D-48 `listTasks` 增量方法的「纯增量」口径——反方裁定：可接受，附守卫（无写副作用、不改签名）→ 已随 D-48 成文。
3. 前端零覆盖——反方裁定：按原写法不充分 → 已收窄：抽纯函数 TS 模块入分母 + walkthrough 契约钉死（P2-5）+ 残余风险成文知悉。

**资源减半时**：按削减顺序砍到第 4 级（保四写操作+两核心视图+认证），批次并为两批。
**规模扩大时瓶颈**：见 §8 末段。
