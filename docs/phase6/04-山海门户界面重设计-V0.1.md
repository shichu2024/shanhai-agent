> 基线：`main` @ `8d5fe03`（PR #31 合入后）。
> 上游输入：综合决策官 TASK-80 brief（2026-09-29）；用户触发意见「现在的界面能力也太差了，基本属于不可用的状态」。

## 0. 一句话结论

在不触碰任何服务端代码与 API 契约的前提下，对门户前端（`src/portal/public/` 三个资产，合计 542 行）做信息架构重组、交互规格补齐与视觉体系重建，把门户从「JSON 直出的调试页」升级为「单用户日常可用的本地操作台」；同时提交 D-43（前端零构建铁律）的解除提案——仅放开前端资产层的构建期工程化，运行期零依赖、T3 扫描、dist 冒烟三项铁律全部保留。

## 1. 背景与目标

### 1.1 现状实证（逐条可复核）

| 病灶 | 证据位置 | 后果 |
|---|---|---|
| 前端为后端 view 模块的手工镜像 | `src/portal/public/app.js` 头部注释自承「Mirror of src/portal/view/*.ts」，542 行 JS 与 9 个 TS 模块（约 414 行）双份维护 | 双维护漂移面：任何文案/格式化修改必须改两处，无机制保证一致（终验报告 §13 已自承此脆弱性） |
| 结构化数据全量 JSON 直出 | agent 详情页 insight / trend / report 直接 `jsonBlock()` 渲染完整 JSON | 「能力观测」不可读，用户无法从原始 JSON 中获得信息 |
| 反馈体系薄弱 | 全部错误（网络失败/401/403/404/409/500）在多数页面折叠为单一文案「加载失败」；resume 成功仅以 alert 风格提示 | 用户无法区分「断网」「未认证」「状态已变化」，恢复路径不明 |
| 无加载态/空态/错误态三态设计 | 加载中显示「加载中……」纯文本；空列表显示「暂无记录」；无骨架屏 | 界面显得「卡住」「坏了」，是「不可用」观感的直接来源 |
| 导航深度缺失 | 无面包屑、详情页无返回链路、无当前位置指示 | 用户在详情页迷失，只能手改 hash |
| 详情页不自动刷新 | 轮询仅覆盖任务/审批列表（5s 一次） | 任务详情页状态过期，用户需手动 F5 |
| 视觉系统缺失 | `style.css` 仅 26 行；状态徽章仅灰底黑字，无语义色 | 状态不可扫读，界面无品质感 |
| 缺乏信息聚合 | 8 个读面平铺在 7 个平级路由 | 用户不知道「进门该看哪里」 |

### 1.2 目标

将门户升级为**单用户日常可用的本地操作台**，用三条可验证的目标口径衡量：

1. 任何一页的主要信息**不需要阅读原始 JSON** 即可获得；JSON 仅作为按需展开的附属证据。
2. 任何一次写操作（批准/拒绝/取消/续跑/崩溃恢复）具备**确认 → 执行中 → 成功/失败反馈 → 下一步引导**的完整链路，失败时给出与错误码一一对应的恢复指引。
3. 界面状态**可扫读**：状态用语义色徽章、相对时间、进度可视化表达；加载/空/错误/断连四态每页齐备。

### 1.3 硬约束继承（不变，逐条声明）

以下条目来自 V0.2 冻结决策与终验收基线，本设计**不作任何变更**：

- API 契约：不新增、不修改、不删除任何端点；请求/响应形状逐字节沿用（A-37）。全部能力仅由既有 14 读 + 5 写端点组合而成。
- Token 流程：`#token=` 片段消费（TASK-96 口径）、sessionStorage、首管 401、403 不可自动登出，均无关闭项。
- 静态资产安全：MIME 白名单、`.` 分段拒绝、415、Host 校验、拒绝嵌入外部源。
- 写面安全模型：100% 经 Manager 落库、跨进程写禁用、`confirmation_token` 一经签发不可撤销。
- 数据语义：脱敏边界、Evidence 字节原样、能力洞察按既有人工审核语义呈现，不新增前端侧加工解释。
- 运行时行为：D-42 boot 条件化、D-46 resume 子进程模型、双形态（dist 产物 + tsx source）等价。
- 质量基线：行覆盖 ≥ 95.13%（PR #29 冻结值，单调不降）；双形态冒烟 16/16；T3 零命中。

## 2. 需求范围

### 2.1 做什么（In Scope）

1. 门户前端信息架构重组：一级导航收敛为「任务 / 审批 / 观测」，观测聚合现有总控数据与 capability / evolution / evidence 三面为二级结构；新增面包屑与全局状态区。
2. 全部 8 个读面的结构化呈现规格：列表表格化、详情卡片化、JSON 折叠化、trend 图表化（纯 CSS/SVG，不引图表库）。
3. 5 个写操作的完整交互流规格：确认对话框、执行中状态、按错误码分类的失败反馈、成功后的下一步引导（含 resume 的 CLI 兜底话术）。
4. 视觉体系：设计 token（语义色/字体阶梯/间距/圆角/阴影）+ 组件清单（徽章/按钮/卡片/表格/模态/Toast/时间线/状态机图/空态/骨架屏）。
5. 前端工程化提案（以决策官对 D-43 的终审裁定为前提）：前端源组件化 + 单文件产物构建（详见 §9）。
6. 每页加载/空/错误/断连四态规格，以及轮询断连检测与恢复。

### 2.2 不做什么（Out of Scope，逐条可判定）

1. 不新增、不修改任何 API 端点、参数、返回体；不触碰 `src/portal/*.ts` 服务端代码、`src/modules/`、`src/runtime/` 任何文件。
2. 不改变认证模型（Token 位置、存储、401/403 语义全沿用）；不引入登录页、多用户、角色权限。
3. 不引入 WebSocket / SSE / 服务端推送；轮询机制保持 5s 间隔不变（仅补齐断连检测与详情页轮询）。
4. 不新增任务创建、治理写（候选采纳/拒绝/存疑）、Skill Builder 操作面。
5. 不引入运行时第三方依赖；除 §9 提案的单一构建期 devDependency（esbuild）外，不引入任何运行时库、框架、图表库、CSS 框架。
6. 不做移动端适配专项（仅保证 ≥1024px 桌面宽度可用）、不做暗色主题、不做 i18n。
7. 不修改既有测试的断言语义；新增测试仅做增量。

## 4. 功能需求 · 全局框架（FR-G）

- **FR-G-1 一级导航**：呈现「任务 / 审批 / 观测」三项；当前页面对应项高亮。审批项在 pending 数 > 0 时显示红色计数徽标，数值 = pending 记录数，> 99 显示「99+」。
- **FR-G-2 Token 状态区**：常驻导航栏右端。`未配置` 态显示琥珀色圆点 + 「设置 Token」，点击弹出设置面板（密码输入框 + 保存/清除按钮）；`已配置` 态显示绿色圆点。保存后重发当前页数据请求。行为沿用 TASK-96 既有口径，仅改变呈现位置（从路由级表单改为全局面板）。
- **FR-G-3 连接状态区**：显示最近一次任意 API 请求的成功时间（HH:MM:SS）。连续 3 次请求失败（网络错误或 5xx）进入断连态：页面顶部出现断连横幅「与本地服务失去连接，请确认 portal 进程在运行」，附「重试」按钮；任一请求成功后自动解除。401/403 不计入断连判定。
- **FR-G-4 面包屑**：详情页（任务/审批/证据/Agent）显示面包屑；列表页不显示。
- **FR-G-5 轮询**：任务列表、审批列表保持 5s 轮询（现状口径）；任务详情、审批详情新增 5s 轮询（仅拉取当前实体）。页面不可见（`document.visibilitychange`）时暂停轮询，恢复可见时立即拉取一次。轮询请求失败按 FR-G-3 计数，不在页面内弹错误。
- **FR-G-6 首次进入引导**：无任何数据且 Token 未配置时，任务列表空态区域显示「三步开始」引导：① 设置 Token（内联面板）；② 启动一个任务（显示 CLI 命令示例）；③ 回到此页自动出现数据。

## 5. 功能需求 · 任务面（FR-T / FR-TD）

### 5.1 任务列表（FR-T）— 数据源 `GET /api/stats`、`GET /api/tasks`

- **FR-T-1 统计卡片区**：页面顶部四个统计卡片：运行中、待审批、已暂停、累计任务数（数据源 `/api/stats`，字段沿用现有渲染口径）。卡片数字使用等宽字体，点击「运行中/已暂停」卡片等价于应用对应筛选。
- **FR-T-2 筛选与工具条**：状态筛选 chip 组（全部/排队/运行中/已暂停/成功/失败/已取消，单选）；搜索框（按标题或任务 id 子串过滤，客户端执行）；右端「手动刷新」按钮与「自动更新于 x 秒前」指示。
- **FR-T-3 列表表格**：列 = 任务（标题 + 截断 id）、状态（语义色徽章）、进度（`current_step/total_steps`）、更新时间（相对时间，title 悬停显 ISO 原文）、操作（查看）。按更新时间倒序。
- **FR-T-4 僵尸 Running 警示**：列表中存在 `is_zombie_running=true` 的记录时，页面顶部显示琥珀色警示条（不阻断操作）：「检测到 N 个任务显示运行中但无活动进程，多为门户进程重启所致，可进入详情执行取消。」文案口径沿用 `view/tasks.ts` 的 `runningWarning`，仅改呈现位置。对应行附加「疑似僵尸」标记。
- **FR-T-5 三态**：加载中显示表格骨架屏（5 行占位条）；空结果显示空态（区分「暂无任务」与「筛选无结果·清除筛选」）；加载失败显示错误卡片（按 FR-W-6 错误分类文案 + 重试按钮），不再使用裸「加载失败」。

### 5.2 任务详情（FR-TD）— 数据源 `GET /api/tasks/:id`

- **FR-TD-1 页头**：标题 + 状态徽章 + 任务 id（等宽、点击复制）+ 更新时间相对值。
- **FR-TD-2 状态进度条**：六态步进可视化（queued → running →（paused）→ succeeded / failed / cancelled），当前态高亮、已历态打勾、终态着色。终态（succeeded/failed/cancelled）额外显示终态说明行。
- **FR-TD-3 元信息卡**：双列网格展示 approval_mode、来源 issue（`#number title`，有则显示）、项目、恢复点摘要、创建/更新时间。字段缺失显示「—」。
- **FR-TD-4 僵尸警示**：`is_zombie_running=true` 时页头下方显示同 FR-T-4 口径的警示条。
- **FR-TD-5 事件时间线**：`recent_events` 渲染为竖向时间线（节点色按 `is_error`；卡片含类型徽章、相对时间、summary、payload 折叠 JSON）。空数组时显示「暂无事件」空态，不渲染空容器。
- **FR-TD-6 操作区**：按状态条件渲染，与现有 `actionBar` 逻辑等价：running →「取消任务」（danger）；paused →「手动续跑」（primary）；failed →「崩溃恢复」（danger）。其余状态不显示操作区。交互细节统一遵守 §8 FR-WR。
- **FR-TD-7 404 处理**：任务不存在（`not_found`）显示「任务不存在或已被清理」空态 + 返回任务列表链接，不作为错误弹出。

## 6. 功能需求 · 审批面（FR-A / FR-AD）

### 6.1 审批列表（FR-A）— 数据源 `GET /api/approvals`

- **FR-A-1 列表表格**：列 = 审批（`#id` + 任务标题）、关联任务状态徽章、决议状态徽章（pending 琥珀 / approved 绿 / denied 红）、请求时间（相对）、操作（处理 / 查看）。排序：pending 置顶（按请求时间正序，最久未处理优先），已决议按决议时间倒序。排序在客户端执行，不改服务端。
- **FR-A-2 筛选**：状态筛选 chip（待处理 / 已批准 / 已拒绝 / 全部）。
- **FR-A-3 三态与 FR-T-5 同构**；空态文案「没有待处理的审批」时附一句「审批由任务的审批门禁自动产生」。
- **FR-A-4 与导航徽标联动**：本页或任务列表任一轮询刷新后，同步更新顶部「审批」导航徽标计数。

### 6.2 审批详情与决议流（FR-AD）— 数据源 `GET /api/approvals/:id`，写 `POST /api/approvals/:id/approve|deny`

- **FR-AD-1 决策卡（pending 态页首）**：卡片标题「等待你的决议」；内容依次为：影响范围摘要（action / task_id / requested_at）、决议提示语（**逐字复用** `view/write.ts` 的 `approveActionHint(task_status)` 口径：「批准后任务仍停留在当前断点；点击『继续执行』或后续 resume 才会真正推进」——该文案是已测契约，禁止改写）、两个操作按钮「批准并等待续跑」（primary）与「拒绝」（danger）。
- **FR-AD-2 批准确认对话框**：显示 action、任务标题、`confirmation_token` 有效期说明（一经签发不可撤销，沿用 D-47 口径）；「确认批准」按钮执行写操作。
- **FR-AD-3 拒绝对话框**：可选理由输入框（≤200 字符，留空提交空字符串）；「确认拒绝」按钮执行。
- **FR-AD-4 决议后引导（本设计的核心闭环）**：
  - 批准成功：决策卡原位切换为绿色结果卡「已批准 · 等待续跑」，显示 `decided_at`；下方给出两条下一步路径——①「前往任务页手动续跑」链接（任务为 paused 时显示）；② CLI 兜底命令（`shanhai resume <task_id>`，等宽、可复制）。此文案是 resume 语义（P3-3：门户提交 spawn 成功即返回，真正续跑以任务页状态为准）的用户可懂表达，必须与 FR-WR-5 口径一致。
  - 拒绝成功：切换为灰色终局卡「已拒绝 · 任务终止于当前断点」，无后续操作。
- **FR-AD-5 已决议详情（decided 态进入）**：页首为决议结果徽章卡（批准绿/拒绝红 + decided_at + decision_payload 折叠 JSON），下方依次为关联任务摘要卡（标题、状态、链接）、上下文 JSON（折叠）。
- **FR-AD-6 并发冲突（409 already_decided）**：返回 409 时，决策卡原位替换为提示卡「该审批已被决议（可能由其他会话或 CLI 完成）」，同时自动重新拉取详情展示真实决议结果。不弹通用错误。

## 7. 功能需求 · 观测面（FR-O）与 Agent 实体页（FR-AG）

### 7.1 观测 · 总控（FR-O-1）

数据源 `GET /api/stats` + `GET /api/tasks` + `GET /api/approvals`（复用全局缓存，无新增请求）。内容：四统计卡片（同 FR-T-1）；「最近任务」迷你列表（最近 5 条，标题+徽章+相对时间，点击进详情）；「待办审批」迷你列表（pending 前 5 条）。本页是「进门第一眼」的默认落点候选——默认落点仍为任务列表（见开放问题 OQ-4）。

### 7.2 观测 · 能力（FR-O-2）— 数据源 `GET /api/agents`、`GET /api/agents/:id/capability`

- 列表：Agent 表格（id、display_name、状态、待反思计数 pending_reflections、最近笔记时间、操作「查看」）。
- 详情（选中 Agent 后页内展开或跳转 `#/agents/:id`，二选一在实现批内定，推荐跳转实体页）：capability 数据**禁止整段 JSON 直出**，按字段结构化为：概览卡（reflection_count / last_reflection_at / patterns 计数）、模式列表（每条 pattern 为卡片：标题 + 置信度 + 出现次数 + 摘要，原始 JSON 折叠于「查看原始数据」）。字段缺失时该节不渲染。

### 7.3 观测 · 演进（FR-O-3）— 数据源 `GET /api/evolution/status`、`GET /api/evolution/suggestions`

- 状态卡：总轮次、距离下次反思还差 N 次、最近触发时间（无记录显示「尚无记录」）。
- 候选列表：每条候选为卡片（id、类型徽章、状态徽章 pending/approved/rejected、创建时间、摘要）；详情区内 `diff` / `pattern` 字段以折叠 JSON 呈现。治理操作（采纳/拒绝/存疑）**不在本期范围**（§2.2-4），卡片不渲染操作按钮，仅提示「治理操作请使用 CLI」。

### 7.4 观测 · 证据（FR-O-4）— 数据源 `GET /api/evidence`、`GET /api/evidence/:id`

- 列表：证据包表格（id、task_id、created_at 相对时间、runs 计数、操作「查看」）。
- 详情：元信息卡（id / task_id / 创建时间）+ runs 表格（attempt / status / started_at / finished_at / resume_log 链接）+ **参考完整性区**：渲染既有 `integrity` 字段为「参考完整性：n 项全部可追溯 / 存在缺失参考」摘要 + 明细列表。Evidence 字节原样约束（D-44）下，前端仅做呈现，不做任何内容加工、不全文渲染大 payload（>2KB 走折叠 JSON 查看器）。
- resume_log 链接行为：沿用现状（404 视为「日志尚未产生」，显示灰色不可点文本「日志未生成」，不报错误）。

### 7.5 Agent 实体页（FR-AG）— 数据源 `GET /api/agents/:id/{insight|trend|report}`

三个请求并行发出，各自独立渲染与失败（一节失败不影响其他节）。

- **FR-AG-1 页头**：display_name + id（等宽可复制）+ 状态徽章。
- **FR-AG-2 洞察区**：insight 结构化为「最近笔记」列表（时间 + 摘要，原始 JSON 折叠）、「待综合条目」计数卡、「反思计数」卡。
- **FR-AG-3 趋势图**：trend 数组渲染为纯 CSS 柱状图（每根柱子 = 一天，高度 ∝ attempts，成功/失败分段着色绿/红），横轴日期，柱上 title 悬停显 `日期 · 尝试 n · 成功 n · 失败 n`。空数据显示「近 14 天无运行记录」。**不引入任何图表库**。
- **FR-AG-4 报告区**：report 的 `report_json` 按 key 分节渲染（每节标题 = key 的语义化映射表，映射缺失的 key 原样显示 key 名）；文本值直接渲染，结构值走折叠 JSON。
- **FR-AG-5 操作**：「触发反思」（primary，写操作遵守 FR-WR）。

## 8. 功能需求 · 写操作通用规范（FR-WR）

适用于全部 5 个写端点（approve / deny / cancel / resume / crash-recovery）及「触发反思」。

- **FR-WR-1 确认对话框**：所有写操作必须经模态确认。对话框内容 = 操作后果一句话（cancel 复用 `cancelModeFor` 双分支口径「进程内取消，实时生效 / 跨进程标记，任务推进到检查点时生效」；crash-recovery 复用 `confirmCrashRecoveryText`；approve/deny 见 FR-AD-2/3）+ 后果说明 + 「确认 / 取消」按钮。上述文案均为已测契约，**逐字复用，禁止改写**。
- **FR-WR-2 执行中态**：点击确认后按钮进入禁用 + 旋转指示，对话框不关闭；同一操作不可重复提交。
- **FR-WR-3 成功反馈**：对话框关闭，原位显示成功结果卡（非 alert），并立即重新拉取当前实体数据刷新页面。任务列表/审批列表在下一次轮询周期同步。
- **FR-WR-4 resume 成功话术**（P3-3 口径的用户表达）：结果卡显示「续跑进程已启动（spawned），PID：xxxx。真正续跑以任务页状态为准」，附「查看续跑日志」链接与 CLI 兜底命令块（`shanhai resume <task_id> --from-package` 场景沿用 resumeNote 口径）。spawn 同步失败但返回 `spawned:true` 的既有缺陷（终验 P3-3 已记录）由「以任务页状态为准」话术覆盖，不在前端做额外探测。
- **FR-WR-5 失败反馈按错误码分类**（对话框内联红字 + 保留重试能力）：

| 错误码 / 场景 | 用户可见文案 | 引导动作 |
|---|---|---|
| 401 unauthorized | 「Token 无效或未配置」 | 打开 Token 设置面板，保存后自动重试原操作 |
| 403 host_forbidden | 「当前绑定地址禁止写操作」（引 P3-③ 口径：非环回绑定下服务端拒绝） | 提示检查启动参数 |
| 400 invalid_task_id | 「参数不合法」 | 无，属程序异常 |
| 404 not_found | 「对象不存在或已被清理」 | 刷新当前列表 |
| 409 already_decided | 「该审批已被决议」 | 自动刷新详情（FR-AD-6） |
| 409 task_not_paused | 「任务当前不可续跑（状态已变化）」 | 刷新当前实体 |
| 409 timeout_applied | 「该任务已被判定超时终局」 | 刷新当前实体 |
| 409 cross_process_graceful_unsupported | 「跨进程任务不支持优雅取消，已转为标记取消」 | 刷新当前实体（此码为成功结果的提示，非失败） |
| 网络失败 / 5xx | 「服务无响应，请确认 portal 进程在运行」 | 重试按钮；计入 FR-G-3 断连判定 |

- **FR-WR-6 幂等与并发**：执行中态保证单实例不重复提交；跨会话并发冲突统一经 409 路径反馈，不做前端乐观锁。

## 9. D-43 解除提案（待综合决策官终审裁定）

### 9.1 问题陈述

D-43 冻结了「门户零构建步骤」——`package.json` 零变更、portal 全部 node 内置、T3 扫描 `src/portal/public/`。该决策的**本意**（据 V0.2 §决策与终验报告）是守护运行期零依赖与供应链最小面，但其实际约束落在了**前端资产的编写方式**上：482 行 `app.js` 必须手工镜像 9 个 TS view 模块，双维护漂移面已被终验报告 §13 自承为脆弱点。本次重设计将把前端从 542 行推向约 3000 行量级（组件化后），手工镜像在工程上不可持续。

### 9.2 关键事实（已核实）

`server.ts` 的静态服务在**运行期直读** `repoRoot/src/portal/public/`，构建期无复制步骤；产物若落回 `src/portal/public/`，则 T3 依赖扫描（覆盖面含 public/）与 dist 冒烟（读取同一路径）**天然覆盖构建产物**，无需任何流水线改动。

### 9.3 方案 A（推荐）：构建期工程化，运行期零依赖不变

- 前端源码迁入 `src/portal/ui/`（TypeScript，组件化模块），由 esbuild（单一 devDependency，单二进制、零传递依赖）打包为**单文件 IIFE** 直出 `src/portal/public/app.js`（产物提交入库，与现状一致）。
- `package.json` 变更面：devDependencies +1（esbuild）、scripts +1（`build:portal`）。`dependencies` 保持零变更，运行期 `node dist/cli.js portal` 零新依赖——D-43 的守护目标（运行期供应链）不受影响。
- 产物新鲜度钉死：新增契约测试在测试进程内执行构建并比对 `public/app.js` 与构建输出逐字节一致（防漂移，替代现在的「人工镜像自觉」）。
- UI 源码纳入行覆盖分母，沿用 `view/*.ts` 先例；覆盖率 ≥95.13% 单调不降门不变。
- T3 扫描面、`dist` 冒烟铁律、A-37 API 契约、serveStatic 行为：全部不变。

**对 D-43 字面口径的影响**：「package.json 零变更」将被违反（devDependencies +1、scripts +1）。这是对 D-43 口径的修订请求——守护目标（运行期零依赖）保留，约束位置从「禁止构建」收窄为「禁止运行期依赖」。

### 9.4 方案 B（备选）：保持零构建

前端继续手写单文件 JS，新设计组件以「函数 + 模板字符串」组织在单文件内；新增「镜像一致性契约测试」：对 view/*.ts 中已测的格式化/文案函数，用 jsdom 断言 app.js 的对应渲染输出等价。成本为零依赖变更，但单文件规模翻倍后双维护漂移依旧，仅治标。

### 9.5 建议

推荐方案 A。若决策官裁定维持 D-43 字面口径，则按方案 B 执行，本设计其余章节不受影响（信息架构、交互规格、视觉规范与构建方式正交）。

## 11. 异常与边界场景（逐条可判定）

1. **401 保留路由重试**：任何页面收到 401 → 页面内容区替换为「需要访问令牌」卡片（保留当前路由与筛选状态于内存），Token 保存后自动重发原请求并恢复页面，不丢上下文。沿用 TASK-96 语义，仅呈现升级。
2. **403 host_forbidden**：写操作专属文案（FR-WR-5）；读操作遇 403 显示「当前绑定地址不允许此访问」。
3. **三类 409** 各自专属文案与刷新引导，见 FR-WR-5 表，不合并为通用错误。
4. **resume spawned:true 但 CAS 失败**（P3-3 既有缺陷）：前端不探测、不告警，由「以任务页状态为准」话术 + resume-log 链接 + CLI 兜底覆盖。
5. **resume-log 404**：显示「日志未生成」灰字，非错误态。
6. **僵尸 Running**：警示条不阻断任何操作；取消操作对僵尸任务走「跨进程标记取消」分支，对话框文案由 `cancelModeFor` 自动命中。
7. **JSON 折叠阈值**：序列化后 >2048 字节默认折叠；≤2048 字节可内联等宽显示（沿用 §12 既有口径）。
8. **轮询断连**：连续 3 次失败出横幅；恢复后自动摘除并立即全量刷新当前页。
9. **空态**：每个列表/时间线/图表均有专属空态文案（区分「无数据」与「筛选无结果」）。
10. **时间呈现**：一律相对时间（`x 分钟前`，复用现有 relTime 口径），title 悬停显示完整 ISO 字符串。
11. **超长文本**：标题超过 60 字符截断 + 省略号 + title 悬停全文；id 一律等宽显示前 8 位 + 悬停复制全文。
12. **浏览器兼容**：Chrome / Edge 最近两个大版本；不使用实验性 API。
