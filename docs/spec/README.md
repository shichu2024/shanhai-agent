## 5. 特别要求清单（角色规范）

### 5.1 最容易被忽略的三个问题

1. **A0 证明基线原文不可引用**——若 WP-B 实施者顺手回看基线文档「补参考」，污染会回流；规格唯一来源必须钉死在本目录；
2. **归因不漂移是验收锚点不是文档措辞**——A4 §3 的机械映射若在实现层被「就近归类」软化，C3-③ 与 T2 同时失效；
3. **T1/T2 依赖字段分散在 A3（TaskRecord 绑定）/A6（信封 + bindingSnapshot）/A1（快照哈希）三处**——任一处实现走样，断言整体落空，评审时应交叉核对。

### 5.2 最可能失败的三个场景

1. A2 §6 交集表与真实 Provider 支持集不符（探针实测收窄）→ Spec 返工；
2. C2 实验中 `provider_rejected_schema` 与 `provider_error` 边界误判 → 契约失败率被污染；
3. trace_index 与 JSONL 双写不一致 → T2 查询漏报越权尝试。

### 5.3 当前方案最依赖的三个假设

1. zod→JSON Schema 链路不越 A2 §6 子集（WP-B 复核）；
2. SQLite 单写者 + WAL 满足「先持久化后继续」的崩溃一致性；
3. 扁平 JSONL + 索引表足以支撑 T1/T2 与 C2 聚合（无嵌套 Span）。

### 5.4 最值得被反方挑战的三个设计点

（R2 已随评审落定：D-3 注册即拒、D-5 快照承载 + promptHash 钉死、D-1 无默认 + 错误信息指名路径；本节保留为初稿记录，落定状态见 §4。）

### 5.5 资源/时间缩减时的削减顺序（对齐章程 §5）

按定稿 §9 削减顺序执行：A4/A5/A6 文档细节可砍说明文字保枚举；A0 已完成不占后续资源；D-1–D-7 决策点评审不可省（影响 WP-B 接口）。

### 5.6 规模扩大时的瓶颈预判

1. JSONL + 索引表在任务量放大后的聚合性能（迁移 OTel/ClickHouse 的触发条件应在第二阶段量化）；
2. 封闭事件/分类集随模块增长的增补流程（每次增补走章程变更规则，防枚举腐化）；
3. 版本快照表的存储增长（无 GC 策略——不可变性与清理策略的张力留给第二阶段）。
