## 1. 总体结构：两条流 + 一个绑定模型

| 流 | 载体 | 内容 | 消费者 |
|---|---|---|---|
| **Trace 流** | per-task 一个 JSONL 文件（`traces/<taskId>.jsonl`，追加 only） | 任务生命周期全部事件 | T1 查询、C2/实验报告、能力快照（只读降级形态） |
| **审计流** | SQLite `audit_events` 表（追加 only） | 版本事件（注册/发布/废弃/回滚）+ `RejectedRequest`（落库前拒绝 + CLI 拒绝） | T2 查询 |

**版本绑定模型（T1/T2 的地基）：** 任务创建时把 `{taskId, agentId, agentVersionId, specContentHash}` 固化进 TaskRecord **并作为每个 Trace 事件的公共信封字段**（§2）——任一事件单独取出都能定位当时生效的 Spec 版本。

## 3. Trace 事件目录（任务流，封闭集）

**层级：** `Trace（文件）→ 任务级事件 → attempt 级调用事件（model_call / tool_call / state_change）`。第一阶段为扁平 JSONL + `eventType` 判别层级，不建嵌套 Span 树（S 削减项：结构留给消费端聚合）。

| eventType | 层级 | 触发（对应 A3 迁移/流程） | 载荷字段（除信封外） |
|---|---|---|---|
| `task_created` | 任务级 | TaskRecord 落库 | `input`（摘要哈希 + 全文）、`inputContractHash` |
| `task_queued` | 任务级 | Created→Queued | `queueDepth` |
| `task_started` | 任务级 | Queued→Running | `bindingSnapshot`：`{toolVersions: [{toolId, implVersion}], modelId, promptHash}`（**T1 的工具/模型/Prompt 版本关联载体**）。`promptHash` 语义（P2-8 钉死）：**首次组装的 system prompt 模板哈希**；第一阶段 Prompt 静态内嵌于 Spec，故其值 = `specContentHash` 的派生（convenience 字段，不新增信息量）——若 WP-B 引入动态 Prompt 组装，则升级为独立组装结果哈希并触发 A5 §3 增补 |
| `attempt_started` | attempt | 新 attempt 开始（信封 `callNo`/`callKind`/`attemptNo` 已承载键位） | `kind`（model/tool，冗余显式） |
| `model_call_completed` | attempt | 模型调用返回 | `modelId`、`latencyMs`、`finishReason`、`usage: {inputTokens, outputTokens, estimated: bool}`、`strategy: "native" / "prompt" / null`（P2-4 修订：实验 A/B 策略标注——原生 structured output / 纯 Prompt 声明；生产运行为 null。11 号 §2.2 实验字段 `strategy` 由本字段投影，不再需要独立记录通道） |
| `tool_call_requested` | attempt | 模型请求工具 | `toolId`、`argsDigest`（参数哈希+受控字段实际值） |
| `tool_call_executed` | attempt | 工具放行执行完成 | `toolId`、`latencyMs`、`resultDigest`、`riskLevel`、`audited: bool` |
| `policy_denied` | attempt | A2 §5 拦截 | `toolId`、`reasonCode`、`consecutiveDenialCount`（**T2 的越权尝试记录**） |
| `attempt_failed` | attempt | Running→Running（新 attempt 前置） | `failureClass/subClass`（A4 attempt 级）、`willRetry: bool` |
| `task_succeeded` | 任务级 | Running→Succeeded | `outputDigest`、`outputContractVerdict` |
| `task_failed` | 任务级 | Running→Failed / Created→Failed | `failureClass/subClass`（终局归因）、`failureRecordId` |
| `task_cancelled` | 任务级 | →Cancelled | `cancelReason`（**v1.1 封闭枚举**：user/approval_denied/approval_timeout/abort/superseded）、`mode: graceful / abort`（v1.1）、`abortedDuring: {callNo, callKind, phase}?`（v1.1，abort 时）、`abortRequestedBy?`（v1.1，跨进程标志）；graceful 语义标记 = `mode=graceful` |
| `crash_recovery_marked` | 任务级 | 恢复路径 | `detectedBy`、`lastKnownStatus` |
| `contract_checked` | 任务级 | 输入/输出契约校验执行点 | `which: input/output`、`verdict`、`violations: [{path, expected, actual}]`（A4 expectedVsActual 同源） |

**v1.1 新增事件（8 个，TASK-43 终审）：**

| eventType | 层级 | 触发 | 载荷（除信封外） |
|---|---|---|---|
| `approval_requested` | 任务级 | L3 挂起：写 ApprovalRequest + Running→Paused | `requestId`、`toolId`、`riskLevel`、`timeoutAt`、`callRef` |

**task_created 载荷扩展（v1.1，灰度留痕）：** 增 `assignmentSource: stable / canary / explicit` + 分派时双指针值（currentVersionId / canaryVersionId 快照）。

**写入规则（冻结）：** ① 每条迁移先持久化后继续（A3 不变式②在 Trace 侧同样成立：状态事件先落盘再执行后续动作）；② 事件追加 only，不更新不删除；③ 文件为 `traces/<taskId>.jsonl`，天然并行写安全（03 号 P2-3）。

## 6. T1/T2 单一查询口径（验收断言映射）

| 断言 | 查询形态（单一查询 = 一次 SQLite join / 一个 JSONL 文件内 grep-able） | 依赖字段 |
|---|---|---|
| **T1**：给定任一 Failed 任务 Trace，返回当时生效 Spec 版本及 Prompt/工具版本关联 | `traces/<taskId>.jsonl` 内：信封字段（agentVersionId + specContentHash）→ Registry 取快照；`task_started.bindingSnapshot` 取 Prompt 哈希与工具实现版本。**单文件 + 单表查询，无跨系统步**。**未 Started 的答案形态（P2-7 修订）：** `Created→Failed` 与 `CrashRecovery` 任务无 `task_started` 事件，其 T1 答案 = **仅信封版本**（agentVersionId + specContentHash → 快照全文），无运行时要素绑定（toolVersions/modelId/promptHash 未发生）——验收脚本按此两级形态断言：有 `task_started` 断言完整绑定，无则断言信封级答案非空 | §2 信封 + §3 `task_started` |
| **T2**：给定任一 Agent 版本，返回运行期全部越权尝试与拦截点 | `audit_events WHERE agentVersionId=? AND kind IN ('task_creation', 'cli_operation')`（**P2-3 修订：kind 并集**——被拒任务创建 + 被拒 CLI 操作，与 A5 §2「CLI 拒绝与 T2 同源」对齐）∪ 各 trace 文件内 `policy_denied` 事件（按 agentVersionId 信封过滤，SQLite trace 索引表支撑）；另附 NULL 兜底单列计数（§4） | §4 + §3 `policy_denied` + §2 信封 |

**支撑索引（WP-B 建表义务）：** `trace_index(taskId, agentVersionId, eventType, timestamp)`——JSONL 为主存储、SQLite 为索引的混合形态，保证 T1/T2 是库内单查询而非文件系统遍历。

**T2′ 审批可举证（v1.1 新增断言，玄武最小验收面）：** 给定任一 Agent 版本，单一查询返回其全部 L3 审批请求及裁决——`ApprovalRequest WHERE agentVersionId=?`（表级索引）∪ Trace `approval_requested`/`approval_decided` 事件（信封 agentVersionId 过滤，trace_index 支撑）——审批挂起、裁决、超时、superseded 全程可举证，与 T2 同一查询形态。

## 6.1 双写一致性与索引恢复程序（P1-5 修订 / D-6 落地）

**双写次序（D-6 已裁决维持）：先 JSONL 后索引**——事件先追加至 `traces/<taskId>.jsonl` 并 flush，成功后写 `trace_index` 行。崩溃窗口内最多丢失索引行、不丢失事件（文件为准）。

| 程序要素 | 定义 |
|---|---|
| **恢复触发点** | `StateManager` 启动扫描——与 A3 §6 崩溃恢复**同一钩子**（进程重启即同时执行两件事：① 标记 Running 遗留任务 → Failed:Runtime(CrashRecovery)（A3 §6 收窄，TASK-40 F-1——Queued/Paused 均不迁移，v1.1；且顺带删除该 taskId 的孤儿 PauseSnapshot，终审 R-4）；② 逐 task 索引对账） |
| **对账水位** | 逐 task 比较：`trace_index` 中该 taskId 的（行数, 末位 eventId）vs JSONL 文件的（行数, 末行 eventId）。水位对账 O(1) 每 task，不逐行 diff |
| **不一致判定与重建规则** | 任一不等 → 删除该 task 的全部 `trace_index` 行，从 JSONL **全量重放**重建该 task 索引（幂等：重建以文件为唯一真源，重复执行结果一致）。终态任务与活动任务同规则 |
| **次序约束** | 索引对账先于崩溃标记（对账只读 TaskRecord/文件，不依赖任务状态；先对账保证后续 CrashRecovery 的 Trace 追加在完整索引之上） |
| **验收挂钩（WP-C 用例，决策官 TASK-40 落实）** | ① kill -9 注入：任务执行中强杀进程 → 重启 → 断言索引与文件一致（自动重建无人工干预）；② T2 复查：kill -9 前 `policy_denied` 事件在重启后仍可经 T2 单一查询命中 |

## 7. 实验/评估数据通道（11 号 §2.2 咬合）

实验每尝试一条 JSONL 记录：`taskId, specId, specVersion, modelId, strategy(A/B), attemptNo, verdict(L1/L2), failureClass, latencyMs`——全部字段可由 §2 信封 + §3 事件（`model_call_completed`（含 `strategy`，P2-4）/ `attempt_failed` / `contract_checked`）投影得出，即「实验数据 = Trace 数据」，不另设记录通道。

## 8. 脱敏机制（v1.1 重写——「已知接受项」升级为真实机制，D-11；推导：`docs/phase2/01` §4.6）

**处理位置：写入时脱敏，原文不落盘**（T3 精神外推——Trace 目录随演示包/开源仓库分发，是事实上的发布物；读出时脱敏要求原文落盘，与 T3 零密钥冲突；不可逆配合 digest 保序）。

**redactionPolicy（运行时配置，平台层——不进 Spec）：** `rules[].pattern`（正则，命中替换为 `[REDACTED:<ruleId>]`）+ `rules[].scope`（payload/all）+ `preserveDigests`（**true，不可关**）。默认规则集：① 密钥格式正则（**复用 T3 扫描清单同一载体**——复盘 §6-2「发布安全清单机制化」落点）；② email；③ 疑似 IP（可选）。

**不破坏 T1/T2 的四条机制（WP-2B 硬条款）：**
1. **脱敏排除表（白名单）：** §2 公共信封 10 字段、`task_started.bindingSnapshot`、全部 `*Digest` 字段——结构化字段不做正则脱敏，仅对自由文本载荷（input/output 原文、message、args/result 原文层）执行；
2. digest 在脱敏**前**按原文计算（跨任务对账稳定——灰度 report、记忆去重依赖）；
3. 脱敏动作留痕：事件载荷附 `redacted: [{ruleId, count}]` 摘要（不含原文）——「脱敏了什么」可审计，「被脱敏内容」不可恢复；
4. **T1/T2 回归断言前置：** 第一阶段 T1/T2/T3 验收脚本必须在脱敏开启库上原样重跑全过（批次二 DoD 硬条款——不过即设计失败，不留灰色态）。

**digest 预言机残余（已知接受，终审 P3-5 注记）：** 对 digest 验证存在低强度「猜测—验证」残余——已知接受，显式记录。

**叙事义务翻转（v1.1 修订，取代 v1「引入脱敏前不得以已脱敏作安全叙事」条款）：** 「Trace 已按配置规则脱敏，规则可枚举、命中可审计；脱敏是缩小暴露面的工程措施，**不是**绝对安全承诺（规则覆盖有边界，T3 发布安全断言独立成立）。」

**记忆 content 同管道（v1.1）：** MemoryRecord.content 过同一 redactionPolicy 管道（记忆内容 = 契约通过的 final output，仍执行规则脱敏）；脱敏管道为记忆的**前置不可削依赖**（规则集可裁、管道不可裁）。

### §8.1 v1.3 修订注记（2026-09-20，第三阶段批次一 · 口径冻结，D-19 冻结决策落地）

> **上位依据：** 《第三阶段设计文档》V0.2 §4.1（D-19 终审冻结）。本节为成文面修订，零数据回填、零行为变更（`task_record.input` 原文入库是第一阶段已验收行为，本版只补辖区归属，处置在批次二以机制收口）。

1. **硬条款辖区（冻结定义）：** 「原文不落盘」硬条款辖区 = **Trace 落盘物（JSONL 全量）+ 记忆 content**。辖区内写入时脱敏、原文不落盘、digest 原文口径——既有条款不变。
2. **本地数据域（新定义）：** SQLite 库（`shanhai.db` 全部表）、`data/` 目录、**`experiment-runs/` 目录**（实验运行自建独立 Runtime：独立 SQLite 库 + traces，`experiment/run.ts`——原文落盘面与主库同构，gitignore 与 T3 SKIP_DIRS 均已覆盖；存量实验库不回填，口径与 `data/` 同款）属**本地数据域**：不随发布物分发是本域唯一的安全依赖。
3. **防线措辞（精确化）：** 发布防线 = `.gitignore` 排除**一道**；T3 SKIP_DIRS 是扫描范围定义，机制上不承担防泄漏职能、**不计为防线**——不存在「双防线」，防线单一正是批次二机制化的理由。
4. **运维纪律条款：** 「运行时数据域不入发布物」列为运维纪律，含三个破例面，逐一点名：①**备份**（备份制品包含本地数据域文件时，制品本身即发布物等价物，须同规管理）；②**导出**（从 SQLite 库导出原文数据即离开本地数据域，导出物按发布物口径对待）；③**`SHANHAI_DATA_DIR` 重定向**（重定向至仓库工作树内时 gitignore 不再覆盖，本地数据域泄入发布面）。
5. **责任人条款：** 本地数据域的脱敏义务由批次二机制承担（入库前过同一 redaction 实例，见第三阶段设计文档 §4.2）——成文（本节）与机制（批次二）两道防线，终结「无条款认领」死角。
6. **风险边界（显式记录）：** 批次二完成前，本地数据域不外流为运维纪律，已知并接受。
7. **T3 未扫描残余口径（D-21 成文；批次四 P2-1 修订）：** T3 扫描的文本扩展名白名单外的文件中，**二进制探测判为二进制者 = 已知未扫描残余**（显式声明的接受面）；白名单外文本形态文件经二进制探测放行后按宽松解码扫描。残余**不属** exit 2「未扫描」语义——exit 2 覆盖「应扫而未扫」（短路根 / 扫描根不存在 / 不可读文件）。**不可读文件（EACCES 等）≠ 二进制残余（批次四 P2-1 区分）：** 读取失败的文件单列计数（汇总行「不可读 N 个文件」）、扫描不中断但终判 exit 2——不可读严格属「应扫而未扫」，不得混入二进制残余计数、不得以 exit 0「干净」放行。
