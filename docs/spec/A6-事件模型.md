## 1. 总体结构：两条流 + 一个绑定模型

| 流 | 载体 | 内容 | 消费者 |
|---|---|---|---|
| **Trace 流** | per-task 一个 JSONL 文件（`traces/<taskId>.jsonl`，追加 only） | 任务生命周期全部事件 | T1 查询、C2/实验报告、能力快照（只读降级形态） |
| **审计流** | SQLite `audit_events` 表（追加 only） | 版本事件（注册/发布/废弃/回滚）+ `RejectedRequest`（落库前拒绝 + CLI 拒绝） | T2 查询 |

**版本绑定模型（T1/T2 的地基）：** 任务创建时把 `{taskId, agentId, agentVersionId, specContentHash}` 固化进 TaskRecord **并作为每个 Trace 事件的公共信封字段**（§2）——任一事件单独取出都能定位当时生效的 Spec 版本。

## 2. Trace 事件公共信封（所有事件必带）

| 字段 | 类型 | 说明 |
|---|---|---|
| `eventId` | string | uuid v4 |
| `timestamp` | string | RFC3339 纳秒 |
| `traceId` | string | = taskId（第一阶段一一对应） |
| `taskId` | string | |
| `agentId` | string | |
| `agentVersionId` | string | **版本固定原则的字段落点（T1）** |
| `specContentHash` | string | 快照哈希（与 agentVersionId 双锚定） |
| `eventType` | string | §3 事件目录 |
| `attemptNo` | integer | 当前 attempt 序号（任务级事件为 0） |

OTel 语义对齐说明（降本措施，非接入承诺）：命名参考 `gen_ai.*` 约定（如 `gen_ai.usage.input_tokens`），便于第二阶段映射；不引入 Span 上下文传播。

## 3. Trace 事件目录（任务流，封闭集）

**层级：** `Trace（文件）→ 任务级事件 → attempt 级调用事件（model_call / tool_call / state_change）`。第一阶段为扁平 JSONL + `eventType` 判别层级，不建嵌套 Span 树（S 削减项：结构留给消费端聚合）。

| eventType | 层级 | 触发（对应 A3 迁移/流程） | 载荷字段（除信封外） |
|---|---|---|---|
| `task_created` | 任务级 | TaskRecord 落库 | `input`（摘要哈希 + 全文）、`inputContractHash` |
| `task_queued` | 任务级 | Created→Queued | `queueDepth` |
| `task_started` | 任务级 | Queued→Running | `bindingSnapshot`：`{toolVersions: [{toolId, implVersion}], modelId, promptHash}`（**T1 的工具/模型/Prompt 版本关联载体**） |
| `attempt_started` | attempt | 新 attempt 开始 | `attemptNo`、`kind`（model/tool） |
| `model_call_completed` | attempt | 模型调用返回 | `modelId`、`latencyMs`、`finishReason`、`usage: {inputTokens, outputTokens, estimated: bool}` |
| `tool_call_requested` | attempt | 模型请求工具 | `toolId`、`argsDigest`（参数哈希+受控字段实际值） |
| `tool_call_executed` | attempt | 工具放行执行完成 | `toolId`、`latencyMs`、`resultDigest`、`riskLevel`、`audited: bool` |
| `policy_denied` | attempt | A2 §5 拦截 | `toolId`、`reasonCode`、`consecutiveDenialCount`（**T2 的越权尝试记录**） |
| `attempt_failed` | attempt | Running→Running（新 attempt 前置） | `failureClass/subClass`（A4 attempt 级）、`willRetry: bool` |
| `task_succeeded` | 任务级 | Running→Succeeded | `outputDigest`、`outputContractVerdict` |
| `task_failed` | 任务级 | Running→Failed / Created→Failed | `failureClass/subClass`（终局归因）、`failureRecordId` |
| `task_cancelled` | 任务级 | →Cancelled | `cancelReason`、`graceful: true`（等待原子调用完成的语义标记） |
| `crash_recovery_marked` | 任务级 | 恢复路径 | `detectedBy`、`lastKnownStatus` |
| `contract_checked` | 任务级 | 输入/输出契约校验执行点 | `which: input/output`、`verdict`、`violations: [{path, expected, actual}]`（A4 expectedVsActual 同源） |

**写入规则（冻结）：** ① 每条迁移先持久化后继续（A3 不变式②在 Trace 侧同样成立：状态事件先落盘再执行后续动作）；② 事件追加 only，不更新不删除；③ 文件为 `traces/<taskId>.jsonl`，天然并行写安全（03 号 P2-3）。

## 4. RejectedRequest 审计记录（审计流）

| 字段 | 类型 | 说明 |
|---|---|---|
| `eventId` | TEXT PK | |
| `kind` | TEXT | `spec_registration / task_creation / cli_operation` |
| `who` | TEXT | 提交主体 |
| `when` | TEXT | RFC3339 |
| `target` | TEXT | agentId / taskId 候选 / CLI 目标 |
| `inputHash` | TEXT | 被拒输入的哈希（不存全文，防审计流膨胀） |
| `rejectReason` | TEXT | 结构化错误码 + 明细 |
| `agentVersionId` | TEXT NULL | 可定位时填写（**T2 按 Agent 版本检索的锚点**） |

## 5. 版本事件（审计流）

| eventType | 触发（A5） | 载荷 |
|---|---|---|
| `version_registered` | 注册成功 | agentId、versionId、contentHash |
| `version_released` | 发布 | + 指针旧值/新值 |
| `version_deprecated` | 废弃 | 同上 |
| `version_rollback` | 指针回滚 | + 指针旧值/新值、操作者 |

## 6. T1/T2 单一查询口径（验收断言映射）

| 断言 | 查询形态（单一查询 = 一次 SQLite join / 一个 JSONL 文件内 grep-able） | 依赖字段 |
|---|---|---|
| **T1**：给定任一 Failed 任务 Trace，返回当时生效 Spec 版本及 Prompt/工具版本关联 | `traces/<taskId>.jsonl` 内：信封字段（agentVersionId + specContentHash）→ Registry 取快照；`task_started.bindingSnapshot` 取 Prompt 哈希与工具实现版本。**单文件 + 单表查询，无跨系统步** | §2 信封 + §3 `task_started` |
| **T2**：给定任一 Agent 版本，返回运行期全部越权尝试与拦截点 | `audit_events WHERE agentVersionId=? AND kind='task_creation'`（被拒任务）∪ 各 trace 文件内 `policy_denied` 事件（按 agentVersionId 信封过滤，SQLite trace 索引表支撑） | §4 + §3 `policy_denied` + §2 信封 |

**支撑索引（WP-B 建表义务）：** `trace_index(taskId, agentVersionId, eventType, timestamp)`——JSONL 为主存储、SQLite 为索引的混合形态，保证 T1/T2 是库内单查询而非文件系统遍历。

## 7. 实验/评估数据通道（11 号 §2.2 咬合）

实验每尝试一条 JSONL 记录：`taskId, specId, specVersion, modelId, strategy(A/B), attemptNo, verdict(L1/L2), failureClass, latencyMs`——全部字段可由 §2 信封 + §3 事件（`model_call_completed` / `attempt_failed` / `contract_checked`）投影得出，即「实验数据 = Trace 数据」，不另设记录通道。

## 8. 已知接受项（显式声明，03 号 R-2）

第一阶段 Trace 中模型输入/输出可能含敏感数据（`task_created.input`、digest 之外的原文层）；**不脱敏，且在引入脱敏前不得以「Trace 已脱敏」作任何安全叙事**。digest 字段（argsDigest/resultDigest/outputDigest）为 SHA-256 摘要，用于索引与去重；原文保留策略属第二阶段。

## 9. 关键假设 / 风险 / 待验证

| # | 内容 | 属性 |
|---|---|---|
| 1 | 扁平 JSONL + eventType 判别（无嵌套 Span）足以支撑 T1/T2 与 C2 报告 | 设计假设（消费端聚合；第二阶段接 OTel 时再补层级） |
| 2 | trace_index 索引表与 JSONL 双写的一致性（先索引后文件，或反之） | 设计决策点（建议：先 JSONL 后索引，崩溃时以文件为准重建索引——幂等） |
| 3 | `bindingSnapshot.toolVersions` 依赖 Tool Registry 提供实现版本号 | 设计假设（WP-B 工具注册须含 `implVersion` 字段——已列入 WP-B 输入） |
| 4 | 敏感数据不脱敏 | 已知接受（显式声明） |
