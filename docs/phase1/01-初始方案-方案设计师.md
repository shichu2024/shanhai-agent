## 1. 问题理解

### 1.1 背景与真实目标

用户以基线文档为「最基础的」设计输入，要求三个角色充分讨论后产出**第一阶段设计文档**，并将全部讨论过程归档到 GitHub。

真实目标不是重写基线文档，而是：

1. 将基线文档中「愿景级」的完整架构（12 神兽、6 个 Phase、V1.1 MVP 清单）**收敛为第一阶段可落地、可验收的工程范围**；
2. 补齐基线文档中缺失或损坏的关键设计定义（见 1.3）；
3. 通过对抗式审查，在动工之前暴露设计分歧、隐含假设和高风险决策点。

### 1.2 表面需求 vs 核心问题 vs 潜在问题

- **表面需求**：输出一份第一阶段设计文档。
- **核心问题**：基线文档描述的是终态蓝图，但没有回答「第一步做什么、做到什么程度算完成」；第一阶段范围若不收敛，极易滑向「什么都做一点、什么都不可用」。
- **潜在问题**：
  - 基线文档本身存在大面积内容缺失（见 1.3），若直接照单实施，会在中途才发现关键定义不存在；
  - 技术栈、存储方案、部署形态在基线文档中完全未指定，属于被回避但无法回避的决策；
  - 「第一阶段」存在两种解读（见 §2.1），若三角色与用户理解不一致，验收标准将失去意义。

## 2. 目标与非目标

### 2.1 「第一阶段」的范围界定【设计假设，需反方与决策官确认】

基线文档 §21 路线图划分了 Phase 0（抽象设计）至 Phase 6。本方案将「第一阶段」定义为：

> **Phase 0（抽象设计）+ Phase 1（最小 Runtime）合并执行，产出为一个可以端到端演示的最小系统。**

理由：Phase 0 是纯设计工作，其全部产出（领域模型、Spec、状态机）恰好是 1.3 所列缺失项；把它与 Phase 1 合并，可以让设计定义直接被代码验证，避免「纸上架构」与实现脱节。

**范围张力（需裁决）**：基线 §22.1 的 V1.1 MVP 清单比 Phase 1 宽（含 Memory、Evaluation、Capability Profile、人工审批、发布回滚）。本方案建议第一阶段**只做 MVP 清单中与最小 Runtime 重叠的子集**，其余（Memory、Capability Profile、人工审批、发布回滚）推迟到第二阶段，仅在第一阶段为其预留数据模型字段和接口位。

### 2.2 第一阶段目标

1. **G1 设计重建**：补齐 1.3 所列全部关键定义，形成《山海司核心规格 V0.1》（领域模型、Agent Spec Schema、Task 状态机、失败分类、版本状态）。
2. **G2 最小 Runtime**：实现 Agent Registry、Agent Version、Task Manager、Model Gateway、基础 Tool Executor、State Manager、基础 Trace、基础错误处理。
3. **G3 端到端验收**：至少 1 个示例 Agent 完成「Spec 定义 → 注册 → 任务执行 → 工具调用 → Trace 记录 → 结构化结果输出」全链路。
4. **G4 过程归档**：三角色全部讨论与设计产物纳入本仓库 `docs/` 目录，Git 版本化管理。

### 2.3 第一阶段非目标

- 不实现女娲 Builder、白泽灵识系统、白虎完整评估、鲲鹏 Federation、九尾狐、饕餮、朱雀（仅允许定义其数据模型占位）；
- 不实现 MCP 接入与 A2A 协议（接口预留）；
- 不实现多 Agent 协作、长任务 Checkpoint/断点恢复、灰度发布、沙箱（沙箱第一阶段仅做进程内隔离与白名单校验）；
- 不建设任何 Web 控制台/UI（CLI 即第一阶段交互界面）；
- 不追求生产级高可用与分布式部署。

### 2.4 成功与失败的定义

- **成功**：G3 验收演示通过；核心规格文档经三角色评审定稿；全部讨论归档至 GitHub。
- **失败**（任一即算）：需要手工改代码或改数据库才能跑通的「演示」；Spec 定义了但没有被 Runtime 强制执行（如 Tool Policy 形同虚设）；无 Trace 可查；关键定义仍是截断状态即开工。

## 3. 总体思路与设计原则

### 3.1 总体思路

**「小内核、硬边界、证据先行」**：

1. **小内核**——第一阶段只做一个单体 Runtime（应龙最小形态），其余神兽以「模块边界 + 数据模型占位」存在，不做独立服务。
2. **硬边界**——Agent Spec 是可执行契约：Runtime 在加载和运行时强制校验 Spec（工具白名单、模型白名单、调用预算），违反即拒绝执行并记录。规格不被执行就不是规格。
3. **证据先行**——从第一个任务起就产出结构化 Trace 与失败记录；这些数据是第二阶段白泽/白虎/女娲的全部输入，没有它们后续无从谈起。

### 3.2 设计原则（继承基线并具体化）

1. 版本固定：一次 Task 执行绑定 Agent/Prompt/Model/Tool 版本（Task 记录中落库）。
2. 策略先于执行：模型调用、工具调用先过 Policy 检查。
3. 默认拒绝：未在 Spec 中声明的工具与模型一律不可用。
4. 最小权限：第一阶段工具风险等级只开放 L0–L2；L3/L4 仅定义枚举与拦截逻辑（拦截即成功，不需要审批流）。
5. 可回滚：Agent Version 采用不可变记录 + 「当前版本」指针，回滚即移动指针。
6. 演进预留：所有核心表为 Memory/Evaluation/Evolution 预留外键字段，但不实现其行为。

## 4. 方案组成

第一阶段交付物分四个工作包（WP）：

### WP-A：核心规格与设计重建（对应 Phase 0 / G1）

| 交付物 | 内容 | 补齐的基线缺失 |
|---|---|---|
| A1 领域模型规格 | Project / Agent / AgentVersion / Task / Tool / Evaluation / Evolution 完整字段定义与关系图 | §5 |
| A2 Agent Spec Schema v1 | Identity、Mission、Responsibilities/Non-Responsibilities、Input/Output Contract（JSON Schema）、Model Policy、Tool Policy、Evaluation Policy（最小）、Evolution Policy（仅边界声明） | §6.2 |
| A3 Task 生命周期状态机 | 完整状态枚举与合法迁移表（见 §5.1 本方案给出的草案） | §7.3/7.4 |
| A4 失败分类 v1 | Input / Planning / Model / Tool / Policy / Runtime / Output 等失败类型枚举与 FailureRecord 结构 | §16.1 |
| A5 版本状态机 | Draft → Reviewed → Released → Deprecated（+ Rollback 语义） | §20.2 |
| A6 Trace 事件规范 | Trace → Task Span → ModelCall/ToolCall/StateChange 事件层级 | §15.2 |

### WP-B：最小 Runtime（对应 Phase 1 / G2）

模块化单体，进程内分层：

```text
shanhai-runtime（单体）
├── AgentRegistry      Agent 与 AgentVersion 的注册、查询、版本指针管理（不可变版本记录）
├── SpecValidator      加载时校验 Spec 合法性与完整性（基于 A2 的 JSON Schema）
├── TaskManager        任务创建、排队、生命周期驱动（A3 状态机）、超时控制
├── ModelGateway       模型调用统一入口：Provider 适配、白名单校验、超时/重试/预算控制
├── ToolExecutor       工具调用统一入口：白名单、参数校验、风险等级检查（L0–L2 放行、L3+ 拦截）、超时、审计记录
├── StateManager       Task 运行状态持久化（含版本绑定快照）
├── TraceRecorder      结构化 JSONL 事件写入（A6 规范；OTel 兼容字段命名，OTel 导出器延后）
└── FailureRecorder    失败记录落库（A4 分类）
```

### WP-C：示例 Agent 与端到端验收（G3）

- C1 示例 Agent「精卫·取数」：输入一个查询意图 → 调用 1 个 L0 工具（如本地只读查询）→ 返回符合 Output Contract 的结构化结果。
- C2 验收脚本：从 Spec 文件注册 → 提交任务 → 全链路 Trace 落盘 → 断言输出契约通过、Trace 事件完整。
- C3 反向验收（同样重要）：一个故意越权的 Spec（声明了未注册工具）必须被拒绝；超预算调用必须被截停并记录失败。

### WP-D：讨论与文档归档机制（G4，满足硬性要求）

- 仓库内建立 `docs/phase1/` 目录，本文件即第一篇；
- 每一轮角色输出（方案初稿、审查报告、修订表、复审、最终裁决）各成一个编号文件提交；
- 最终定稿文档以 `docs/phase1/第一阶段设计文档-定稿.md` 收口，并在仓库 README 建立索引。

### 4.1 技术选型建议【设计假设，欢迎反方挑战】

| 决策点 | 建议 | 备选 | 理由 |
|---|---|---|---|
| 语言/运行时 | TypeScript (Node.js) | Go | LLM SDK 生态最全、Schema 工具链成熟（JSON Schema/zod）、迭代速度快；Go 在运行稳定性和并发上更优但第一阶段无此压力 |
| 架构形态 | 模块化单体（单进程） | 微服务 | 第一阶段无扩展压力；模块间用接口隔离，保留拆分可能 |
| 结构化存储 | SQLite | PostgreSQL | 零部署成本、单文件可随仓库归档；数据模型与 SQL 方言保持 PG 兼容以便迁移 |
| Spec/版本制品 | 文件系统 + Git | 数据库 | Spec 即代码，可 diff、可审查、可回滚，天然满足「归档到 GitHub」 |
| Trace 存储 | JSONL 文件 | OTel Collector | 零依赖起步；字段命名对齐 OTel 语义约定，第二阶段平滑接入 |

## 5. 关键流程

### 5.1 Task 生命周期状态机（本方案草案，补齐基线 §7.3/7.4）

```text
Created → Queued → Running → Succeeded
                       ├→ Failed        （执行失败，已记录 FailureRecord）
                       ├→ Timeout       （超时，计入失败分类）
                       └→ Cancelled     （用户/系统取消）
Queued → Cancelled
Failed/Timeout → Retrying → Running    （仅幂等任务允许，重试上限由 Spec 声明）
```

不变式：任何终态（Succeeded/Failed/Timeout/Cancelled）不允许再迁移；状态迁移即 Trace 事件。

### 5.2 正常流程（端到端）

1. 用户通过 CLI 提交任务（引用 agentId + 输入）。
2. TaskManager 创建 Task（Created），加载 Agent 当前版本，**固化版本绑定快照**。
3. SpecValidator 校验 Spec；不合法 → Task 直接 Failed（FailureRecord: Input/Spec 类）。
4. Queued → Running；ModelGateway 按 Model Policy 调用模型（白名单 + 预算检查前置）。
5. 模型请求工具 → ToolExecutor 检查白名单/风险等级/参数 → 执行 → 审计记录。
6. 输出经 Output Contract 校验 → Succeeded；结果与 Trace 落盘。
7. 全程每个关键动作产生 Trace 事件（A6）。

### 5.3 异常流程

- **模型超时/故障**：按 Model Policy 重试；超出次数 → Failed（Model 类失败）；有降级模型则切换并记录。
- **工具失败**：L0–L2 工具失败按重试策略处理；仍失败 → Failed（Tool 类失败）。
- **L3/L4 工具请求**：直接拦截，Task 记录 Policy 拦截事件，任务继续或按 Spec 声明失败（拦截本身是预期行为，不是系统故障）。
- **预算超限**：截停当前调用链 → Failed（Runtime 类失败，标注 BudgetExceeded）。
- **进程崩溃**：第一阶段接受任务丢失，但重启后 StateManager 能将遗留 Running 任务标记为 Failed（崩溃恢复最小版）；Checkpoint/断点恢复为第二阶段。

### 5.4 边界情况

- 输入不符合 Input Contract：创建阶段即拒绝，不进入队列。
- 同一 Agent 并发多任务：允许（无共享可变状态；Agent 版本不可变保证一致性）。
- Spec 引用了不存在的工具/模型：注册阶段（而非运行阶段）即拒绝。
- 空结果：Output Contract 中显式声明 `allowEmpty`，未声明而输出空 → 判定失败。

### 5.5 职责与触发

- 谁做：本阶段全部逻辑由 Runtime 单体承担；「谁负责」在代码层表现为模块归属（见 WP-B），无人工流程环节（审批流延后，L3+ 一律拦截）。
- 何时触发：任务提交触发执行链；注册触发校验；每次调用触发策略检查与 Trace。

## 8. 取舍说明

- **接受「单体 + SQLite + 文件」的简单性，牺牲分布式与扩展性**：适用条件——单机、单用户、演示与实验负载；当出现多用户并发或生产部署需求时此方案不再适用，需引入 PG 与服务化拆分（接口已预留）。
- **接受审批流缺位，用「L3+ 一律拦截」替代**：安全性不降级（宁可拦死不可放过），牺牲了第一阶段做有副作用任务的能力。
- **接受崩溃后任务丢失（仅标记失败）**：换取不实现 Checkpoint 的 simplicity；长任务是第二阶段鲲鹏的事。
- **接受 Trace 仅 JSONL**：换取零依赖；用字段命名对齐 OTel 控制迁移成本。
- **不做 UI**：CLI + 文件即第一阶段的全部人机界面，全部精力投入 Runtime 内核。

## 9. 特别要求清单

### 9.1 最容易被忽略的三个问题

1. **基线文档是残缺的**（§1.3）——最危险的不是已识别的缺失，而是「读起来通顺但语义不完整」的段落造成的设计者错觉。
2. **Spec 不被强制执行就等于没有 Spec**——SpecValidator 与 Policy 检查若只做形式校验，整个「规格驱动」理念在第一行代码就破产。
3. **Trace 从第一天就要落盘**——第二阶段白泽/白虎/女娲完全依赖第一阶段的运行证据；第一阶段的「临时省略」会让第二阶段从零开始。

### 9.2 最可能失败的三个场景

1. Model Gateway 对真实 LLM 的不稳定输出缺乏防御（超时、格式漂移、拒答），导致端到端演示脆弱。
2. Spec Schema 设计过重（追求覆盖基线全部 Policy 字段），导致示例 Agent 定义成本过高、验收跑不通。
3. 范围解读分歧（§2.1 的 MVP vs Phase 1）在三角色间未收敛，各自按不同预期产出，最终返工。

### 9.3 当前方案最依赖的三个假设

1. 第一阶段单体架构不会很快成为瓶颈（即短期内无多用户/生产压力）。
2. LLM 输出可被契约约束到可度量通过率（§7-4）。
3. 用户认可「L3+ 拦截」替代审批流的权宜方案。

### 9.4 最值得被反方挑战的三个设计点

1. **技术选型（TypeScript/SQLite/单体）**——是否有 Go/PG/服务化视角的强理由推翻。
2. **第一阶段范围切割**——把 Memory、Capability Profile、人工审批、发布回滚推出第一阶段是否正确（基线 MVP 清单明确包含它们）。
3. **「拦截代替审批」的安全策略**——是否过于保守，或反而隐藏了「将来补审批流时 Runtime 控制流需要重构」的成本。

### 9.5 资源/时间/人员缩减时的削减顺序

1. 先砍 C1 示例 Agent 的丰富度（保留 1 工具，不做多轮对话）；
2. 再砍 StateManager 崩溃标记，接受重启后遗留脏状态（人工清理）；
3. 最后砍 A4/A5/A6 中与 Runtime 无直接执行依赖的文档细节（保留枚举定义，砍说明文字）。
不可削减底线：SpecValidator、Policy 强制检查、Trace 落盘、版本不可变。

### 9.6 规模扩大时最先成为瓶颈的部分

1. JSONL Trace 的查询与聚合（最先崩，需迁 OTel/ClickHouse 类方案）。
2. TaskManager 的进程内队列（需引入持久化队列/消息中间件）。
3. SQLite 写并发（需迁 PostgreSQL）。
4. 单体代码库的模块边界纪律（需以 repo/服务边界物理化拆分）。
