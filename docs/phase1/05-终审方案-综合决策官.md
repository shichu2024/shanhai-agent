## 3. 最终方案（冻结版）

### 3.1 阶段界定与范围基线

第一阶段 = Phase 0（抽象设计）+ Phase 1（最小 Runtime）合并执行，产出端到端可演示的最小系统。范围基线以用户确认结果为准（A/B/C 三选项，决策官推荐 B，见 §3.5 与 §5）。**任何选项下均不变的结构**：三条设计底线、四个工作包、技术栈、核心机制（§3.3/§3.4）。

三条设计底线（不可削减）：
1. Spec 必须被 Runtime 强制执行（否则「规格驱动」不成立）；
2. Trace 从第一个任务起落盘（第二阶段白泽/白虎/女娲的全部输入）；
3. AgentVersion 不可变（注册时全文快照入库）。

### 3.2 工作包与责任边界

| 工作包 | 内容 | 前置条件 | 责任边界 |
|---|---|---|---|
| WP-A | A0 基线残缺扫描（**已解除阻塞，可立即启动**）；A1 Spec Schema；A2 Model/Tool Policy；A3 Task 状态机；A4 失败分类；A5 版本状态机；A6 事件模型 | A0 无前置；A1–A6 以用户范围裁决为前置 | 每个 A 项 DoD：字段表完整 + 可直接映射为 WP-B 对应模块实现输入 + 三角色各一票 + 决策官终审签字 |
| WP-B | 最小 Runtime 模块化单体：Registry / SpecValidator / TaskManager / ModelGateway / ToolExecutor / StateManager / TraceRecorder / FailureRecorder | WP-A 对应 A 项通过 DoD | 模块间接口隔离；无服务化拆分 |
| WP-C | C1 端到端演示；C2 契约通过率验收；C3 反向验收 | WP-B 完成对应模块 | 验收标准见 §4，已冻结 |
| WP-D | 讨论归档机制（docs/phase1/ 逐轮提交 GitHub） | 无 | 本目录即履约记录 |

### 3.3 技术决策冻结表

| 决策点 | 冻结结论 |
|---|---|
| 语言与架构 | TypeScript 模块化单体（zod/JSON Schema 服务 SpecValidator） |
| 结构化存储 | SQLite；Spec 注册全文快照入库（不可变）；文件改动必须重新注册生成新版本 |
| Git 角色 | 审计历史与 diff，不承载版本内容 |
| Trace | per-task JSONL 文件；OTel 语义命名为降本措施，非接入承诺 |
| 迁移承诺 | ERD 与 ORM 查询层可迁移，不承诺 DDL 级方言兼容 |

### 3.4 核心机制冻结

- **Task 状态机 V0.2**：`Created / Queued / Running / Paused(空壳) / Succeeded / Failed / Cancelled`；重试 = Running 内新 attempt（maxAttempts 默认 3）；Timeout 收敛为 Failed.failureClass（任务级/调用级分层）；终态无出边；每条迁移先持久化后继续；状态迁移即 Trace 事件；崩溃恢复：重启发现非终态遗留 → Failed:Runtime(CrashRecovery)。
- **预算模型**：maxModelCalls + maxTokens（任务级）；usage 以 provider 返回为准、缺失本地估算并标注 estimated。
- **工具策略**：L0–L2 放行（L1/L2 审计，L2 必须声明受控字段），L3/L4 拦截；拦截返回结构化 policy_denied（含 reasonCode）；maxConsecutiveDenials 默认 2，超限 → Failed:Policy(PolicyBlocked)。
- **版本状态机**：Draft → Released → Deprecated + `shanhai agent rollback` 指针回滚 CLI。
- **取消语义**：等待当前原子调用完成后取消。
- **审计边界**：TaskRecord 落库前校验失败 → RejectedRequest 审计（无 Task）；落库后校验失败 → Created→Failed（一行判定规则写入 A3）。

### 3.5 范围选项 B 的并入形态（推荐，待用户确认）

| MVP §22.1 差额项 | 选项 B 下的第一阶段形态 | 成本 |
|---|---|---|
| 基础 Evaluation | C2 通过率统计 + FailureRecorder 聚合报表 | ≈0（本就在验收设计内） |
| Capability Profile | 基于 Trace/FailureRecord 的只读能力快照（无独立 Registry） | ≈0 |
| 基础 Memory | 仅工作记忆（任务内上下文），不做持久化与可信度状态机 | ≈0 |
| 发布与回滚 | 版本指针回滚 CLI（已并入 §3.4） | 已计入 |
| 人工审批 | **延后至第二阶段**（Paused 空壳 + ApprovalRequest 预留已到位） | 若强行并入：Paused 完整实现 + 挂起/恢复语义 + CLI 审批交互，三处结构改动，工期显著延长 |

理由：4 项以近零成本并入，将「裁剪用户明示需求」的授权争议从 5 项收窄到 1 项；人工审批是唯一不可极小成本并入项，且其第二阶段引入点已完成结构预留。
