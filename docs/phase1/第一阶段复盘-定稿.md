## 3. 假设 #4 实验结论（LLM 输出契约可约束性）

**结论：策略 A（原生 structured output）与策略 B（纯 Prompt 声明）六层首次通过率全部 ≥80% 决策线，未触发第二阶段显式决策点。** 模型 glm-4.6（单一、版本钉死、temperature=0），制品冻结 `3e4fca3af01…`，N=30/策略（3 Spec 分层 × 10），数据通道 = Trace 标准通道。

| 策略 | s1-summary | s2-extraction | s3-decision-report |
|---|---|---|---|
| A（原生） | 100% | 90% | 90% |
| B（Prompt） | 90% | 100% | **80%（压线）** |

- A 的失败样本仅 2 例 attempt 级 `call_timeout`（重试后全过，含重试通过率 100%）；B 的失败集中于 `schema_violation` / `truncation`（s1×B 含 1 例终局失败，含重试通过率 96.7%）。
- **引用限制声明（冻结）：s3×B 恰压 80% 线，Wilson 95% 下界 49%——第二阶段扩样前，不得引用该层作更强结论。** 小样本不确定性如实成立（N=10/层时 80% 观测率的 95% CI 约 49%–94%）。
- 成本代理口径修正（F-2）：报告原按 `model_call_completed` 计数漏计失败 attempt，已按 `attempt_started`（已发起口径）重算注记——s2×A 1.10、s3×A 3.10；通过率与 CI 不受影响，聚合代码已改口径。

## 4. F-1 全过程案例（「规格冲突如何被验收暴露」过程资产）

**缺陷**：CLI 分两进程 `task create` → `task run` 时，run 进程启动即执行 A3 §6 崩溃恢复扫描，Queued 任务被误迁移 `Failed:Runtime(CrashRecovery)`——文档化工作流（README 快速开始）不可走通，任务永不可执行。

**全过程（六步）**：

1. **发现（验收侧）**：WP-C 验收执行中发现，Trace 序列存证（`task_queued → crash_recovery_marked → task_failed`，`startedAt=null`）——13 项验收断言本身不含该路径，属验收执行中的路径外观察。
2. **定位**：根因为规格内冲突——A3 §6（Queued/Running 无差别迁移、无归属概念）× A5 §2 / README（create/run 分进程）。单测与实验均单进程故不暴露：**单进程假设掩盖了多进程工作流**。
3. **方向性裁定（决策官）**：不阻断 WP-C（缺陷不在验收断言路径上）但不得带病结项；修复方向 = 扫描收窄至仅 Running（只迁移有执行副作用的状态），Queued 真丢失防护限定最小手段，禁止重机制。
4. **修订（方案设计师，`6761b3b`）**：A3 §6 重写（收窄 + Queued = durable pending 语义澄清 + 只读警示边界）+ A4/A6 共 3 处跨文档一致性修正——**只改 A3 会把规格内冲突换个位置保留**。
5. **修复（执行官，`faabf68`）**：`WHERE status = 'running'` 一行收窄 + F-2/F-3/F-4 同批 + 新增 4 单测（54/54）；诚实声明：真实模型路径本环境缺密钥不可执行。
6. **重验（反方审查官，`4b2c1a2`）**：4 条机械标准全过，含在持密钥环境按 README 原样补验真实模型两进程路径（46 事件 0 次 `crash_recovery_marked`）；kill -9 三条原样重跑确认收窄未破坏崩溃恢复本体。

**可复用教训**：

- 规格条款的适用范围要写明「进程模型」假设——「重启恢复」在单进程内嵌测试里永远正确，在分进程 CLI 里就是缺陷；验收必须覆盖文档化工作流而非仅规格断言路径。
- 跨文档引用同一机制时，修订必须全链一致（A3/A4/A6 三处）。
- 环境受限方的诚实声明 + 持钥方的补验衔接，比「假装跑过」或「整体降级为 mock」都更可靠——本轮闭环链的正确运转方式（终审裁定语）。
