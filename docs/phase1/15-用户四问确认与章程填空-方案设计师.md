## 2. 逐问解读与落点

### 问① 场景真实性 → 答案重构了 A-1 的形态（非「否」，不触发终止规则）

用户场景 = **「从零了解一个 Agent 完整的验证流程」**——学习/理解目标，而非 08 号假设的「长期运行 + 审计治理的生产资产」场景。诚实记录三点：

1. **A-1 原口径未被确认**，但也未被否定——用户的真实目标与第一阶段交付物高度兼容：最小系统端到端跑通「定义 → 执行 → 证据 → 评估 → 验收」，正是一条**可亲身运行、可逐步拆解的完整验证流程**。对学习者而言，T1/T2 断言与 Trace 落盘就是「验证流程可被亲手检验」的保证；
2. **价值排序变化（供定稿采用）**：第一阶段的第一价值主张从「生产治理地基」调整为「**完整验证流程的可运行参考实现**」——可演示性、可读性、可跟随复现的权重上升；差异化论证（08 号）降级为开源定位的支撑材料，不再是用户侧立项主因；
3. **A-5 痛点清单**因此定性为「用户认知框架」而非「生产实证」——定稿叙述按此校准，不作夸大。

### 问② 目标形态 = 开源项目

## 3. 新增硬性安全规则的落地（写入章程 §4/§7）

| 规则 | 落地 |
|---|---|
| 线上/发布产物不得包含模型与密钥 | Provider/模型配置一律走配置文件模板 + 环境变量/本地配置注入；仓库与发布物中只留 `config.example`（占位值）；`.env`、密钥文件入 `.gitignore` |
| 仅可支持配置 | Runtime 的 ModelGateway 以「无配置即拒绝启动」为实现原则（与 V0.2「确定性预算注入」同一风格：约束在入口强制，不靠约定） |
| 验收断言（新增 T3） | 发布产物扫描：构建输出中不得出现任何密钥形态（已知密钥格式正则 + 模型权重文件），出现即验收不通过 |
