## 第一部分：V0.2 全案 Pre-mortem

### 1.1 方法与设定

**思想实验**：假设现在是实施周期结束后的复盘日，第一阶段已被宣告失败。从「失败」这一既定事实反推死因，按 **概率 × 伤害** 排序。每条死因给：失败叙事 → 根因链 → 早期预警信号 → 最早的不可逆点 → 预防/缓解。

**审查对象**：V0.2 全案 = 01/03/05/08/09/11 号文档构成的合并方案（Phase 0+1 合并、四工作包、三底线、判定线体系）。

### 1.2 死因清单（按概率 × 伤害排序）

#### 死因 #1「无人区死亡」：定稿与实施之间没有 owner（概率最高）

- **失败叙事**：2027 年中，`docs/phase1/` 收录了 14 份高质量文档与一份用户确认，仓库 `src/` 目录为空。第一阶段不是失败于做错，而是失败于**从未开工**。
- **根因链**：本议题的交付物是设计文档 → 三角色权限与激励都终止于「定稿收口」→ 11 份文档中没有任何一份指明 WP-B 的实施者、时间盒、环境与密钥预算 → 设计资产停在 Git 里自然过期（基线残缺的下场重演：文档腐烂）。
- **早期预警信号**：第 5 轮裁定收口时，产物清单里只有 `第一阶段设计文档-定稿.md` 而无实施章程。
- **最早的不可逆点**：定稿发布日。此后三角色协作解散，「谁来做」变成无主问题。
- **预防/缓解（成本：一份文档）**：定稿 = 设计文档 + **最小实施章程**（实施 owner、时间盒、按 01 §9.5 削减顺序排好的资源预案、密钥与环境清单）。建议决策官裁定：无实施章程不定稿。

#### 死因 #2「三问悬置」：外部依赖无时限，或答案为否定后沉没成本拖延

- **失败叙事**：用户三问（场景/形态/范围）发出后长期未复，或答「①否」；讨论以「再等一轮」「再补一个论证」继续消耗轮次，正确的终止决定（08 §3.4：场景为否则不立项）被 14 份文档的沉没成本绑架。
- **根因链**：09 号 §4 把三问设为唯一外部依赖，但**没有设定悬置处理规则与终止执行条件**——「①否 → 停止」写了结论，没写谁在何时执行。
- **早期预警信号**：三问发出后 2 周无回复；或用户答「①否」后仍出现新讨论文档。
- **最早的不可逆点**：WP-B 动工日（若在否定性回答前动工，投入作废）。
- **预防/缓解（成本：一条裁定）**：决策官现在设定两条规则——(a) 三问未复期间 WP-B/WP-C 不启动，A0 类纸面工作可继续；(b) 用户答「①否」时，本轮立即转为**终止性收敛裁定**，将 10/11 号文档资产标注为「可复用于组合方案实施」（Trace 数据模型、步数法协议、假设 #4 实验设计均可移植），终止不是作废。

#### 死因 #3「空心地基」：Trace 落盘了，但证据不可用（伤害最大）

- **失败叙事**：第一阶段验收全绿（事件存在、契约通过、拦截生效），第二阶段白泽/女娲开工时发现：Trace 字段口径漂移、span 关联断裂、失败分类互相污染——**落盘 ≠ 可用证据**。D2/D4 是仅有的无可替代主张，其地基（证据质量）从第一天就是坏的，且无人验收过质量。
- **根因链**：C2 验收断言的是「Trace 事件完整」（存在性），不是「Trace 能回答问题」（可用性）；A6 事件规范有层级定义，无**内容质量判据**。
- **早期预警信号**：验收脚本里对 Trace 的断言只有 `events.length > 0` 类检查；抽查两条 trace 无法拼出一次失败的完整因果链。
- **最早的不可逆点**：第一批真实任务跑完（脏数据模式固化进使用习惯与下游脚本）。
- **预防/缓解（成本：两条验收断言）**：**把 11 号的 Q1/Q4 查询变成自家验收**——山海司宣称 Q1（从失败 Trace 定位 Prompt/工具版本）与 Q4（证明白名单全程强制、拦截可举证）在自家系统为「0 跨系统步」，则 C2 验收增加两条机械断言：验收脚本必须能在单一 SQLite/Trace 查询内回答 Q1 与 Q4。答不出 = 地基空心，验收不通过。这一条同时是 11 号自请挑战点②的解（见第三部分）。

#### 死因 #4「安全但无用」：L3+ 全拦导致用户绕过平台

- **失败叙事**：真实业务任务大多需要 L3 副作用（发消息、写数据），平台一律拦截，输出清一色 `PolicyBlocked`；用户在平台外直接调工具完成任务——平台技术上零事故，社会上**零采用**。
- **根因链**：前 4 轮只审查了「拦截代替审批」的技术重构成本（P1-2），未审查其**采用成本**；C1 示例 Agent 是只读取数任务，永远暴露不了这条死因。
- **早期预警信号**：C1/C2 的全部任务都是只读；没有任何真实业务任务被放进验收集。
- **最早的不可逆点**：用户第一次绕过平台完成任务（习惯形成）。
- **预防/缓解（成本：一次沟通）**：范围 B 的定稿显式声明第一阶段价值主张 =「只读/低风险自动化 + 证据地基」，副作用任务明示为第二阶段（审批流就位后）；C1 至少纳入 1 个真实业务场景的只读任务（哪怕就是「对本仓库做只读分析」），让演示回答真实问题。

#### 死因 #5「S3 塌方」：假设 #4 失败于高复杂度契约，演示脆弱

- **失败叙事**：C2 实测 S3（混合契约）含重试通过率 < 80%，触发第二阶段决策点——但第二阶段远未到，眼前是第一阶段演示；临时降复杂度、改 Spec、回写 A2 规则的循环把演示窗口拖垮。
- **根因链**：已有分支预案（11 号 2.3）处置判定，但**没有处置时间**——实验时点在 WP-C 验收前，留给修复的余量为零。
- **早期预警信号**：S2（中复杂度）首次通过率 < 85%。
- **最早的不可逆点**：WP-B 就绪后的第一周实验结果。
- **预防/缓解（成本：演示脚本预案）**：实验前置于 WP-B 最早可跑时点（11 号已定，强调执行）；演示脚本预置 S1/S2 降级版路径，S3 塌方时演示叙事退到「分层契约规则已产出」而非硬扛。

#### 死因 #6「纸面数字反噬」：实测推翻 A-3 判定，立项依据事后受损

- **失败叙事**：WP-B 就绪后按 11 号协议实测组合方案，发现 Q1 实际 ≤2 步（本报告抽查已证实 prompt-trace 关联存在，见第二部分），A-3 判定线第 3 行生效；但定稿已把「A-3 成立」写成立项依据，外部读者拿实测反推「立项论证注水」。
- **根因链**：11 号诚实标注了「纸面量化、待实测校准」，但**定稿引用时的口径未约束**。
- **预防/缓解（成本：一句措辞）**：定稿风险节将 A-3 表述为「纸面判定成立（判定线 2026-09 快照），实测协议随附，允许被校准」——把数字写成可校准的快照而非结论。

#### 死因 #7「演示事故」：L2 副作用 + 取消等待语义 + 无沙箱的真实破坏

- **失败叙事**：演示中一个 L2 工具（临时文件/草稿提交）在被取消的任务里仍然完成副作用，或写错位置；「平台治理」叙事当场反转为「平台闯祸」。
- **根因链**：P2-5 裁定的取消语义（等待原子调用完成）防了状态错位，**没有防副作用可见性**——Cancelled 任务留下一堆已生效的副作用。
- **预防/缓解（成本：演示纪律）**：演示环境一律用一次性数据集；Cancelled 任务的 Trace 中显式标注「取消点之前已生效的副作用清单」（V0.2 数据模型已可承载，一行断言）。

#### 死因 #8「流程疲劳」（次要，监测即可）

轮次膨胀或三角色异步延迟拖垮节奏。既有「内容收敛为准」原则约束，概率低伤害中；预警信号是「连续两轮无实质分歧仍新增轮次」。

### 1.3 死因结构分析（本轮 pre-mortem 的核心发现）

把 8 条死因按防御状态分类：

| 类别 | 死因 | 防御状态 |
|---|---|---|
| 技术类 | #5（假设#4/S3）、#6（A-3 校准）、#7（事故） | **已有预案**（11 号实验设计、判定线第 3 行、取消语义）——防御良好 |
| 证据类 | #3（空心地基） | 部分防御（A6 规范存在），**缺质量判据**——本次补齐（Q1/Q4 自家断言） |
| 组织/社会类 | #1（实施断层）、#2（三问悬置）、#4（采用绕过） | **几乎裸奔**——11 份文档全部在「怎么做对」内部展开，「谁来做、有人用吗」两问无产物 |

**结论**：山海司第一阶段最可能的死因不是任何已识别的技术风险——技术死因已被 11 份文档和判定线体系防御到罕见水平——而是**组织死因**：无人实施、悬置拖延、无人使用。这与第 4 轮「论证地基是 A-1」的发现同构：项目的最大风险始终在纸面之外。

## 第二部分：本轮竞品断言抽查（滚动机制第 3 次）

### 抽查 1：Langfuse prompt 版本与 trace 的关联（11 号 Q1 的最优假设）

**结果：证实存在。** Langfuse 官方明确：prompt 版本经 prompt management 与 trace 关联，支持按 prompt 版本比较质量指标；2026 年教程演示了「编译 prompt → 关联到被追踪的 generation」的完整链路。

**对 11 号的影响**：Q1 计数中「prompt 版本定位」一步按最优假设记为系统内操作——假设成立，该步不增跨系统步。**Q1 的跨系统步数估计因此偏保守（对组合方案不利方向）**：工具版本（Q1 步③）仍无任何证据可记入 trace，两步跨系统成本（工具仓库人工对齐 + 人工补记）维持。Q1 可能落在 2–3 步而非 4 步。**判定主判据不受影响**：A-3 的成立线由「不可回答 3/5」独立触发，Q1/Q3 步数只影响边缘。
**处置要求**：11 号在定稿引用时更新 Q1 计数口径并注明本次抽查；判定结论（A-3 成立）不变。

### 抽查 2：D2/D4「无可替代」判定 vs 2026 治理平台品类（回应决策官指定重点）

**结果：D2 需再次收窄，D4 维持。**

2026 年「AI Agent 治理」已是**商业化平台品类**：多家产品提供运行时策略强制、审计痕迹、行为记录生成审计证据（对齐 GDPR/HIPAA 等合规框架）、策略版本控制、Agent 清单与审查历史作为审计方证据；CSA 已发布含「工具与能力管理」维度的治理成熟度模型。

- **对 D2（证据认知）**：「运行证据 → 审计证据」这一层**已被商业平台覆盖**。D2 的「无可替代」必须收窄到「**能力结论制品**」：能力画像（能力 Y → 任务样本 × 通过率 × 版本切片的证据链）作为可查询、可保鲜（随版本更新自动失效/重算）的一等实体——抽查未发现任何产品做到这一层。弱替代矩阵 D2 行修正为：「审计证据层有强替代（商业治理平台）；能力结论制品层无可替代」。
- **对 D4（受控演进）**：未发现对应物——「失败样本 → 改进候选制品 → 实验记录 → 准入状态」的流程制品模型在治理平台（做合规）与观测平台（做数据）两侧都不存在。**判定维持：无可替代。**
- **连带修正**：08 号第五类对照「治理/规格层尝试」需更新为「已商业化的 Agent 治理平台」，差异化叙事从「无人做治理」校准为「**治理平台做合规证据，山海司做能力认知与演进闭环**」——两者在「审计」上有重叠，在「认知与演进」上正交。

### 抽查小结

三次抽查累计触发两次收窄（第 4 轮 D1/D3、本轮 D2），一次证实（本轮 prompt 关联）——滚动机制在真实起作用，且每次收窄后论证都变得更精确而非更弱。建议维持机制至定稿。

## 第三部分：对 11 号文档三个自请挑战点的回应

1. **「不可回答」判定是否过严**：不过严。11 号 Q2 的步④「人工固化成文档」本身就是无系统承载的承认——「能人工拼出一次性答案」与「系统能持续回答」的差别正是「制品 vs 惯例」的差别，也是山海司「平台而非文档」（08 §5.2 咬合）的立论点。**维持判定**，但建议在定稿中把「不可回答」重命名为「无制品承载」（更精确，避免「永远答不出」的字面误读）。
2. **山海司「0 跨系统步」是目标态被当现状呈现**：指控成立。V0.2 尚未实现，计数表「对照」列须标注【目标态，非现状】。更重要的修正是把该目标态**变成验收义务**——即本报告 S3（C2 增加 Q1/Q4 单系统可回答断言）：宣称 0 步，就要在验收里证明 0 步。这同时是死因 #3 的直接防御。
3. **S1–S3 复杂度梯度是否自然**：纸面无法判定，但实验设计已把字段数/嵌套深度/枚举数设为解释变量，可事后检验。补一条防定制要求：**任务集与 3 份 Spec 在实验启动前固化归档（Git commit 哈希），启动后不得修改**——防「按通过率反推任务难度」的嫌疑。

## 第四部分：提请第 5 轮裁定事项

1. **S1**：裁定「定稿 = 设计文档 + 最小实施章程」，无章程不定稿（防死因 #1）；

4. **弱替代矩阵 D2 行收窄 + 第五类更新为商业化治理平台**（本轮抽查结果，需回写 08 号对应表格后随定稿固化）；
