## 2. 新发现与处置建议

### ND-1（P2）低代码平台行「版本工程薄弱」部分证伪

Dify 2026 年已有应用/工作流级正式版本控制与恢复回滚（官方文档工作流：Draft → Publish → Restore；社区实测评价正面）。08 号该行「版本工程薄弱」须收窄为：**「版本工程限于应用/工作流级发布与回滚；无跨要素（Prompt/工具/知识/Spec）版本关联图谱，无受控演进（候选→实验→准入）语义」**。收窄后该行差异主张仍然成立（D5/D4 层面），但「薄弱」一词以 2024 年认知描述 2026 年现实，定稿前必须改。
**处置**：设计师回写 08 §4.1 低代码行（文字级修订，不动结构）。

### ND-2（P2）Provider 结构化输出 Schema 子集差异——实验设计须增补处置

这是本轮全量复核最重要的发现。11 号实验设计假设「策略 A（原生 structured output）+ L2 本地 Schema 校验」语义一致——**已证实不成立**：

- OpenAI strict mode 拒绝含不支持关键字的 Schema（子集约束），模型输出保证符合该子集；
- Anthropic 对 Schema 做严格校验、遇不支持元素报错；
- 两家子集**互不相同且均非 JSON Schema 全集**。

后果：Provider 侧合规 ≠ 本地校验通过。若实验 Schema 使用了任一家不支持的关键字，策略 A 会直接报错（schema 被拒）；若 Schema 限定在子集内，本地 L2 校验的关键字覆盖面会窄于设计预期——**「契约」的定义在两个 Provider 之间不可移植**。

**处置（实验执行前必改，三条）**：
1. A2 输出契约 Schema 规定使用**两家支持子集的交集**（至少：避免 `patternProperties`/`if-then-else`/`not`/`unevaluated*`/非常用 `format`），并将此约束写入 Spec 设计规则；
2. 实验失败分类增补子类 `provider_rejected_schema`（Schema 被 Provider 拒绝，非模型输出问题，不得混入契约失败率，类比 infra_failure 处理）；
3. 指标 4 的失败分布中，「provider 通过但本地校验失败」样本单独计数——该子类是「语义不一致」的直接度量，也是假设 #4 实验的副产品产出。

### ND-3（P3）Anthropic 平台已提供 prompt 版本 + 评估 + 回滚

核查中发现的边缘信号：Claude 平台已提供 prompt 版本管理、基于标注测试集的评估与经 pinned session 的回滚。这不推翻 D3（范围仅 prompt 级，非 Agent 全要素版本-准入-回滚闭环），但说明**平台级版本-评估-回滚正在被上游逐要素补齐**——A-4 窗口收窄的又一实证。
**处置**：定稿风险节 A-4 条目追加此信号；D3/D5 正文各加一句「上游已推进至 prompt 单要素」的注记。

### ND-4（口径微调）Langfuse 工具版本：无原生字段，metadata 可注入

11 号 Q1 步③「工具版本不在任何 trace 字段中」微调为：**「无原生工具版本字段；可经 metadata 手工注入，但注入属使用方约定纪律，无强制与一致性保证——是弱关联的又一形态而非制品」**。Q1 计数维持 2–3 步（metadata 注入纪律本身即 11 号 §1.2 定义的「人工约定成本」），判定不变。
**处置**：11 号 Q1 依据栏一句话修订。
