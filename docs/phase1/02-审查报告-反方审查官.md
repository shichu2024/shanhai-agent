## 1. 审查总览

**整体评价：方案骨架成立，方向正确，但当前版本不可直接进入实施。**

本方案最强的部分是三条设计底线（Spec 强制执行、Trace 第一天落盘、版本不可变）和反向验收设计（C3）——它们分别守住「规格驱动」的成立性、第二阶段的输入来源、以及「只验 happy path」这一最常见的验收造假路径。基线残缺的事实核查我做了独立复核，13 处声称全部属实，且我还发现了 6 处方案未列入的遗漏（见 P3-1）——这反而强化了 WP-A 的必要性，而不是削弱它。

**最可能的失败环节（先说结论）：**

1. **范围裁决悬空**：方案把 MVP 清单 15 项中的 5 项移出第一阶段，但这是修改用户明示的「必须实现」清单，不是补齐缺失定义。裁决未落地前，WP-B/WP-C 的验收标准无法冻结，后续一切工作都建立在待定前提上。
2. **Task 状态机草案存在内部矛盾**（终态不变式 vs Retrying 迁移），作为 A3 交付物的种子定义不能带病通过。
3. **假设 #4（LLM 输出契约可约束）承载了全部验收，却没有量化验收设计**——如果 C2 跑不通，按当前方案连「差多少、往哪修」都无法回答。

方案自身质量明显高于一般初稿：假设显式标注、取舍说明、削减顺序、自陈挑战点一应俱全。本报告的挑战集中在上述三点及若干落地缺口，不构成对总体架构的否定。

## 2. 分级问题清单

### P0-1 范围裁决未决即作为方案结构前提（阻塞验收标准冻结）

- **问题**：§2.1 将「第一阶段」定义为 Phase 0+1，并把 Memory、Evaluation、Capability Profile、人工审批、发布回滚 5 项移出第一阶段（基线 §22.1 共 15 项「必须实现」，移出占 1/3）。
- **原因**：基线 §22.1 是用户明示的「必须实现」清单。三角色对**缺失内容的补齐**有授权（填空），对**明示需求的裁剪**没有授权（改需求）。方案假设 #1 把两者混为一谈。
- **影响**：若用户实际预期是 §22.1 全集，第一阶段验收时被判「不完整」，WP-A 产出的一半定义要重排，WP-C 验收脚本重写。这是全方案最大的单点返工风险。
- **修复建议**：
  1. WP-A 启动前取得用户对范围的**显式确认**（一行文字即可：「第一阶段 = Phase 0+1 子集，MVP 差额项延后」），归档进本目录；
  2. 「用户裁决」这个动作目前没有 owner 和时限（见特别要求 Q3），方案修订时应指定：由决策官在终审时向用户提出、且为发布定稿的前置条件；
  3. 同时给出裁决的降级预案：若用户坚持全集，哪几项可以极小成本并入（如「基础 Evaluation」可降为 C2 中的通过率统计本身；Capability Profile 可降为基于 Trace 的只读能力快照）。

### P1-1 Task 状态机草案内部矛盾与迁移缺失

- **问题**（§5.1 草案，四个具体缺陷）：
  1. **不变式自相矛盾**：声明「任何终态（Succeeded/**Failed**/**Timeout**/Cancelled）不允许再迁移」，但同一张图存在 `Failed/Timeout → Retrying → Running`。要么 Failed/Timeout 不是终态，要么重试不存在，二者只能其一。
  2. **Retrying 缺失败出口**：`Retrying → Running` 之后再失败去哪里？回到 Retrying 还是进 Failed？重试上限计数器（retryCount）存哪里、由谁判定达上限，状态机无法自洽表达。
  3. **Created → Failed 未画**：§5.2 步骤 3 说 Spec 校验失败「Task 直接 Failed」，但流程图中从 Created 出发只有 → Queued。
  4. **Timeout 未分层**：任务级超时与调用级超时（§5.3 模型超时）是两个概念，都映射到同一个 Timeout 状态会导致失败归因混淆（A4 失败分类需要区分它们）。
- **影响**：A3 是 WP-A 核心交付物，也是 TaskManager 的实现依据；带矛盾的种子定义会直接传导为实现 bug 或验收歧义。
- **修复建议**：改用 **attempt 模型**消解矛盾——重试是 `Running` 状态内部的新 attempt（attemptCount 计入 TaskRecord），不离开 Running；attempt 耗尽才迁移到 Failed。这样 Failed/Timeout/Cancelled 保持真终态，不变式成立，且 Retrying 这个状态可以整个删掉（见 §5 不必要复杂度）。同时补 `Created → Failed` 迁移、为每条迁移标注触发事件与持久化点。

### P1-2 「拦截代替审批」的真实重构成本被误判

- **问题**：方案 §9.4-3 询问「是否隐藏将来补审批流时控制流重构的成本」——答案是**是，但成本位置判断错了**。真正的重构成本不在拦截逻辑（拦截 → 放行/审批的切换是策略查表，便宜），而在于：**当前状态机没有任何「暂停等待外部输入」的状态**，Runtime 与 CLI 也没有任何人工介入通道。
- **原因**：第二阶段补审批流需要同时动三处：状态机新增 Paused/AwaitingApproval 态及迁移、Runtime 增加挂起点与恢复点、CLI 增加审批交互。三处中前两处若第一阶段完全不留位，就是结构性重构。
- **影响**：第一阶段省下的设计量，第二阶段以「Runtime 主循环加挂起语义」的形式偿还，且挂起语义会影响并发任务的调度设计——属于越晚引入越贵的改动。
- **修复建议**（成本极低）：A3 状态机中**预留 Paused 状态与迁移（Running → Paused → Running/Cancelled），实现可以是空壳**（迁移定义存在、第一阶段无触发器）；审批接口位用一条 ApprovalRequest 数据结构记录表达即可。这不增加第一阶段实现量，只增加几行 schema。

### P1-3 L3+ 拦截缺少对模型的反馈协议（预算内空转风险）

- **问题**：§5.3 说 L3/L4 拦截后「任务继续或按 Spec 声明失败」。「任务继续」意味着 Runtime 要把「工具被拒」作为某种结果反馈给模型——反馈消息格式未定义；更严重的是，模型完全可能反复请求同一被拒工具，在预算耗尽前空转。
- **影响**：端到端演示脆弱（被拒 → 模型死缠 → 超预算 → 任务以 BudgetExceeded 而非 PolicyBlocked 失败，失败归因失真，直接污染 A4 失败分类的数据质量）。
- **修复建议**：定义拦截反馈消息格式（结构化的 policy_denied 结果，含原因码）；定义**最大连续拦截次数**（如 2 次，超过即 Failed: Policy 类，主因记 PolicyBlocked）；该路径纳入 C3 反向验收。

### P1-4 假设 #4（LLM 契约可约束性）没有量化验收设计

- **问题**：C2 验收只说「断言输出契约通过」，未定义运行次数与通过率阈值。方案自己把假设 #4 标注为「待验证（C2 中量化）」，但 C2 实际上没有量化设计。
- **影响**：LLM 输出非确定性下，跑 1 次通过 ≠ 假设成立，跑 3 次挂 1 次 ≠ 假设破产。验收标准不可判定 → 假设 #4 永远停留在「待验证」，第二阶段（白泽/白虎依赖输出质量）的输入质量无据可依。
- **修复建议**：C2 明确：同一任务运行 N≥10 次，报告契约通过率；给出决策阈值（示例：≥80% 视为假设成立；<80% 触发结构化输出/修复重试策略加码，且这是一个**显式的第二阶段决策点**而非隐式兜底）。阈值数值可由决策官裁，但样本量和阈值本身必须存在。

### P2-1 版本不可变与「文件系统 + Git」的落地机制未指定

- **问题**：Spec 走文件系统 + Git，AgentVersion 是不可变记录——注册时是**把 Spec 快照复制入库**，还是**引用文件路径/Git commit**？未指定。
- **影响**：若为引用：注册后用户在 Git 中修改同版本文件，Runtime 读到的是新内容，「不可变」名存实亡，版本固定原则（§3.2-1）被击穿。
- **修复建议**：注册时将 Spec 全文快照写入 SQLite 不可变记录；Git 仅承载审计历史与 diff 能力；文件改动必须走重新注册生成新版本。一句话写进 A1。

### P2-2 预算模型未定义，C3 超预算用例不可构造

- **问题**：预算的计量单位（token / 货币 / 调用次数）、作用域（单任务 / Agent 累计）、计量来源（provider 返回 usage 还是本地估算）均未定义。C3 要求「超预算必须被截停」，但测试没有确定性的预算注入手段。
- **影响**：要么反向验收测不了，要么测了但不具备确定性（依赖真实 LLM 消耗波动）。
- **修复建议**：A2 的 Model Policy 中明确预算字段结构（建议：`maxModelCalls` + `maxTokens`，任务级作用域，usage 以 provider 返回为准、缺失时本地估算并标注）；C3 用极小预算（如 maxModelCalls=1 + 第二次调用的用例）构造确定性截停。

### P2-3 Trace JSONL 的并发写未定义

- **问题**：§5.4 允许同一 Agent 并发多任务，但未定义 JSONL 是全局单文件还是 per-task 文件。全局单文件并发追加会交错损坏行。
- **修复建议**：per-task 一个 JSONL 文件（天然支持按任务归档与并行写）；若坚持全局文件则需写序列化。写入时机（每次状态迁移即持久化）也应一并写明。

### P2-4 被拒绝请求的留痕缺失

- **问题**：§5.4「输入不符合 Input Contract：创建阶段即拒绝」——是被静默丢弃，还是留下记录？方案未定义。
- **影响**：从安全审计角度，被拒请求（谁在何时用什么输入探测了系统）恰恰是最该留痕的事件；静默丢弃会让第一阶段的安全叙事出现空洞，且基线玄武原则要求全链路可追踪。
- **修复建议**：定义 RejectedRequest 审计记录（不创建 Task、不进队列，但写 Trace/审计流）。

### P2-5 Running 态取消的中断传播语义未定义

- **问题**：`Running → Cancelled` 存在，但取消一个正在执行的 LLM 调用/工具调用，第一阶段是尽力中止（AbortController）还是等当前原子调用完成？未定义。
- **影响**：不定义会出现「任务已 Cancelled 但 L2 工具副作用已发生」的状态错位。
- **修复建议**：明确第一阶段语义 = **等待当前原子调用完成后取消**（简单、诚实、与无 Checkpoint 的定位一致），写入 A3 迁移表注记；立即中止留给第二阶段。

### P2-6 「SQL 方言保持 PG 兼容」是伪承诺

- **问题**：SQLite 与 PostgreSQL 在类型系统（JSONB vs TEXT、数组、部分索引、SERIAL）上差异是结构性的，「方言兼容」实践上做不到。
- **修复建议**：把兼容承诺改到正确层次：**数据模型（ERD）与 ORM 查询层保持可迁移**，不承诺 DDL 级兼容。这样承诺可兑现，也不影响选型结论。

## 4. 成立部分（明确认可，不要求改动）

1. **基线残缺是事实而非判断**：独立复核 13 处全部属实。「第一阶段必须内置设计重建」的结论成立，且因清单外还有遗漏（P3-1）而更加成立。
2. **Phase 0+1 合并、让设计被代码验证**：成立。分开执行反而会产生「纸上架构」漂移。
3. **技术选型（TS / 模块化单体 / SQLite / 文件+Git / JSONL）**：**成立，我没有 Go/PG/服务化的推翻理由**。第一阶段无多用户、无生产部署、无高并发压力，Go 的优势用不上；TS 的 Schema 工具链（zod/JSON Schema）直接服务 SpecValidator；SQLite 单文件可随仓库归档与「归档到 GitHub」的要求意外契合。挑战应落在落地细节（P2-1/P2-6），不在选型本身。
4. **「Spec 必须被 Runtime 强制执行」与「Trace 从第一个任务落盘」两条设计底线**：成立，且是本方案最有价值的部分——它们分别守住「规格驱动」的成立性与第二阶段的全部输入。
5. **C3 反向验收（越权被拒、超预算被截停）**：成立。多数同类方案只验 happy path，此项显著提升验收可信度。
6. **削减顺序与不可削减底线（§9.5）**：成立。底线四项（SpecValidator、Policy 强制检查、Trace 落盘、版本不可变）选得准。
7. **崩溃恢复最小版**（接受任务丢失、重启标记 Failed）：成立，与无 Checkpoint 的整体定位自洽。

## 5. 特别要求回答

**Q1：这个方案最可能在哪个环节失败？**
C2 端到端验收遇真实 LLM 输出不稳定（方案自排第一，我同意），但要补一刀：其根因是 P1-4——当前验收设计无样本量与阈值，失败发生时连「差多少、往哪修」都无从回答，届时会退化为主观争论而非工程决策。第二顺位是 P0-1：范围裁决若在开发中途才被推翻，返工面最大。

**Q2：哪个假设一旦不成立，整个方案受最大影响？**
假设 #2/#10（范围解读）。假设 #4 不成立只影响验收刻度和第二阶段输入质量（结构不动）；范围假设不成立则工作包划分、验收脚本、甚至「第一阶段」这个词的含义全部重排。它是唯一能「推翻结构」而非「调整参数」的假设。

**Q3：哪个模块或步骤实际上没有明确责任人？**
两个：(1) WP-A 交付物的**完整性判定**——A1–A6 谁签字算补齐？建议三角色各出一票、决策官终审，写进修订版；(2) **「向用户提请范围裁决」这个动作**——方案说需要裁决，但没有说谁在什么时限内以什么形式提出。无 owner 的裁决请求 = 永远悬空的裁决。

**Q4：哪个设计只是理论上可行，现实中难以落地？**
两处「将来不痛」的承诺：「SQL 方言保持 PG 兼容」（P2-6，结构性差异决定它是伪承诺）和「字段命名对齐 OTel 语义、第二阶段平滑接入」（命名对齐能降低成本但不消除成本——OTel 接入真正的工作量在 Span 上下文传播与 Collector 部署，命名只是零头）。修订版应把这两项从「承诺」降级为「降低迁移成本的措施」，避免它们成为范围决策的依据。

**Q5：哪些内容属于不必要的复杂度？**
三处：(1) **Retrying 状态**——attempt 模型可将其消解（见 P1-1 修复），少一个状态少一类迁移歧义；(2) **A5 版本状态机的 Reviewed 环**——第一阶段无人工流程，没有人有权限把 Draft 变成 Reviewed，这个状态无触发者；建议第一阶段简化为 Draft → Released（+ Deprecated），Reviewed 随审批流在第二阶段进入；(3) **A2 中的 Evolution Policy「仅边界声明」**——非目标的东西不需要在 Spec v1 占字段，数据模型层预留外键已足够。

**Q6：如果只能保留一半功能，应该保留什么？**
保留（按序）：SpecValidator + Policy 强制执行 → TraceRecorder + FailureRecorder → TaskManager 最小状态机（6 状态 + attempt 计数足够）→ C1 + C3 验收（含 P1-3 的拦截反馈路径）。可砍：A5 完整版本状态机、A6 事件层级丰富度（保留枚举砍层级）、C2 多场景（保留单场景 + 通过率统计）、StateManager 崩溃标记。判断标准：**「第二阶段的输入」（证据类）与「规格驱动的成立性」（强制执行类）优先于一切便利性与完整性。**

**Q7：如何证明修订后的方案确实比当前方案更好？**
三个可检查的标志：(a) 修订版逐条映射本报告问题编号并给出处置（接受/部分接受/拒绝 + 理由），无未回应的 P0/P1；(b) 状态机迁移表无矛盾，且每条迁移标注了触发事件、持久化点与 A4 失败分类映射；(c) 用户对范围（P0-1）的显式确认以文字形式归档在本目录。三者全部可机械核对——这本身就是「更好」的可证明定义。

## 6. 给方案设计师修订的优先级建议

1. **先解 P0-1**：向决策官/用户提请范围裁决（指定 owner 与形式），裁决结果归档；
2. **再解 P1-1 / P1-4**：状态机改 attempt 模型 + C2 加样本量与阈值——这两项直接决定 A3 交付物与验收脚本的可写性；
3. **P1-2 / P1-3 低成本高回报**：Paused 空壳状态 + 拦截反馈协议，各只需几行 schema 级改动；
4. P2 系列随修订顺手补齐（多为一段文字或一条 schema 的事）；
5. P3 系列可在修订版或定稿中处理。
