## 3. V0.2 修订内容（替代 `01-初始方案` 对应章节）

### 3.1 替代 §2.1 末段：范围裁决前置条件与降级预案【新增】

**裁决请求**：由综合决策官于终审时向用户提出，形式为一行确认文字（例：「第一阶段 = Phase 0+1 子集，MVP §22.1 差额项延后至第二阶段」），归档至 `docs/phase1/`。该确认为**定稿发布与 WP-B/WP-C 验收标准冻结的前置条件**。A0（基线残缺扫描）为唯一豁免项，可立即启动（范围无关）。

**降级预案（若用户坚持 §22.1 全集，按并入成本排序）**：

| MVP 差额项 | 极小成本并入方式 |
|---|---|
| 基础 Evaluation | 降为 C2 通过率统计 + FailureRecorder 聚合报表 |
| Capability Profile | 降为基于 Trace/FailureRecord 的只读能力快照（无独立 Registry） |
| 基础 Memory | 降为仅工作记忆（任务内上下文），不做持久化记忆与可信度状态机 |
| 发布与回滚 | 版本指针回滚 CLI（本就已并入，见 §3.7） |
| 人工审批 | **不可极小成本并入**：需 Paused 状态完整实现 + 挂起/恢复语义 + CLI 交互三处结构改动；若用户坚持，需接受第一阶段工期显著延长，须向用户明示此取舍 |

### 3.2 替代 §5.1：Task 状态机 V0.2（attempt 模型 + Paused 预留）

状态集：`Created / Queued / Running / Paused(预留空壳) / Succeeded / Failed / Cancelled`。
Timeout 不再是独立状态（任务级与调用级超时均收敛为 Failed 的 failureClass，消除归因混淆）。Retrying 状态删除。

| 迁移 | 触发事件 | 持久化点 | A4 失败分类映射 |
|---|---|---|---|
| Created → Queued | Spec 与 Input Contract 校验通过，入队 | TaskRecord.status + Trace(TaskQueued)，先写后行 | — |
| Created → Failed | Spec 校验失败 / 输入不符合 Input Contract（同时写 RejectedRequest 审计，见 §3.9 的边界：结构化拒绝走审计流，已建 Task 的走本迁移） | TaskRecord + FailureRecord + Trace | Input / Spec |
| Queued → Running | 调度器取出执行 | TaskRecord + Trace(TaskStarted) | — |
| Queued → Cancelled | 用户取消（等待中，无副作用） | TaskRecord + Trace | — |
| Running → Running（新 attempt） | 调用级失败/超时且 attemptCount < maxAttempts | attemptCount 更新 + Trace(AttemptFailed) | Model / Tool（attempt 级记录，不计入任务失败） |
| Running → Paused | 预留（第一阶段无触发器；第二阶段审批挂起点） | — | — |
| Paused → Running / Cancelled | 预留 | — | — |
| Running → Succeeded | 输出契约校验通过 | TaskRecord + Trace(TaskSucceeded) | — |
| Running → Failed | attempt 耗尽 / 任务级超时 / 预算超限(BudgetExceeded) / 连续拦截超限(PolicyBlocked) / 输出契约失败(ContractViolation) | TaskRecord + FailureRecord + Trace(TaskFailed) | Model / Tool / Runtime / Policy / Output |
| Running → Cancelled | 用户取消：**等待当前原子调用完成后生效**（§3.9） | TaskRecord + Trace(TaskCancelled) | — |
| （恢复路径）Queued/Running 遗留 → Failed | 进程重启发现非终态遗留任务 | TaskRecord + FailureRecord | Runtime(CrashRecovery) |

不变式：Succeeded / Failed / Cancelled 为真终态，无出边；每条迁移**先持久化后继续**；状态迁移即 Trace 事件。ApprovalRequest 数据结构预留（字段：requestId、taskId、toolId、riskLevel、requestedAt、decision、decidedAt），第一阶段只定义不写入。

### 3.3 替代 §4.1 技术选型表中两行（P2-1 / P2-6 / OTel 降级）

| 决策点 | 建议 | 理由（修订后） |
|---|---|---|
| 结构化存储 | SQLite；**AgentVersion 注册时将 Spec 全文快照写入不可变记录，Git 仅承载审计历史与 diff；文件改动必须重新注册** | 击穿不可变性的引用方案被否决 |
| 迁移承诺 | **数据模型（ERD）与 ORM 查询层保持可迁移**，不承诺 DDL 级方言兼容 | 原「SQL 方言 PG 兼容」为伪承诺，降级 |
| Trace 存储 | per-task JSONL 文件；**OTel 字段命名对齐是降低迁移成本的措施，不构成「平滑接入」承诺**（真正成本在 Span 上下文传播与 Collector 部署） | 同上降级 |

### 3.4 Spec Schema v1 增补与删减（P2-2 / P1-3 / R-3 / Q5-3）

Model Policy 新增字段：`maxModelCalls`（任务级）、`maxTokens`（任务级）、`maxAttempts`（调用级重试上限）；usage 以 provider 返回为准，缺失时本地估算并标注 `estimated: true`。

Tool Policy 明确：风险闸门 L0–L2 放行（L1/L2 审计）、L3/L4 拦截；`maxConsecutiveDenials`（默认 2，可覆盖）；**L2 工具必须声明受控字段**（参数范围/目标白名单）。

删减：Evolution Policy 从 Spec v1 删除（非目标不占字段；数据模型外键预留足够）。

### 3.5 拦截反馈协议（P1-3，新增小节）

拦截时返回给模型的结构化结果：`{ result: "policy_denied", toolId, reasonCode, message }`。连续拦截计数达 `maxConsecutiveDenials` → Running → Failed，failureClass = Policy(PolicyBlocked)，**归因不漂移**（不得记为 BudgetExceeded）。

### 3.6 替代 WP-C：验收 V0.2（P1-4 / P2-2）

- C2：同一任务运行 **N≥10 次**，报告契约通过率；**阈值 ≥80%（示例值，终审由决策官裁定）**；<阈值 → 触发显式第二阶段决策点（结构化输出 / 修复重试加码），非隐式兜底。
- C3（3 条反向验收）：① 越权 Spec（声明未注册工具）注册即拒；② `maxModelCalls=1` + 触发第二次调用 → 确定性截停，Failed:Runtime(BudgetExceeded)；③ 连续请求被拒工具 ≥2 次 → Failed:Policy(PolicyBlocked)，失败归因不漂移。

### 3.7 版本状态机简化 + 回滚 CLI（Q5-2 / R-1）

A5 状态机：`Draft → Released → Deprecated`（Reviewed 随第二阶段审批流引入）。提供 `shanhai agent rollback <agentId> <versionId>` 指针回滚 CLI（A5 唯一可演示部分）。§2.1「发布回滚延后」表述修正为「发布流程与灰度延后；版本指针回滚在第一阶段范围内」。

### 3.8 WP-A 增补（P3-1 / P3-2 / P3-3）

- **新增 A0（唯一可立即启动项）**：对基线文档做全文残缺扫描（机械搜索 `chatgpt-content-reference` 占位标记），产出完整残缺清单（含审查官新发现的 6 处：§2.1 链路图、§9.5 Evidence、§10.6 EvolutionCandidate、§12.2 AgentCard、§17 端到端闭环、§24 产品结构）；修正 §13.2→§13.1 笔误。
- **DoD（每 A 项）**：字段表完整 + 可直接映射为 WP-B 对应模块实现输入 + 三角色评审通过（各一票，决策官终审签字）。
- **两层校验职责**：注册时校验 = 准入（引用完整性）；任务时校验 = 防御性重复（防版本指针移动、外部篡改、库内工具注销导致的悬空引用）。

### 3.9 其他补齐（P2-4 / P2-5 / R-2）

- **RejectedRequest 审计记录**：创建阶段被拒的请求（输入不合契约等）不创建 Task、不进队列，但写审计流（谁、何时、何种输入、拒因）——安全审计上被拒请求恰是最该留痕的事件。
- **取消语义**：等待当前原子调用完成后取消，避免「已 Cancelled 但 L2 副作用已发生」的状态错位；立即中止留给第二阶段。
- **已知接受项（显式声明）**：第一阶段 Trace 中模型输入/输出可能含敏感数据，脱敏策略第二阶段引入；在此声明前不以「Trace 已脱敏」作任何安全叙事。
