# 第一部分：粘合层量化验证（跨系统操作步数法）

## 1.1 目的与判定线

**验证对象**：A-3 假设——「组合方案（LangGraph + Langfuse + promptfoo + 自研 Guard）的粘合层成本随规模增长成为主要成本」（第 4 轮降级为【待量化验证】）。

**判定线（先声明，防止事后挪门柱）**：

| 结果 | 判定 |
|---|---|
| 组合方案在代表查询上的跨系统人工步数中位数 ≥ 5，或 ≥2/5 查询「无制品承载」 | A-3 成立：粘合层成本是结构性缺口，非配置问题 |
| 步数中位数 3–4 且全部有制品承载 | A-3 部分成立：成本真实但可管理，「自研优于组合」论证重心完全落在 D2/D4 |
| 步数中位数 ≤ 2 且全部有制品承载 | A-3 不成立：应承认组合方案对 D1/D3/D5 场景够用，收窄山海司主张 |

> **术语与口径（第 5 轮裁定落地）**：①原「不可回答」统一定稿命名为「**无制品承载**」——查询目标数据在任何组件中都不存在承载制品，非步数问题；②Q1 计数经反方滚动抽查（第一次）校准为 **2–3 步**（Langfuse prompt-trace 关联经抽查证实存在），判定结论不变（见 §1.5）。

**诚实声明**：本部分是**设计期纸面量化**（各组件按其文档化能力计数，标注【待验证】），非实测。方法同时是**基准测试协议**：WP-B 最小 Runtime 就绪后，任何人可用同一协议实测组合方案，校准本表的步数估计。

## 1.2 度量定义

- **跨系统人工步（计 1 步）**：为完成查询，需要①切换系统/工具（IDE、三方平台控制台、CI、数据库客户端），或②人工搬运数据（复制 ID、手工对齐时间戳、人工导出再导入）。
- **系统内自动步（计 0 步，仅记录）**：同一系统内的一次查询/一次点击。理由：自动步可被脚本化，跨系统人工步才是粘合层的本体成本。
- **无制品承载**（原「不可回答」，12 号裁定统一重命名）：查询目标数据在任何组件中都不存在承载制品（如组件不记录该字段、无流程制品模型），无论多少步都无法得到可持续保鲜的答案。无制品承载是比高步数更硬的缺口。
- **前提设定**：组合方案按第 4 轮审查官给出的最优弱配置计数——trace_id 贯穿 + promptfoo CI + Langfuse prompt 版本标签【待验证：Langfuse prompt 标签能否关联到 trace span，当前按能关联的最有利假设计数】。审查官的 steelman 原则在此延续：**给对手最优惠的计数**。

| # | 查询 | 对应主张/断层 | 为什么有代表性 |
|---|---|---|---|

| Q2 | 「Agent X 现在具备能力 Y 吗？」——用运行证据回答，并给出证据链（哪几次任务、通过率多少） | D2 / 认知断层 | 弱替代矩阵判「无可替代」，需展示缺口形态 |
| Q3 | Agent 版本 v1.2 → v1.3 之间 Prompt/工具/Spec 各改了什么？谁批准的发布？如何一键回滚？ | D3+D5 / 演进断层 | 发布准入与回滚的日常操作 |

## 1.4 组合方案计数表（纸面估算，逐步给出依据）

| 查询 | 计数 | 步骤分解（跨系统人工步加粗） | 依据与【待验证】 |
|---|---|---|---|
| Q1 | **2–3 步（第 5 轮反方抽查校准；原纸面计数 4 步）** | ①Langfuse 打开该 trace→ ②经 prompt 管理关联到 prompt 版本【抽查证实 prompt-trace 关联存在，原第 ②④ 步的人工搬运部分可省】→ ③工具版本仍需切换到工具仓库/注册表，人工按 trace 中的工具名 + commit 时间对齐 | 步 ③ 的时间戳对齐是审查官所述「弱关联」的典型成本；工具版本不在任何 trace 字段中【待验证：Langfuse 是否记录工具版本】 |
| Q2 | **无制品承载** | Langfuse 可查 Agent X 的 trace 与评分，但「能力 Y 的证据链」（任务样本 × 通过率 × 版本切片）无承载系统：需 **①人工定义能力口径 ②人工圈定样本集 ③人工导出计算 ④人工固化成文档**，且下次版本更新后口径与结果随即过期 | 这不是步数问题而是缺数据模型：观测平台存 span 不存「能力结论制品」。D2 能力结论制品层的「无可替代」（第 5 轮收窄口径）从纸面判定细化为**结构性无制品承载** |
| Q3 | **5 步** | **①prompt 版本 diff：Langfuse 内或 Git（若用标签管理）**→ **②工具变更：Git/包管理器另行 diff**→ **③Spec 变更：又在第三处（代码库或文档）**→ **④发布批准记录：CI/工单系统，第四处**→ **⑤回滚：无统一版本指针，需人工按 ①–③ 的对齐结果逆操作** | 四类变更分散在四个系统，「版本关联图谱」无人承载；回滚非原子操作 |
| Q4 | **无制品承载（部分）** | 越权尝试的拦截记录取决于自研 Guard 是否落库：若 Guard 只在代码内抛异常 → **拦截事件不入任何持久系统，事后无法举证**；即使 Guard 有日志，**与 trace 对齐需人工按时间戳 + trace_id 粘合**（+2 步），且「全程无越权」的完备性证明无系统承载 | D1 收窄口径（「围绕制品的拦截审计」）的缺口实体化：拦截存在≠拦截可审计 |
| Q5 | **无制品承载** | 失败样本在 Langfuse 可查，但「改进候选」无制品：**①人工聚类 ②人工写候选文档 ③验证记录散落 CI ④准入状态无系统**——候选→实验→准入→发布链路无承载，恰为弱替代矩阵判「无可替代」的原因 | D4 缺口形态与 Q2 同构：缺的不是数据是流程制品模型 |

**计数结果（含第 5 轮抽查校准）**：有制品承载的查询（Q1/Q3）跨系统人工步数 = Q1 2–3 步（抽查校准）、Q3 5 步，中位数 3.75（Q1 取 2.5）；无制品承载查询 3/5（Q2/Q4 部分/Q5）。

**对照（山海司【目标态，非现状】——0 跨系统步是验收义务而非既有事实）**：Q1–Q5 均为单系统单查询（TaskRecord → Trace → SpecVersion/ToolVersion/Prompt 版本同源关联；CapabilityProfile/EvolutionCandidate 为一等实体；RejectedRequest 为审计实体）——每查询 0 跨系统步。**该对照列按 12 号裁定转为验收义务**：Q1 的 0 步主张 = 验收断言 T1（单一查询从 Trace 定位生效 Spec/Prompt/工具版本），Q4 的举证主张 = 验收断言 T2（单一查询返回运行期全部越权尝试与拦截点）——答不出即验收不通过，防「空心地基」。第一阶段只需落地其中 Q1/Q4 的数据模型（Trace + RejectedRequest + 版本快照已冻结于 V0.2），Q2/Q5 的查询实体在第二阶段（白泽/女娲）。

## 1.5 判定与公正性说明

**按 1.1 判定线：A-3 成立**（Q1 经抽查校准后中位数 3.75，已低于第一条判据的 ≥5——**本判定现完全由第二条判据独立支撑：无制品承载 3/5 ≥ 2/5**；距判定线第 3 行的「≤2 步且全部有承载」仍有 Q3=5 步与 3/5 无承载的硬距离）。但必须如实呈现三点局限：

1. **纸面量化，校准已启动**：步数基于组件文档化能力的最优假设计数；滚动抽查已执行两次（Q1 的 prompt-trace 关联被证实并校准、D2 被收窄），【待验证】标注处的其余字段能力仍需按 §3.9 滚动机制或实测继续校准。若后续抽查/实测进一步推翻（尤其 Q3 降到 ≤2 步且 Q2/Q5 出现承载制品），判定线第 3 行生效，A-3 收窄——本判定允许被校准，这正是 S6「可校准快照」口径的含义。
2. **组合方案也在演进**：Langfuse 等平台正在把 prompt 管理做深【推测判断】；本计数是 2026-09 快照，随 A-4 窗口同步贬值。
3. **步数不是全部成本**：组合方案的粘合成本还含「口径过期后重做」（Q2/Q5 的人工结论无保鲜机制），未计入步数——本判定对组合方案偏保守（有利）。

**对差异化论证的影响**：Q2/Q5/Q4 的「结构性无制品承载」为 D2 能力结论制品层与 D4 的「无可替代」、以及 D1 收窄口径提供了实体化证据——缺口不是「要多点几下」，是**没有承载制品**。这与「平台而非文档」论证（§5.2）互相咬合。

# 第二部分：假设 #4 验证实验设计（LLM 输出契约可约束性）

## 2.1 假设与问题定义

- **假设 #4 原文**（01 号文档 §7-4）：LLM Provider 输出可被 JSON Schema 约束到「契约通过率可度量」的程度。
- **已裁定判定线**（05 号文档裁决 1）：N≥10，通过率 ≥80% 为决策线；<80% 触发显式第二阶段决策点；报告须附按 A4 失败分类的失败样本分布。
- **研究问题**：在第一阶段 ModelGateway + SpecValidator 的实际实现下，Agent 输出的契约通过率是多少？失败归因分布如何？结构化输出与重试策略能把通过率提升到多少？
- **统计假设**：H0：首次通过率 < 80%；H1：首次通过率 ≥ 80%。显著性检验不追求（N 小、目的是工程决策线而非科学结论），但须报告置信区间（Wilson 区间，N=30 时 80% 观测率的 95% CI 约65%–90%——诚实呈现小样本的不确定性）。

## 2.2 实验设计

**变量与控制**：

| 变量 | 取值 | 控制 |
|---|---|---|
| Agent/Spec 类型 | 3 类（见材料） | 每类独立统计，禁止只报合计 |
| 结构化输出策略 | A: 原生 structured output / JSON mode（若 Provider 支持）；B: 纯 Prompt 声明 Schema + 解析校验 | A/B 各跑一遍（同一任务集），差值即「策略收益」 |
| 重试预算 | 0（首次）与 ≤2（合计 ≤3 次尝试，对应 maxAttempts=3 裁定） | 首次通过率为主指标，含重试通过率为次指标 |
| 模型与采样 | 单一模型、版本钉死、temperature 按生产值（默认 0） | 模型/版本/参数写入实验记录 |
| Spec 复杂度 | 记录各 Spec 输出契约的字段数/嵌套深度/枚举数，作为解释变量 | 不做刻意梯度，第一阶段 3 类 Spec 即自然梯度 |

**材料**：

1. 3 个示例 Agent Spec（与 WP-C 验收共用同一套，不另造）：
   - S1 低复杂度：结构化摘要（flat，≤5 字段，1 层枚举）；
   - S2 中复杂度：结构化信息提取（10–15 字段，含嵌套对象与格式约束如日期/枚举）；
   - S3 高复杂度：决策报告（含自由文本字段 + 结构化结论字段 + 引用列表的混合契约）。
2. 任务集：每 Spec 10 个任务（合计 N=30，满足 N≥10 的裁定且按类型分层）；任务由 WP-C 用例库导出，预先固化输入与评判要点。
3. **制品冻结（12 号裁定采纳）**：3 份 Spec 与任务集在实验启动前提交 Git 并固化哈希，commit 哈希记录于实验报告首部；**启动后不得修改**——防止为通过率定制任务或契约，任何修订须开新实验轮次并重新冻结。

**程序（每任务）**：Spec 注册（含输出契约 Schema）→ 提交任务 → ModelGateway 调用（按策略 A/B）→ 两层校验：L1 JSON 可解析、L2 Schema 校验（含枚举/格式）→ 不通过则按重试策略重试 → 每次尝试独立落 Trace（attempt 粒度）。

**指标**：

1. 首次通过率（主指标，按 Spec 分层）；
2. 含重试通过率（次指标）；
3. 平均尝试次数 / 任务（成本代理）；
4. 失败分布：按 A4 失败分类映射（预期类别：schema_violation / enum_violation / format_violation / unparseable_output / truncation），给出「差多少、往哪修」的机械答案（裁决 1 附加要求）。

**数据记录**：每尝试一条 JSONL——`taskId, specId, specVersion, modelId, strategy(A/B), attemptNo, verdict(L1/L2), failureClass, latencyMs`。落 TraceRecorder 标准通道，即「实验数据 = Trace 数据」——实验本身就是 D2（证据认知）的第一次实跑。

## 2.3 判定与分支动作

| 结果 | 动作 |
|---|---|
| 首次或含重试通过率 ≥80%（3 类 Spec 均达标） | 假设 #4 成立，C2 验收脚本冻结执行 |
| 整体 ≥80% 但 S3（高复杂度）<80% | 部分成立：输出契约分层——高复杂度 Spec 强制要求原生 structured output 支持或契约拆分；写入 A2 定稿的 Spec 设计规则 |
| 含重试仍 <80% | 触发显式第二阶段决策点（裁决 1 原文）：候选路径 = 原生结构化输出 API 加码 / 输出契约降复杂度 / Provider 更换；**不静默兜底** |
| 失败分布集中于单一类别（如 truncation 占 >60%） | 定向修复优先于整体降级（按 A4 分类直接定位） |

**时机与 owner**：WP-B（ModelGateway + SpecValidator）就绪后、WP-C 验收执行前；owner = 设计师（执行可委托 WP-B 实施者），报告归档 `docs/phase1/` 并作为 C2 验收的证据输入。

**边界情况预置**：Provider 中途限流/超时（排除出通过率分母、单独计数为 infra_failure，不得与契约失败混算）；Schema 校验器自身 bug（实验前用已通过样本自校验校验器）；任务输入本身导致的无解输出（判例排除，需三人裁决小组一致）。

## 2.4 与既有裁定的咬合

- maxAttempts=3（05 号裁决 2-②）→ 重试预算 ≤2 的设计来源；
- 失败样本分布要求（裁决 1 附加）→ 指标 4 直接落实；
- 「<80% 是决策线不是失败线」→ 2.3 第 3 行的分支动作显式化，无隐式兜底。

# 第三部分：特别要求清单

1. **最容易被忽略的三个问题**：①第一部分的纸面计数给组合方案用了最优假设，实测推翻时须承认而非辩护（判定线已预置第 3 行）；②实验的 N=30 支持工程决策但不支持统计断言，Wilson CI 必须随报告呈现；③Q2/Q5「无制品承载」依赖「组合方案不额外自研」的边界——若用户为组合方案追加自研组件，它就不再是组合方案而是部分山海司，这恰是论证的一部分而非漏洞。
2. **最可能失败的三个场景**：实测发现 Langfuse 已原生记录工具版本（Q1 塌到 ≤2 步）；假设 #4 在 S3 类 Spec 上含重试仍 <80%；实验执行者把 infra_failure 混入契约失败率污染判定。
3. **最依赖的三个假设**：Langfuse trace 不含工具版本【待验证】；第一阶段 3 类 Spec 能代表后续 Spec 复杂度分布【设计假设】；Provider 原生结构化输出与 Schema 校验语义一致（枚举/格式严格性）【待验证】。
4. **最值得反方挑战的三个设计点**：①「无制品承载」的判定是否过严（组合方案可以「人工固化成文档」算弱承载）；②步数法把自动化成本记 0 是否人为压低组合方案劣势口径的反面——即是否反而高估了山海司（山海司的「0 跨系统步」是目标态而非现状）；③S1–S3 的复杂度梯度是否自然而非为通过率定制。
5. **资源减半时削减**：Q5（D4 已无可替代共识，缺口展示可精简）；策略 B（纯 Prompt 声明）可只在 S1 上跑作为锚点；不可削减：Q1/Q2/Q4、首次通过率主指标、A4 失败分布。
6. **规模扩大时的瓶颈**：纸面计数需随每个组件的大版本更新重算（§3.9 机制限定为抽查，扩规模时应升级为专项）；实验任务集需随 Spec 类型增长扩充，N 的下限规则（每类型 ≥10）会导致实验成本线性增长——第二阶段应转为持续回归而非一次性实验。
