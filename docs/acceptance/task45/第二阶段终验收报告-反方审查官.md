## 七、特别要求回答

1. **最可能失败环节**：T3 执行接线的 fail-open 叠加（手动脚本+无 CI+exit 无测试+短路零发现）；其次是 `data/` 域外流破例（§五-A）。
2. **最脆弱假设**：「运行时数据永不入发布物」（单一 gitignore 防线）与「redaction 管道实例永远同一注入」（无同实例断言，未来重构可静默破裂）。
3. **无责任人环节**：DB 原文缝隙——A6 §8 不管辖、无条款认领、无测试断言，是「人人以为对方管」的死角。
4. **理论可行现实难落地**：注入时重扫描兜底——需处理规则集漂移与 dedup 语义，成本高于写入侧收口，不建议。
5. **不必要复杂度**：`RedactionRule.scope` 装饰字段；`config.ts:33` 退化三元；EXCLUDED_SUBCLASSES 常量与 SQL 双份维护。
6. **只保留一半功能保留什么**：写入侧脱敏管道 + digest 原文口径 + report/指针解耦 + 人工确认制（D-14）——这四件是第二阶段的承重墙，其余皆可缓。
7. **如何证明改进**：三条新增机械断言——①含密钥输出→记忆→注入→provider system 无密钥端到端；②终态任务 approve/deny 结构化拒绝；③T3 CLI 级 exit 码（命中=1/干净=0）。红灯现状→修复转绿即为改进证明。
