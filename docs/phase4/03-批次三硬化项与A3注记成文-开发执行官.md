## R-1 嵌套信号封闭分类表（替代单点特判）

终审指出：V0.2 §4.4 的信号上浮仍是单点特判表述，须落为封闭分类表——枚举全部子任务退出态 → 父委托调用归因的映射。成文如下（与 `src/runtime/delegation.ts` 文件头注释逐行一致，实现按此表分派）：

| # | 子任务退出态 | 父委托调用边界处置 | 实现锚点 |
|---|---|---|---|
| 1 | `succeeded` | 返回终态摘要 `{taskId,status,outputDigest,output}`（tool_call_executed，父模型继续） | `Delegation.summarize` |
| 2 | `failed`（含子 Created→Failed：inputContract 不合） | 返回失败摘要（同上）——**失败不自动传播**，父模型自行决策（F-12-③） | 同上 + `failChild` |
| 3 | `cancelled`（子被单独取消 / 审批拒绝 / 超时） | 返回取消摘要——父不受影响，从摘要感知（F-13） | 同上 |
| 4 | `cancelled(superseded)`（因父取消传播） | 重抛取消信号——父随后按 cancel 语义终局（graceful→`user` / abort→`abort`） | `Delegation.execute` 末段 + `TaskManager.executeLoop` catch |
| 5 | `paused`（子级 L3 审批 / 崩溃窗口③合法长驻） | `DelegationWaitSignal` 上浮——父在委托调用边界 Paused（幂等，不创建新父级审批） | `executor.ts` 包装为 `DelegationPauseSignal` → `persistDelegationWait` |
| 6 | `created` / `queued`（乱序容错 / 防御分支） | `DelegationWaitSignal` 上浮——同上（提示「先处置子任务」）。注：崩溃落点「子已落库未起跑 + 父 Running」时父被扫描终局（Failed），父无 resume 路径，子留 Queued 由 stale 警示可见——本行为防御性保留 | `Delegation.execute` 锚点分支 |
| 7 | `running`（**子独立 resume 进程在飞**，父 Paused） | **可达态（崩溃窗口②现场）**：操作者 `task run --resume <child>` 独立进程跑子循环，期间该进程崩溃 → 恢复扫描终局子（CrashRecovery），父保持 Paused；resume 父幂等重入见子终局 → 返回失败摘要，父模型决策。嵌套同进程段内「子在飞而父不在执行」不可达（父崩溃即窗口①双双终局） | 崩溃矩阵②行 + `A-20-⑥ 窗口②` 用例（SQL 合成该可达态验证重入语义） |

系统表述：任何子任务退出态必然落入上表 7 行之一——不存在「子 pause 被父 attempt 循环误归 `Tool(execution_failed)` → 重试 → 复制子任务」的路径：委托原语在 `ToolExecutor` 委托路径中 attempt=1（禁重试），且 `DelegationWaitSignal` / `ApprovalRequiredSignal` / 取消信号均原样上浮、不进 attempt 异常归类（`toolExecutor.ts` 委托原语 catch 特判）。

## R-2 双快照写序（子级审批上浮为父级挂起时）

终审指出：V0.2 未显式写子 PauseSnapshot 与父快照的落库步骤与先后写序。成文如下（先持久化后迁移，A3 不变式②贯穿）：

```text
子级 L3 审批信号上浮（嵌套子循环抛 ApprovalPauseSignal）：
  第 1 步（子侧，TaskManager.persistPause 既有序列）
    ① 子 PauseSnapshot 落库（contextJson + callCounters + nextCallRef）
    ② 子 ApprovalRequest(decision=pending) 落库（挂子 taskId——第二次人工介入的裁决面）
    ③ 子 Running→Paused（CAS）→ Trace(task_paused)
  第 2 步（父侧，TaskManager.persistDelegationWait 新序列）
    ④ 父 PauseSnapshot 落库（contextJson 同构 + delegation.childTaskId 锚 + 提示 note）
    ⑤ 父 Running→Paused → Trace(task_paused, reason=delegation_child_wait, childTaskId)
```

写序 = **先子后父**：子任务必须已持久化处于 Paused（合法长驻）后，父快照的 `childTaskId` 锚才可信；父侧**不创建新 ApprovalRequest**——第二次人工介入挂子 taskId，委托本身已由第一次父级审批放行（父 resume 放行锚点 `requestForCallRef(nextCallRef)` 复用该 approved 请求，故乱序/重复 resume 幂等）。崩溃落点由三窗口矩阵覆盖：落在①~③之间 → 子可能 Running（被扫描终局）而父 Running（同被终局，窗口①）；落在④⑤之间 → 父 Running 被扫描终局（R-4 兜底删孤儿快照），子保持 Paused。

## 二次委托风暴封闭句

对「父委托子、子再委托孙」的二次委托风暴情形，本期给予**运行期调用点封闭拒绝**：深度上限默认 1（`DELEGATION_DEPTH_LIMIT`），任何 `delegationDepth ≥ 1` 的任务再请求 `task-delegate` 即遭 `policy_denied(risk_level_blocked)`，载荷 `reason=delegation_depth`，孙任务零创建（子 Spec 声明 task-delegate 时注册放行——仅运行期拦截，与设计 §4.4 治理规则表一致）。若未来放宽深度上限，环路（委托树内重复 agentId，A→B→A）仍由 `parentTaskId` 上溯校验独立封闭（`reason=delegation_cycle`，先于深度检查）。两层共同构成对任意深委托链的封闭性：**限深拒绝 + 环路禁止**。

## A3 注记（随批登记）

1. **parentTaskId 规格-实现漂移登记（P2-1）**：A3 §4 早有 `parentTaskId` 规格行，但 `db.ts` 迁移从未落地——属规格-实现存量漂移（WP-4A 审查确认，旧记忆「列已在」有误）。本批以 `ADD COLUMN task_record.parentTaskId TEXT` 补迁移落地（零数据回填，存量行为不变=默认 NULL 即根任务），并增列 `delegationDepth INTEGER NOT NULL DEFAULT 0`。
2. **resume 时序（成文进 A3 注记）**：规范时序 = **先子后父**；乱序容错：resume 父时子任务仍 Paused/pending → 父保持 Paused + 结构化提示「先处置子任务」（幂等，可重复 resume，不创建新父级审批）；「子 Running 而无执行进程」= 不可达态（嵌套中父必在执行；父若崩溃已被恢复扫描终局，见崩溃三窗口矩阵）。
3. **A6 §3 事件目录增补 ×2（章程变更提案载体 = 设计文档 §4.4）**：`task_delegated`（子创建时，父 Trace：childTaskId/agentId/agentVersionId/inputDigest/delegationDepth/note）、`task_delegation_completed`（子终态时，父 Trace：childTaskId/status/outputDigest）。
4. **闸门顺序修订（A2 §8 v1.2）**：声明检查 → 目标白名单（**等级无关**，task-delegate 参数映射 `agentId`；既有 L2 工具维持字面 `target` 检查、行为零变更，回归断言随批）→ 等级分支（L3 审批 / L4 拦截）→ L2 参数范围。
