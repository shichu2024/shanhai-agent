## 1. 问题理解

**背景：** 第一阶段交付了最小 Runtime 闭环（Spec→执行→Trace→评估→验收，54/54 测试，13 项验收全过），规格 V1 中以「空壳预留」「显式声明延后」处理的 9 项能力成为第二阶段的全部范围。这些预留点（Paused 空壳、ApprovalRequest 8 字段、evaluationPolicy 字段位、memoryPolicy 单值、A1 §6 外键预留、A5 无回退边、A6 §8 脱敏声明）是本设计的接入锚——第二阶段的本质是**把预留点激活为真实机制，且不破坏任何已冻结断言**。

**真实目标：** 不是「补齐功能清单」，而是让山海司从「单版本单任务的验证参考实现」演进为「具备安全治理（玄武）、质量门（白虎最小）、认知积累（白泽最小）、受控演进（女娲最小）的可信 Agent 平台」——V1.1 四组件的职责在第二阶段各取**最小可行形态**。

**表面需求 vs 核心问题 vs 潜在问题：**
- 表面需求：落地 §10 的 9 项延后能力；
- 核心问题：每项能力都有「与不可变/可举证底线的接触面」——审批触及版本绑定、脱敏触及 T1/T2、灰度触及指针语义、记忆触及 Trace 真源性。设计的主战场是这些接触面，不是功能本体；
- 潜在问题：批次间隐藏耦合（如灰度 promotion 依赖 Reviewed 环、Evolution guardrail 依赖 Reviewed）若不在批次计划中显式排布，会在实施中途反噬排期（组织死因：悬置拖延的历史风险）。

## 2. 目标与非目标

**目标：**
1. 9 项延后能力全部给出字段表级规格扩展（A1–A6 增补，WP-2B 可直接实现）；
2. 批次计划：依赖顺序 + 每批 DoD + 削减顺序；
3. 冻结决策表延续（D-8 起）+ 规格 V1 兼容迁移路径；
4. T1/T2/T3 断言在全部扩展后仍机械可断言（含扩展断言 T2′）。

**非目标：**
- 不做沙箱执行环境（V1.1 §14.4，第三阶段）；
- 不做远程 Agent / 联邦协议标准化（鲲鹏远程侧，第三阶段）；
- 不做白虎完整评估体系（只激活 evaluationPolicy 最小断言 + Reviewed 环所需最小评估门）；
- 不做多 Runtime 实例 / 分布式（SQLite 单写者模型保持）；
- 不承诺 OTel 立即接入（批次四为条件触发制，见 §4.9）。

**成功定义：** 三票齐备、规格升格 V1.x、批次一可直接拆解为 WP-2B 任务。
**失败定义：** 任一扩展破坏 T1/T2/T3 可断言性，或迁移路径要求存量数据重写。

## 3. 总体思路与设计原则

1. **预留点激活原则：** 所有扩展落在 V1 已预留的锚点上（Paused / ApprovalRequest / evaluationPolicy / memoryPolicy / 外键列），不推翻任何已冻结结构——F-1 教训的正面应用：改一处必须全链一致（A1–A6 联动修订），且每条新机制写明「进程模型假设」；
2. **平台层与 Spec 层分权：** 数据治理（脱敏规则）、发布策略（灰度权重）、审批人配置属**运行时配置**（平台层）；风险声明（approvalPolicy）、记忆策略（memoryPolicy）、演进边界（evolutionPolicy）属 **Spec**（版本化、随快照冻结）——与 T3「配置不入版本、Spec 全快照」的既有分权一致；
3. **不可变性外推：** AgentVersion 不可变 → 演进只能产生**新版本候选**，永不就地修改；记忆条目不可变 + 状态机外置（可信度流转写状态列，内容列追加 only）；
4. **真源不迁移原则：** JSONL+SQLite 双流仍是唯一真源；OTel 是投影层（§4.9），任何断言不得只依赖投影；
5. **默认即第一阶段：** 所有新字段的默认值 = 第一阶段行为（approvalPolicy 缺省 never、canaryWeight 缺省 0、memoryPolicy 缺省 working）——存量 Spec、存量库、存量 CLI 脚本零迁移成本。

## 4. 方案组成：九项设计与规格扩展草案

### 4.1 人工审批完整流（玄武最小形态）

**触发器语义（A3 Paused 激活）：**

| 触发 | 条件 | 迁移 |
|---|---|---|
| T-A1 高风险工具请求 | 模型请求 L3 工具且该 Spec `approvalPolicy.mode` 允许 | `Running → Paused`，写 ApprovalRequest（decision=pending） |
| T-A2 显式声明 | `approvalPolicy.mode: "always"`：任务启动即挂起审批 | `Queued → Paused`（经 Running 前置检查后）**不采用**——见决策 D-9，第二阶段仅工具级触发 |
| T-A3 审批通过 | CLI approve | `Paused → Running`，继续执行该工具调用 |
| T-A4 审批拒绝 | CLI deny | `Paused → Cancelled`（cancelReason=approval_denied） |
| T-A5 审批超时 | `approvalPolicy.timeoutMs` 到期 | 按 `onTimeout` 策略（见下） |

**A1 增补 `approvalPolicy`（Spec 层，可选，缺省 = 第一阶段行为）：**

| 字段 | 类型 | 必填 | 默认 | 约束 |
|---|---|---|---|---|
| `mode` | string | 是（当 approvalPolicy 存在） | — | 枚举：`never`（缺省语义，等价不声明）/ `onHighRisk`（L3 工具请求时挂起）。`always` 第二阶段不实现（注册拒绝，防伪声明） |
| `timeoutMs` | integer | 否 | 86400000（24h） | ≥1000 |
| `onTimeout` | string | 否 | `deny` | 枚举：`deny`（→ Cancelled，同拒绝）/ `fail`（→ Failed，failureClass 见 A4 增补） |

**A2 §4 修订（L3/L4 分治——本设计最大语义变更）：**

| 等级 | 第一阶段 | 第二阶段 |
|---|---|---|
| L3 高风险不可逆 | 注册即拒 | **注册放行**（仅当 Spec 声明 approvalPolicy.mode=onHighRisk；未声明而引用 L3 工具 → 仍注册拒绝，防「声明了却无审批路径」的死声明——对齐底线 1） |
| L4 禁区 | 注册即拒 | **维持注册即拒，永久**（写入安全域/凭据操作不属于「人工可审」范畴——玄武 §14.1「默认拒绝 + 显式授权」的硬核） |

运行期闸门顺序（A2 §8 增补）：L3 请求 → approvalPolicy 允许？→ 写 ApprovalRequest → Paused；审批通过后**该次调用**放行（不是该工具永久放行——每次 L3 调用独立审批）。`policy_denied` 新增 reasonCode：`approval_denied`（拒绝/超时 deny 后模型再请求同一调用时返回）。

**ApprovalRequest 表（A3 §5 激活，8 字段已定 + 2 增补）：**

| 字段 | 类型 | 说明 |
|---|---|---|
| （D-4 已定 8 字段） | | requestId / taskId / agentVersionId / toolId / riskLevel / requestedAt / decision / decidedAt |
| `timeoutAt` | TEXT | = requestedAt + timeoutMs（超时判定锚点，恢复扫描用） |
| `callRef` | TEXT | 挂起时的调用键 `callNo × callKind`（恢复后续跑该调用的定位） |

**CLI 审批交互（A5 §2 增补命令）：**

| 命令 | 语义 | 副作用 |
|---|---|---|
| `shanhai approval list [--pending]` | 审批队列（含 taskId/agentId/**绑定的 agentVersionId 与 contentHash**/toolId/超时剩余） | 无 |
| `shanhai approval show <requestId>` | 详情（含被请求参数 digest + 该 Spec 绑定快照摘要） | 无 |
| `shanhai approval approve <requestId>` | 通过 | ApprovalRequest.decision=approved + `Paused → Running` + Trace 事件 |
| `shanhai approval deny <requestId> [--reason]` | 拒绝 | decision=denied + `Paused → Cancelled` + Trace 事件 |

**审批超时与挂起任务的崩溃恢复（A3 §6 增补——F-1 同型缺陷预防）：**
- **Paused 不进恢复扫描**（与 Queued 同理：Paused 是持久化的合法长驻状态，无「副作用悬空」问题——副作用恰是被冻结等待审批的那个调用，尚未发生）；
- 超时判定由**下次任意进程触碰该任务时惰性判定**（approve/list/task run 扫到 Paused 且 now > timeoutAt → 按 onTimeout 迁移）+ `approval list` 主动扫描——**不引入后台定时器进程**（CLI 单机模型不变）；
- 恢复扫描增只读警示单列：`stalePausedTasks`（Paused 且已超时但未被惰性判定——提示操作者跑一次 `approval list`），不改状态。

**Paused 期间语义：** 任务级超时（taskTimeoutMs）**暂停计时**（挂钟不等于执行时钟，TaskRecord 增 `pausedDurationMs` 累计列）；预算不新增（无调用发生）；attempt 计数保持。

**A4 增补：**

| Class.SubClass | 触发 | 计入契约失败率 |
|---|---|---|
| `Policy(ApprovalTimeout)` | onTimeout=fail 的审批超时终局 | 否 |
| （Cancelled 终态不产生 FailureRecord——approval deny 走 Cancelled，同第一阶段取消语义） | | |

**A6 增补事件：** `approval_requested`（载荷：requestId/toolId/riskLevel/timeoutAt）、`approval_decided`（载荷：requestId/decision/decidedBy/耗时）、`task_paused`（载荷：reason=high_risk_tool、requestId）、`task_resumed`（载荷：requestId）。信封不变。

**T2′ 扩展断言：** 给定任一 Agent 版本，单一查询返回其全部 L3 审批请求及裁决（audit/ApprovalRequest 按 agentVersionId 索引 + Trace `approval_requested` 事件）——审批可举证是玄武最小的验收面。

### 4.2 Reviewed 版本环（A5 状态机扩展 + 白虎最小评估门）

**新状态机（D-10）：**

```text
Draft ──release──▶ Released ──deprecate──▶ Deprecated
  │                                    ▲
  └──review──▶ Reviewed ──release──▶ Released（同上入 Released）
```

- `review` 迁移：Draft → Reviewed；触发 = CLI `shanhai agent review <agentId> <versionId> [--evaluation <evalId>]`；
- **直发保留**（兼容）：Draft → Released 不经 Reviewed 仍合法（第一阶段存量行为不变）；Reviewed 是**可选质量门**，非强制路径——强制待白虎评估体系成熟后另行裁决（决策点 D-10，接受反方挑战）；
- Reviewed 版本**可绑定测试任务**（`--draft` 类比：`Reviewed` 状态允许显式 `--reviewed` 测试运行，不进正式队列），不可被正式任务绑定、不可为指针目标——只有 Released 可；
- 迁移封闭集增补：`draft→reviewed`、`reviewed→released`；**无回退边**（Reviewed → Draft 禁止——不可变原则外推：质量门判定不可撤销，只能重新注册新版本）。

**最小评估门（evaluationPolicy 激活，A1 §2 增补实现语义）：**

| 字段 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `evaluationPolicy.assertions` | array | `[]` | 输出契约断言集（V1 已有字段位，激活校验行为） |
| `evaluationPolicy.reviewGate` | string | `"manual"` | `manual`（review 命令要求人工确认）/ `"assertions"`（review 时自动跑 assertions 全过方可迁移）/ `"none"` |

`review` 命令执行流：reviewGate=assertions → 对该版本跑一组 `--reviewed` 测试任务（WP-2B 定义默认任务集来源）→ 全过 → Draft→Reviewed + 审计事件 `version_reviewed`（载荷：evalId、assertions 结果摘要）；任一失败 → 拒绝迁移 + RejectedRequest(kind=cli_operation) 审计。`evaluationId` 预留列（A1 §6）激活回填。

**指针与回滚不变：** release/rollback 目标约束仍为 Released（Reviewed 不是合法指针目标）；灰度 canary 指针亦只能指向 Released（§4.7）。

### 4.3 任务立即中止（abort，与 P2-5 取消语义的分界）

**两级取消语义（A3 §2 增补迁移）：**

| 级别 | 触发 | 行为 | 终态 |
|---|---|---|---|
| graceful（V1 已有） | `shanhai task cancel <taskId>` | 挂起标志，等待当前原子调用完成 | Cancelled，Trace `graceful: true` |
| **abort（新增）** | `shanhai task cancel <taskId> --force` | 不等待：① 若在模型调用中——放弃该 Promise 结果（AbortController）；② 若在工具执行中——尽力终止（子进程 kill；进程内函数不可中断则等待其返回但**丢弃结果**）；③ 立即迁移 | Cancelled，Trace `graceful: false` + 载荷 `abortedDuring: {callNo, callKind, phase}` |

**边界（显式声明）：**
- abort 的粒度是 **Runtime 放弃等待**，不是副作用回滚——工具已发出的外部副作用（如已写文件）不撤销、不补偿；Trace 如实记录中止发生在哪个调用中，事后审计依赖此记录；
- abort 到达时任务恰在两次原子调用之间 → 行为等同 graceful（无副作用差异）；
- `Queued → Cancelled`（abort 到达 Queued 任务）= 立即，无等待；
- `Paused → Cancelled`（abort 审批挂起中的任务）= 立即，关联 ApprovalRequest 置 `decision=superseded`（新枚举值——审批请求随任务终结作废，不产生 approved/denied 假裁决）；
- abort 与 graceful 竞争（两命令并发）：先落库者生效（SQLite 单写者串行化）；
- **进程模型假设（F-1 教训条款）：** abort 只能中止**本进程正在执行**的任务；另一进程 Running 中的任务，abort 命令写 `abortRequested` 持久化标志（TaskRecord 增列），执行进程在下一个原子调用边界检查并执行中止——跨进程 abort 延迟上限 = 最长原子调用时长（与 graceful 同界，差异仅在进程内 immediacy）。

**A6 增补：** `task_cancelled` 载荷扩展（`mode: graceful|abort`、`abortedDuring?`、`abortRequestedBy?`）；`TaskRecord` 增列 `abortRequested`（0/1）。

### 4.4 持久化记忆与可信度状态机（白泽最小形态）

**A1 增补 `memoryPolicy` 取值扩展：**

| 取值 | 语义 | 第二阶段实现 |
|---|---|---|
| `working`（缺省） | 仅任务内上下文（V1 行为） | 已有 |
| `persistent` | 任务间持久记忆 | 新增，结构：`{type:"persistent", writePolicy:"task_output"（唯一来源，第二阶段仅此值）, maxEntriesPerTask: integer(默认 10), retentionDays: integer(默认 90)}` |

**MemoryRecord 新表（白泽最小，挂靠 Registry 模块——不新增第八模块之外的模块，记忆读写经 TaskManager 执行期调 Registry 存储 API）：**

| 字段 | 类型 | 约束 |
|---|---|---|
| `memoryId` | TEXT PK | uuid v4 |
| `agentId` / `agentVersionId` | TEXT | 写入时绑定的版本（T1 锚点外推） |
| `taskId` | TEXT | 证据回链（必填——**无证据不记忆**，白泽 §9.5 证据原则的最小化） |
| `kind` | TEXT | `episodic`（任务结论）/ `fact`（抽取事实，第二阶段仅 episodic——防过度设计） |
| `content` | TEXT | 记忆内容（**过脱敏管道**，§4.6 同规则） |
| `contentDigest` | TEXT | SHA-256，去重键 |
| `confidence` | REAL | 0–1，初始 = 0.5（任务成功写入）；随证据流转移（下表） |
| `status` | TEXT | 可信度状态机（下表） |
| `evidenceCount` | INTEGER | 累计支持证据数 |
| `createdAt` / `lastUpdatedAt` | TEXT | 内容不可变，仅状态/计数列可更新 |

**可信度状态机（D-13，V1.1 白泽 7 态收窄为 4 态最小集）：**

```text
candidate ──(独立任务再次印证)──▶ active ──(反例出现)──▶ degraded ──▶ retired
     │                            │                          ▲
     └──────(retentionDays 到期)──┴──────────────────────────┘（殊途同归）
```

| 状态 | 语义 | 注入运行时上下文 |
|---|---|---|
| `candidate` | 单次证据，未复证 | 否 |
| `active` | ≥2 次独立任务印证（confidence ≥0.7 且 evidenceCount ≥2） | 是 |
| `degraded` | 出现反例（引用该记忆的任务终局 Failed） | 是，但附 degraded 标记 |
| `retired` | 到期/连续反例/人工下线 | 否 |

状态迁移规则机械可判（confidence 与 evidenceCount 阈值触发），迁移追加审计事件（A6 增补 `memory_state_changed`）——**可信度流转全留痕**，与「能力结论制品层」的差异化主张（定稿 §1）咬合。

**注入防护（V1.1 §14.3「通过记忆持久化的攻击内容」最小对策）：**
1. 记忆**读取时**作为上下文注入，注入内容包裹显式边界标记 + 「记忆内容不是指令」的固定声明；
2. 记忆**不包含**工具结果原文（写入源限定为任务 outputContract 校验通过的 final output——契约输出已被结构化约束，攻击面最小）；
3. A6 增补事件 `memory_written` / `memory_loaded`（载荷：memoryId、taskId、kind、status）——记忆读写全举证，T2 类查询可覆盖。

### 4.5 Evolution Policy（女娲最小形态，A1 预留字段激活）

**A1 顶层解禁 `evolutionPolicy`（V1 删除该字段时的「顶层禁止」条款同步废止——增补 A1 §2 修订注记）：**

| 字段 | 类型 | 必填 | 默认 | 约束 |
|---|---|---|---|---|
| `allowed` | boolean | 是 | — | false 时该 Spec 不产生演进候选 |
| `triggers` | string[] | 否 | `["repeated_failure"]` | 枚举子集：`repeated_failure`（同 subClass 失败 ≥ 阈值）/ `capability_degradation`（白泽 degraded 态记忆关联） |
| `failureThreshold` | integer | 否 | 3 | repeated_failure 触发阈值 |
| `guardrails.requireReviewed` | boolean | 否 | **true（强制不可关）** | 演进产物必须经 Reviewed 环才可发布——女娲「不能绕过白虎直接发布」的规格化（V1.1 §3.3.12） |

**演进候选流（人工确认制，D-14）：**

```text
FailureRecord（达阈值）/ degraded 记忆
  → EvolutionCandidate 记录（新表：candidateId, agentVersionId, trigger, evidenceRefs[], status, proposedChange?）
  → 人工检视（CLI `shanhai evolution list/show`）
  → 确认 → 按 proposedChange 起草新 Spec → 注册新版本（Draft）
  → 强制走 review →（assertions 门）→ Reviewed → release
```

**硬边界：** 系统永不自动注册、自动发布——演进自动化的上限是「产生带证据链接的候选」（女娲最小闭环 = 候选生成 + 证据聚合 + 强制质量门），变更本体永远人工起草。这与底线 3（不可变）和三角色对抗机制（本项目自身验证过的模式）同构。`evolutionCandidateId` 预留列（A1 §6 / A4 §2）激活回填。

### 4.6 Trace 脱敏（A6 §8 已知接受项 → 真实机制）

**处理位置（D-11）：写入时脱敏，原文不落盘。** 理由：① T3 精神外推——发布物零密钥，Trace 落盘物同等对待（Trace 目录会随演示包/开源仓库分发，是事实上的发布物）；② 读出时脱敏要求原文落盘，密钥管理复杂度（加密保险库）与 T3「无密钥即拒绝」冲突；③ 不可逆是特性不是缺陷——配合 digest 保序（见下），检索与对账能力不受损。

**redactionPolicy（运行时配置，平台层——不进 Spec，理由见 §3-2）：**

| 配置项 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `rules[].pattern` | string(正则) | 见下 | 命中即替换为 `[REDACTED:<ruleId>]` |
| `rules[].scope` | string | `payload` | `payload`（仅载荷原文层）/ `all`（含 input/output 全文） |
| `preserveDigests` | boolean | **true（不可关）** | digest/信封字段永参与脱敏排除表 |
| 默认规则集 | — | — | ① 密钥格式正则（**复用 T3 扫描清单同一载体**——复盘 §6-2「发布安全清单机制化」的落点）；② email；③ 疑似 IP（可选启用） |

**不破坏 T1/T2 的机制（本项最大风险点，§7 详列）：**
1. **脱敏排除表（白名单）**：公共信封 10 字段（A6 §2）、`task_started.bindingSnapshot`、全部 `*Digest` 字段——结构化字段不做正则脱敏，只对自由文本载荷（input 原文、output 原文、message、args/result 原文层）执行；
2. digest 在脱敏**前**计算（内容身份以原文 digest 为准，跨版本对账稳定）；
3. 脱敏动作自身留痕：事件载荷增 `redacted: [{ruleId, count}]` 摘要（不含原文）——「脱敏了什么」可审计，「被脱敏内容」不可恢复；
4. **T1/T2 回归断言前置**：WP-2B 实现时，第一阶段 T1/T2 验收脚本必须在脱敏管道开启的库上原样重跑全过（批次二 DoD 硬条款）。

**叙事义务翻转（A6 §8 修订）：** 引入后声明改为——「Trace 已按配置规则脱敏，规则可枚举、命中可审计；脱敏是缩小暴露面的工程措施，**不是**绝对安全承诺（规则覆盖有边界，S3 发布安全断言独立成立）」。

### 4.7 灰度发布（A5 指针模型扩展）

**双指针 + 权重分派（D-12）：**

| 字段（Agent 表增列） | 类型 | 默认 | 约束 |
|---|---|---|---|
| `canaryVersionId` | TEXT NULL | NULL | 只能指向同 agentId 的 **Released** 版本；设置时不得等于 currentVersionId |
| `canaryWeight` | INTEGER | 0 | 0–100；0 = 无灰度（缺省 = 第一阶段行为） |

**分派规则（版本绑定原则不变——创建时一次性固化）：**
- 任务创建入口（A3 §3.1 落库前检查②指针解析处）：按 `canaryWeight` 概率分派 stable/canary 指针 → 解析出的 agentVersionId 固化进 TaskRecord（此后指针移动不影响已创建任务——V1 语义原样保持）；
- TaskRecord 增列 `assignmentSource`（`stable / canary / explicit`——explicit = 命令行显式指定版本的创建）；
- **分派可举证**：分派结果记入 `task_created` 事件载荷（assignmentSource + 分派时的双指针值）——灰度期间任一任务可回溯「为什么进了金丝雀」。

**CLI（A5 §2 增补）：**

| 命令 | 语义 |
|---|---|
| `shanhai agent canary set <agentId> <versionId> --weight N` | 设置灰度（审计事件 `canary_configured`） |
| `shanhai agent canary clear <agentId>` | 权重归零（立即，审计） |
| `shanhai agent promote <agentId>` | canary → stable：指针移动 + canary 清零（审计事件 `version_promoted`） |
| `shanhai agent report <agentId> [--since]` | 按 assignmentSource 分组的通过率对比（数据源 = FailureRecorder + Trace，C2 聚合口径复用） |

**晋升/回退判据（机械可断言，非自动执行）：** promote 前置检查 = 金丝雀组契约通过率 ≥ stable 组 − 5pp 且样本数 ≥ 20（阈值可配，判据输出在 `report`，**决定权留人**——与 Evolution 同一治理哲学：系统举证，人裁决）。回退 = `canary clear`（权重归零立即生效，无时间窗——V1 rollback 语义的灰度版）。

**边界：** Deprecated 目标不可设为 canary；canary 指向版本被 deprecate 时 → 设置被 P2-6 同规则拒绝（先 clear 或换目标）。

### 4.8 OTel 真接入（条件触发制——第二阶段只立机制，不承诺接入）

**触发条件（量化，满足其一才立项实施——D-15）：**
1. 单库 Trace 文件数 > 10,000 或 T1 单查询 P95 > 500ms（存储/检索压力实测信号）；
2. 出现 ≥2 个 Runtime 实例或首个远程 Agent 接入（鲲鹏触发，跨实例聚合需求成立）；
3. 用户/外部 APM 对接需求显式提出。

**满足前的义务（批次四交付的是这个）：** ① 触发指标进 `shanhai agent report` 旁挂的只读健康面板（文件数、索引行数、查询延迟采样）；② 本文档 §4.8 的投影层设计作为已归档设计资产，触发后直接实施。

**投影层设计要点（触发后实施规范，现在冻结）：**
- **JSONL+SQLite 是唯一真源，OTel 是投影**——事件 → OTLP span/log 双流转换器（Trace 文件为 Task Span，调用事件为子 Span，`gen_ai.*` 属性名已对齐 A6 §2）；导出失败只记告警事件，**不阻塞任何任务执行路径**；
- T1/T2/T3 断言**永不下沉到 OTel 后端**——断言查询始终走 SQLite/JSONL（真源不迁移原则，§3-4）。

### 4.9 多 Agent 协作治理（最小形态，建议裁至第三阶段——D-16）

**最小形态的裁剪裁定：** 第二阶段只交付**委托数据模型 + 治理规则**，不做编排器、不做远程协议：

| 交付物 | 内容 |
|---|---|
| `parentTaskId` 列 | TaskRecord 增列（NULL = 根任务）——委托的锚点，A1 §6 外键预留的姊妹位 |
| 委托语义 | 委托 = 以父任务 output 为 input 创建子任务（子任务走**完整**生命周期：Spec 校验→执行→Trace→终态），子任务绑定**子 Agent 自己的 Spec 版本**（工具策略、预算均不继承父任务——玄武 §14 默认拒绝原则外推：跨 Agent 无隐式授权） |
| 治理硬规则 | ① 委托深度上限（运行时配置，默认 2）；② 子任务工具风险等级作用域独立（父 L3 审批不覆盖子 Agent 的 L3）；③ 子任务终态回填父任务上下文的方式 = 显式 input（无共享内存） |
| 明确延后（第三阶段） | Supervisor 编排器、AgentCard 协议、远程 Agent、跨 Agent 指令污染防护专项（V1.1 §14.3 后三条） |

**理由：** 委托模型是记忆/Evolution 之外唯一必须在表结构上预留的项（不预留则第三阶段迁移需回填全表）；编排器与协议在单机 SQLite 模型下没有真实消费场景，先做即过度设计。**接受反方就此挑战**——若审查认为「无编排器的委托模型无验证价值」，可整体裁至第三阶段，仅留列。

### 4.10 批次计划（依赖顺序 + DoD + 削减顺序）

**对决策官初步建议的裁定：** 基本接受四批框架，两处微调（给理由）：① 「批次二 脱敏+灰度」维持，但**灰度对批次一 Reviewed 无硬依赖**（promotion 判据只需通过率对比，不需要 Reviewed 环），真依赖链是批次三 Evolution guardrail → 批次一 Reviewed——维持原批次归属不变，理由改为「数据治理与发布策略同属平台层配置机制，实现面同源（Agent 表 + 运行时配置 + report 聚合）」；② 多 Agent 从批次四中**裁出**（§4.9），批次四收窄为「OTel 条件监测 + 发布安全清单机制化（T3 魔数清单配置化 + safetensors 嗅探——复盘遗留 #2/#6-2 顺势归批）」。

## 5. 关键流程（正常/异常/边界，含谁负责/何时触发/失败怎么办）

**F-1 审批正常流：** 模型请求 L3 工具（Running 中）→ ToolExecutor 识别 L3 + approvalPolicy 允许 → TaskManager 写 ApprovalRequest（持久化，先写后行）→ `Running → Paused`（Trace: task_paused + approval_requested）→ 审批者 `approval list` 看到（含绑定版本摘要）→ `approve` → 校验任务仍 Paused 且 request pending → `Paused → Running` → ToolExecutor 执行该次调用 → Trace: approval_decided + tool_call_executed。
**F-2 审批异常：** ① 审批者看到时任务已被 abort（superseded）→ approve 返回结构化错误 + 审计；② 审批期间版本被 deprecate → **不影响**（任务绑定 agentVersionId 固定，审批针对绑定版本——审批界面显示的就是绑定版本，不存在「审的不是跑的」）；③ 超时无人审 → 惰性判定按 onTimeout 迁移（§4.1）；④ 同任务多次 L3 请求 → 每次独立 ApprovalRequest，逐个审批。
**F-3 跨进程中止边界流：** 进程 A `task cancel --force` → 目标任务在进程 B Running → A 只写 abortRequested 标志 + 审计 → B 在当前原子调用边界读到标志 → 执行中止迁移 → A 侧命令返回「已登记，生效依赖执行进程」——**两段式诚实语义**，不谎报立即生效。
**F-4 脱敏写入流：** 事件构造 → 对载荷自由文本字段执行规则集 → 计算并附 `redacted` 摘要 → digest（原文口径）→ 写 JSONL → 写索引（双写次序不变，D-6 不回退）。
**F-5 灰度分派流：** `task create` → 读双指针 + 权重 → 分派（显式指定版本则跳过）→ 固化 agentVersionId + assignmentSource → 落库（先持久化后继续不变）→ task_created 事件留痕。
**F-6 演进候选流：** FailureRecorder 落 FailureRecord → 演进扫描（report/evolution list 时惰性聚合，不常驻进程）→ 达阈值生成 EvolutionCandidate（evidenceRefs 回链）→ 人工检视 → 起草新 Spec → 注册 → review → release——全链已有机制组合，无新执行路径。

| 8 | 审批人单人（CLI 操作者）模型够用；多审批人/会签为第三阶段 | 已知取舍（用户确认范围 implied——单机参考实现定位） |
| 9 | Paused 不进恢复扫描无副作用悬空风险（副作用即被冻结的未发生调用） | 已知事实（由先持久化后继续不变式保证） |
| 10 | 灰度 promote 判据（−5pp / N≥20）阈值合理 | 推测判断（首批真实数据后校准，判据输出与决定权分离缓解） |

## 8. 取舍说明

1. **审批只做工具级（T-A2 always 模式不实现）**：任务级挂起（整任务审批）在 CLI 单操作者模型下与「先跑 Dry-run 再正式跑」等价，已有 --draft/--reviewed 覆盖，做了即伪需求——牺牲与 V1.1 玄武全量审批的对齐进度，换取第二阶段范围收敛；
2. **脱敏写入时不可逆（无保险库）**：牺牲事后取证原文能力（digest 仍可对账），换 T3 一致的零密钥简单性——取证粒度退化为「脱敏后原文 + 命中摘要」；
3. **Evolution 人工确认制**：牺牲自动化演进演示效果，换不可变底线的绝对安全——女娲闭环在第二阶段是「候选 + 证据 + 强制门」，不是自动修复；
4. **OTel 条件触发制**：牺牲「九项全落地」的形式完整性，换真源单一性（无真实触发就接入 = 维护两套真相的风险）；
5. **多 Agent 裁至第三阶段**：牺牲 V1.1 鲲鹏最小面，换单机模型下的诚实范围。

## 9. 特别要求清单

**9.1 最容易被忽略的三个问题：**
1. **Paused × 崩溃恢复扫描**——若照抄第一阶段扫描逻辑把 Paused 当非终态遗留迁移 Failed，则挂起审批任务在重启后全部被误杀（F-1 的同型缺陷：规格条款未写明进程模型假设）。本文 §4.1 已显式排除，反方请专项复核；
2. **审批界面的版本锚定**——审批者天然看「当前指针版本」，而任务绑定的是创建时版本；两版本不同时「审的」与「跑的」不同。本文以「审批列表强制显示绑定 agentVersionId + contentHash」解决，属易被实现层忽略的 UI 细节；
3. **脱敏 × digest 的次序**——digest 必须在脱敏前按原文计算，否则跨版本/跨任务对账（灰度 report、记忆去重）全部失配。实现顺序错误不会被单测自然暴露（单任务内自洽），需跨任务对账断言。

**9.2 最可能失败的三个场景：**
1. 审批挂起任务在两进程 CLI 模型下长期无人处置（超时惰性判定依赖有人触碰）——缓解：stalePausedTasks 警示 + 默认 24h deny；残余风险：静默库中挂起任务不可见（接受，与 staleQueuedTasks 同级风险）；
2. 脱敏规则误伤结构化字段破坏 T1/T2——缓解：排除表白名单 + 第一阶段验收脚本重跑硬条款（DoD 失败即设计失败，不留「部分可查」灰色态）；
3. 记忆注入被诱导为指令（V1.1 §14.3 明示攻击面）——缓解：来源限定 + 边界标记；残余风险真实存在（推测判断 #4），若反方判定不充分，降级方案 = 记忆默认不注入、仅 report 可见。

**9.3 当前方案最依赖的三个假设：** §7 之 #2（脱敏排除表充分）、#4（记忆来源限定有效）、#1（L2/L3/L4 三分够用）。

**9.4 最值得被反方挑战的三个设计点：**
1. **审批超时默认 deny → Cancelled**（而非 Failed）：Cancelled 不进失败统计、不触发 Evolution——若审查认为「超时该算治理失败信号」，应改 onTimeout=fail 为默认（当前选择理由：超时是治理流程惰性，不是任务失败，不该污染 C2 类统计与演进触发）；
2. **Reviewed 环可选（直发保留）**：若审查认为质量门不强制则形同虚设，应改「L3 工具的 Spec 强制 Reviewed 才可 release」（风险闸门与质量门绑定）——代价是存量直发路径收窄；
3. **多 Agent 整体裁至第三阶段**：若审查认为委托模型无编排器即无验证价值，进一步裁到只留 parentTaskId 列；反之若认为数据模型本身需真实验证，可升为批次四实现项。

**9.5 资源/时间/人员减少时的削减**：§4.10 削减顺序（多Agent→OTel→T3机制化→Evolution→记忆高级态→灰度→脱敏*→中止）；底线不可削：审批 + Reviewed + T1/T2/T3 零回退。

**9.6 规模扩大时可能成为瓶颈的部分：** ① SQLite 单写者——并发审批写 ApprovalRequest、多 Runtime 实例写 trace_index 串行化（第三阶段迁移 PostgreSQL 的既定路径，定稿 §4.2）；② 审批人单点——会签/多审批人在单机模型无解；③ Trace 文件数线性增长——OTel 触发线（10k 文件）即为此设，投影层设计已冻结待触发。

## 11. 与规格 V1 的兼容迁移路径

**存量数据（SQLite）：**
1. 全部 schema 变更 = 新增表（ApprovalRequest 实体化 / MemoryRecord / EvolutionCandidate）+ 现有表 ADD COLUMN（TaskRecord ×4 列、Agent ×2 列、AgentVersion 零变更）——SQLite `ALTER TABLE ADD COLUMN` 原地支持，**无数据回填**（新列默认值即第一阶段语义：abortRequested=0、assignmentSource=NULL→报表归 explicit 口径、canaryWeight=0）；
2. 存量 AgentVersion 快照（specVersion "1"）零触碰——不可变底线；执行层校验器按 specVersion 分派，v1 快照按 v1 规则复验（两层校验不变式保持）；
3. 存量 Trace 文件零迁移——新事件类型只追加；旧文件缺新字段不构成错误（消费端按 eventType 判别，向后兼容读取）。

**CLI 行为：** 旧命令签名与语义零变更（release/deprecate/rollback/list/show/cancel/register 原样）；新命令族（approval/review/canary/promote/report/evolution）全部增量。第一阶段 README 快速开始流程在第二阶段 Runtime 上**原样可走通**（批次一 DoD-⑥ 的验收面）。

**Spec 编写者：** v1 Spec 文件在新 Runtime 仍可注册（D-17 等价展开）；仅当使用新能力（approvalPolicy/memoryPolicy.persistent/evolutionPolicy）才需升 v2。

**断言资产迁移：** 第一阶段 T1/T2/T3 验收脚本 + 54 单测 = 每批次回归门槛（零回退硬条款）；T2′（审批可举证）与灰度/脱敏断言为增量脚本，不修改旧断言本体。
