## 1. 问题理解

**背景：** 第一阶段交付了最小 Runtime 闭环（Spec→执行→Trace→评估→验收，54/54 测试，13 项验收全过），规格 V1 中以「空壳预留」「显式声明延后」处理的 9 项能力成为第二阶段的全部范围。这些预留点（Paused 空壳、ApprovalRequest 8 字段、evaluationPolicy 字段位、memoryPolicy 单值、A1 §6 外键预留、A5 无回退边、A6 §8 脱敏声明）是本设计的接入锚——第二阶段的本质是**把预留点激活为真实机制，且不破坏任何已冻结断言**。

**真实目标：** 不是「补齐功能清单」，而是让山海司从「单版本单任务的验证参考实现」演进为「具备安全治理（玄武）、质量门（白虎最小）、认知积累（白泽最小）、受控演进（女娲最小）的可信 Agent 平台」——V1.1 四组件的职责在第二阶段各取**最小可行形态**。

**表面需求 vs 核心问题 vs 潜在问题：**
- 表面需求：落地 §10 的 9 项延后能力；
- 核心问题：每项能力都有「与不可变/可举证底线的接触面」——审批触及版本绑定与**执行态持久化**（V0.2 新增：P0-1 教训）、脱敏触及 T1/T2、灰度触及指针语义、记忆触及 Trace 真源性。设计的主战场是这些接触面，不是功能本体；
- 潜在问题：批次间隐藏耦合（如灰度 promotion 依赖 Reviewed 环、Evolution guardrail 依赖 Reviewed）若不在批次计划中显式排布，会在实施中途反噬排期（组织死因：悬置拖延的历史风险）。

## 2. 目标与非目标

**目标：**
1. 9 项延后能力全部给出字段表级规格扩展（A1–A6 增补，WP-2B 可直接实现），**每条机制写明进程模型假设**（V0.1 自设条款，V0.2 补齐审批续跑与记忆迁移两处缺失）；
2. 批次计划：依赖顺序 + 每批 DoD + 削减顺序（依赖显式，可机械核对）；
3. 冻结决策表延续（D-8 起）+ 规格 V1 兼容迁移路径；
4. T1/T2/T3 断言在全部扩展后仍机械可断言（含扩展断言 T2′）。

**非目标：**
- 不做沙箱执行环境（V1.1 §14.4，第三阶段）；
- 不做远程 Agent / 联邦协议标准化 / 委托编排器（鲲鹏全部，第三阶段，见 §4.9）；
- 不做白虎完整评估体系（只激活 evaluationPolicy 最小断言 + Reviewed 环的 diff 检视清单）；
- 不做多 Runtime 实例 / 分布式（SQLite 单写者模型保持）；
- 不做**任意断点续跑**（本设计只交付审批挂起点专用的最小检查点 PauseSnapshot，见 §4.1——Running 中途崩溃仍 CrashRecovery 终局，A3 §6 语义不变）；
- 不承诺 OTel 立即接入（批次四为条件触发制，见 §4.8）。

**成功定义：** 三票齐备、规格升格 V1.x、批次一可直接拆解为 WP-2B 任务。
**失败定义：** 任一扩展破坏 T1/T2/T3 可断言性，或迁移路径要求存量数据重写。

## 3. 总体思路与设计原则

1. **预留点激活原则：** 所有扩展落在 V1 已预留的锚点上，不推翻任何已冻结结构——F-1 教训的正面应用：改一处必须全链一致（A1–A6 联动修订），且**每条新机制写明「进程模型假设」**（V0.1 仅 abort 写了；V0.2 补齐审批续跑 §4.1-4 与记忆状态迁移 §4.4 两处）；
2. **平台层与 Spec 层分权：** 数据治理（脱敏规则）、发布策略（灰度权重）、审批人配置属**运行时配置**（平台层）；风险声明（approvalPolicy）、记忆策略（memoryPolicy）、演进边界（evolutionPolicy）属 **Spec**（版本化、随快照冻结）——与 T3「配置不入版本、Spec 全快照」的既有分权一致；
3. **不可变性外推：** AgentVersion 不可变 → 演进只能产生**新版本候选**，永不就地修改；记忆条目不可变 + 状态机外置（可信度流转写状态/计数列，内容列追加 only）；
4. **真源不迁移原则：** JSONL+SQLite 双流仍是唯一真源；OTel 是投影层（§4.8），任何断言不得只依赖投影；
5. **默认即第一阶段：** 所有新字段的默认值 = 第一阶段行为（approvalPolicy 缺省 never、canaryWeight 缺省 0、memoryPolicy 缺省 working、injection 缺省 off）——存量 Spec、存量库、存量 CLI 脚本零迁移成本。

## 4. 方案组成：九项设计与规格扩展草案

### 4.1 人工审批完整流（玄武最小形态）

#### 4.1-1 触发器语义（A3 Paused 激活）

| 触发 | 条件 | 迁移 |
|---|---|---|
| T-A1 高风险工具请求 | 模型请求 L3 工具且该 Spec `approvalPolicy.mode` 允许 | `Running → Paused`，写 ApprovalRequest（decision=pending） |
| T-A2 显式声明 | `approvalPolicy.mode: "always"`：任务启动即挂起 | **不实现**（注册拒绝，防伪声明——见决策 D-9；第二阶段仅工具级触发） |
| T-A3 审批通过 | CLI approve | `Paused → Running` → 续跑执行（**迁移由 resume 进程执行，§4.1-4**） |
| T-A4 审批拒绝 | CLI deny | `Paused → Cancelled`（cancelReason=`approval_denied`）——**任务级终局** |
| T-A5 审批超时 | `approvalPolicy.timeoutMs` 到期 | 按 `onTimeout` 策略：`deny`（默认）→ Cancelled（cancelReason=`approval_timeout`）；`fail` → Failed（见 A4 增补） |

**deny 语义（V0.2 钉死，消解 P1-1 双重定义）：** deny 与超时-deny 均为**任务级终局**——任务进 Cancelled 真终态后模型不再获得任何执行机会，不存在「拒绝后模型再请求同一调用」的路径，故**不设 `approval_denied` reasonCode**（死枚举预防，A2 §5 删 `budget_exhausted` 的 P2-1 先例）。approve 之后模型在**后续轮次**再次请求 L3 工具（新调用键）→ 生成**新的** ApprovalRequest、再次挂起——每次 L3 调用独立审批，这是设计语义而非缺陷；审批疲劳由 `maxConsecutiveDenials` 之外的预算与任务超时自然封顶（任务不可能无限挂起：每次挂起都消耗挂钟且受 timeoutMs 约束）。

**cancelReason 封闭枚举（V0.2 增，P3-2 采纳）：** `user / approval_denied / approval_timeout / abort / superseded`——互斥，落 TaskRecord 与 `task_cancelled` 事件，C2 与审计口径可分离。

#### 4.1-2 A1 增补 `approvalPolicy`（Spec 层，可选，缺省 = 第一阶段行为）

| 字段 | 类型 | 必填 | 默认 | 约束 |
|---|---|---|---|---|
| `mode` | string | 是（当 approvalPolicy 存在） | — | 枚举：`never`（缺省语义，等价不声明）/ `onHighRisk`（L3 工具请求时挂起）。`always` 注册拒绝（防伪声明） |
| `timeoutMs` | integer | 否 | 86400000（24h） | ≥1000 |
| `onTimeout` | string | 否 | `deny` | 枚举：`deny`（→ Cancelled）/ `fail`（→ Failed:Policy(ApprovalTimeout)） |

#### 4.1-3 A2 §4 修订（L3/L4 分治）与运行期闸门

| 等级 | 第一阶段 | 第二阶段 |
|---|---|---|
| L3 高风险不可逆 | 注册即拒 | **注册放行**（仅当 Spec 声明 approvalPolicy.mode=onHighRisk；未声明而引用 L3 工具 → 仍注册拒绝，防「声明了却无审批路径」的死声明——对齐底线 1） |
| L4 禁区 | 注册即拒 | **维持注册即拒，永久**（写入安全域/凭据操作不属于「人工可审」范畴） |

**L2→L3 工具重登记的漂移窗口路由（V0.2 显式化，P2-1 采纳；V0.3 R-3 回退修订）：** 工具在 Tool Registry 被重登记为 L3 后，存量 Spec（按 L2 声明）的任务时防御性复验**维持 `Created → Failed: Spec(defensive_revalidation_failed)`，不改道转 ApprovalRequest**。理由：隐式改道与「默认拒绝」原则冲突；工具等级升级的正确路径 = 操作者重登记 + Spec 作者显式新版本声明 approvalPolicy。**运行期调用点窗口（复验后、调用前）若登记等级已变 L3：按当前登记等级拦截（`policy_denied(risk_level_blocked)` 可达）——恢复第一阶段 A2 §4-2 防御纵深行为（V0.3 R-3 裁决回退：版本固定原则保护的是 Spec 语义稳定性，不外推到「工具本体已被重判定为高风险不可逆仍在飞任务按旧等级执行」——那是安全阀，不是语义锚；与「等级只能升不能降」登记原则同向）。三处同步：本节 + §4.11 A2 增补行 + A2 §4-2 修订注记（F-1 全链一致条款）。**

**可见性（V0.3 R-5 采纳）：** report 旁挂「受工具升级影响的 Spec」只读单列（Spec 声明等级 < 当前登记等级的存量引用清单）——与 staleQueued/stalePaused 同一模式，把「Spec 作者该跟进」从原则立场变成可见信号。

运行期闸门顺序（A2 §8 增补）：L3 请求 → approvalPolicy 允许？→ 写 ApprovalRequest + **PauseSnapshot**（§4.1-4）→ Paused；审批通过后**该次调用**放行（每次 L3 调用独立审批）。`policy_denied` reasonCode 封闭集**不变**（不新增 approval_denied）。

#### 4.1-4 审批挂起的执行续跑：挂起即退出模型（V0.2 新增，P0-1 修复，决策 D-18）

**进程模型假设（显式声明）：** 两进程 CLI 模型（`task create` / `task run`）下，run 进程**不长驻等待裁决**。挂起即退出；**`Paused → Running` 迁移权归 resume 进程**（V0.3 R-1 修订，消解 approve/resume 互斥与「迁移后 spawn 前」崩溃窗口）：

```text
run 进程遇 L3 请求
  → 写 PauseSnapshot（执行态快照，先持久化）
  → Running → Paused 迁移 + Trace(task_paused / approval_requested)
  → run 进程正常退出（exit code 提示「awaiting approval <requestId>」）
  → [操作者审批] shanhai approval approve <requestId>
  → 只写 decision=approved + Trace(approval_decided) ——任务保持 Paused
  → approve 默认前台 spawn `shanhai task run --resume <taskId>`（--detach 可选；spawn 失败/崩溃不影响任务状态）
  → [resume 进程] 校验 Paused ∧ approved ∧ snapshot 完整
      → Paused → Running 迁移（先持久化）+ Trace(task_resumed)
      → 同进程内反序列化 snapshot → 从 nextCallRef 继续执行至终态
```

**approve 只写裁决、resume 持有迁移权（R-1 的状态机结构事实）：** 审批者只裁决（decision 字段），执行者（approve-spawn 或 manual-resume）持有 `Paused → Running` 迁移权——任何时刻崩溃，任务**要么 Paused（合法长驻，等 resume）要么已在执行进程手中**，不存在「Running 且无执行进程」的悬空窗口。`resumedBy = approve-spawn | manual-resume` 双值均真实可达：approve 崩溃于 spawn 前（或 --detach 后操作者未续跑）→ 任务停留 Paused → `task run --resume <taskId>` 手动续跑依然成立。

**PauseSnapshot 表（执行态最小检查点，新表）：**

| 字段 | 类型 | 约束 |
|---|---|---|
| `taskId` | TEXT PK | 与 TaskRecord 一对一（挂起期间） |
| `contextJson` | TEXT | 模型对话消息数组（含系统提示、历史调用与结果）序列化 |
| `callCounters` | TEXT | 各调用键（callNo × callKind）的 attemptNo 计数器序列化（A2 §2.1 运行期计数器的持久化载体——仅审批挂起场景） |
| `nextCallRef` | TEXT | 挂起时点的调用键（恢复后执行的动作） |
| `savedAt` | TEXT | RFC3339 |

**规则：**
1. **先持久化后迁移**（不变式②一致）：snapshot 整行事务写入成功才执行 Paused 迁移；kill 落在 snapshot 后、迁移前 → 任务留 Running → 重启恢复扫描按 CrashRecovery 终局（既有语义，正确）+ **顺带删除该 taskId 的 snapshot**（R-4：该任务从未进入 Paused，不触发「离开 Paused 即删」——孤儿快照由恢复扫描/终局迁移兜底清理）；kill 落在迁移后不可能（进程已退出）；
2. **续跑前置校验与迁移（R-1 修订）：** `--resume` 校验 status=Paused ∧ 存在 decision=approved 的 request ∧ snapshot 存在且完整 → **同进程内完成 `Paused → Running` 迁移（先持久化）+ 反序列化 + 继续执行**——与不变式②「先持久化后继续」天然同构；任一校验不满足 → 结构化错误（Paused+pending → 提示先审批；非 Paused → 报告当前状态）；
3. **approve 校验（P3-3 采纳）：** request.taskId 匹配 ∧ request.agentVersionId == TaskRecord.agentVersionId（防跨任务误用）∧ 任务仍 Paused ∧ request 仍 pending ∧ now ≤ timeoutAt（先落库者生效，SQLite 单写者串行化）；**通过后只写 decision=approved + Trace(approval_decided)，任务保持 Paused**（R-1：approve 不做状态迁移），随后可选 spawn（默认前台 `task run --resume`；spawn 失败只提示，不回滚 decision、不影响任务状态——manual-resume 兜底）；
4. **生命周期：** snapshot 在任务离开 Paused（resume 迁移后 / deny / timeout / abort）时**即删**；另由恢复扫描与 CrashRecovery 终局迁移兜底清理（规则 1）；它是执行态暂存，不是审计对象（审计由 Trace 事件承载）；不随发布物分发（本地 SQLite data 目录不在 T3 发布物范围）；
5. **与 A3 §6「Checkpoint 属第二阶段」承诺的对齐声明（诚实边界）：** 本设计交付的是**审批挂起点专用**的最小检查点，不是任意断点续跑——Running 中途崩溃仍 CrashRecovery 终局、Queued 仍 durable pending，A3 §6 收窄语义一字不改。任意断点 Checkpoint 若第三阶段引入，PauseSnapshot 是其首块拼图。

**批次一 DoD 增补（V0.2，反方要求的端到端用例；V0.3 R-1 增断言）：** run 进程于 Paused 态退出/被 kill → `approval approve` → `--resume` 续跑 → 任务至终态（Succeeded/Failed）——全链 Trace 事件齐（task_paused → approval_decided → task_resumed → 终态）；**另断言：approve 崩溃于 spawn 前（或 --detach 后），任务停留 Paused，`task run --resume` 手动续跑仍可达终态**。**此用例组不过，审批流不算成立。**

#### 4.1-7 超时判定与崩溃恢复（A3 §6 增补——F-1 同型缺陷预防）

- **Paused 不进恢复扫描**（V0.1 立场，反方确认成立）：Paused 是持久化的合法长驻状态，无副作用悬空——副作用即被冻结等待审批的那个调用，尚未发生；
- 超时判定**惰性执行**（下次任意进程触碰该任务时：approval list / approve / task run --resume 扫到 Paused 且 now > timeoutAt → 按 onTimeout 迁移）——**不引入后台定时器进程**；
- 恢复扫描增只读警示单列：`stalePausedTasks`（Paused 且已超时但未被惰性判定——提示操作者跑一次 `approval list`），不改状态；
- **report 旁挂审批超时计数单列**（P3-1）：不进 C2 失败率（超时是治理惰性非任务失败），但必须可见，不只藏在 Trace 里。

**Paused 期间语义：** 任务级超时（taskTimeoutMs）**暂停计时**（挂钟 ≠ 执行时钟，TaskRecord 增 `pausedDurationMs` 累计列）；预算不新增；attempt 计数器由 snapshot 承载。

#### 4.1-8 A4 / A6 增补

**A4 增补：**

| Class.SubClass | 触发 | 计入契约失败率 |
|---|---|---|
| `Policy(ApprovalTimeout)` | onTimeout=fail 的审批超时终局 | 否 |

（approval deny 走 Cancelled 终态，不产生 FailureRecord——同第一阶段取消语义；superseded 同理。）

**A6 增补事件：** `approval_requested`（requestId/toolId/riskLevel/timeoutAt/callRef）、`approval_decided`（requestId/decision/decidedBy/耗时/superseded 标注）、`task_paused`（reason=high_risk_tool、requestId）、`task_resumed`（requestId、resumedBy=approve-spawn | manual-resume）。信封不变。

### 4.2 Reviewed 版本环（A5 状态机扩展 + 白虎最小检视门）

#### 4.2-1 新状态机（D-10）

```text
Draft ──release──▶ Released ──deprecate──▶ Deprecated
  │                                    ▲
  └──review──▶ Reviewed ──release──▶ Released（同上入 Released）
```

- `review` 迁移：Draft → Reviewed；CLI `shanhai agent review <agentId> <versionId>`；
- **直发保留**（兼容）：Draft → Released 不经 Reviewed 仍合法（第一阶段存量行为不变）；Reviewed 是**可选质量门**——反方立场支持保留直发（02 号 §4），V0.2 维持；
- Reviewed 版本可绑定测试任务（显式 `--reviewed` 测试运行，不进正式队列），不可被正式任务绑定、不可为指针目标——只有 Released 可；
- 迁移封闭集增补：`draft→reviewed`、`reviewed→released`；**无回退边**（质量门判定不可撤销，只能重新注册新版本）。

#### 4.2-2 review 的检视内容：diff 驱动最小检视清单（V0.2 新增，P1-5 修复）

**检视对象（机械化生成）：** `review` 命令自动生成与**同 agentId 上一 Released 版本**的 Spec diff 报告，人工按清单逐项确认：

| # | 检视项 | 自动标注 |
|---|---|---|
| 1 | 工具集变化（新增/移除；**风险等级上调重点标红**） | diff 机械生成 |
| 2 | 预算变化（maxModelCalls / maxTokens，增幅 >50% 标黄） | diff 机械生成 |
| 3 | mission 职责 / 非职责边界变化 | diff 机械生成 |
| 4 | approvalPolicy 变化（新高风险工具准入） | diff 机械生成 |
| 5 | input/outputContract 结构变化 | diff 机械生成 |

- `manual` 档（reviewGate 默认）：CLI 交互逐项确认上述清单；
- `assertions` 档：自动跑 `evaluationPolicy.assertions` 契约断言 **+ 生成 diff 报告 + 人工确认清单**（自动化部分不替代人工签核——契约断言在运行期已被强制校验，其增量价值在「发布前批量预跑」而非新信息，诚实承认）；
- `version_reviewed` 审计事件载荷（V0.2 修订）：`{ evalId?, checklist: [{item, verdict, note?}], diffAgainst: <上一 Released versionId> }`——检视内容可追溯；
- **诚实声明（V0.2 显式）：** 第二阶段 Reviewed = **流程签核 + 变更面受控检视**，不是完整质量判定。Evolution `requireReviewed` guardrail 依赖的即此检视（变更面有人看过且留痕），其表述强度相应调整为「变更面受控」而非「质量已验证」（§4.5 同步）。

`evaluationPolicy` 字段语义（A1 §2）：`assertions`（V1 字段位，激活校验行为）+ `reviewGate: "manual"(默认) / "assertions" / "none"`。`evaluationId` 预留列激活回填。

**指针与回滚不变：** release/rollback 目标约束仍为 Released；灰度 canary 指针亦只能指向 Released（§4.7）。

### 4.3 任务立即中止（abort，与 P2-5 取消语义的分界）

**两级取消语义（A3 §2 增补迁移）：**

| 级别 | 触发 | 行为 | 终态 |
|---|---|---|---|
| graceful（V1 已有） | `shanhai task cancel <taskId>` | Running：挂起标志，等待当前原子调用完成；**Paused：立即迁移**（挂起态无在飞原子调用，「等待完成」语义不适用——P2-6 采纳） | Cancelled，`graceful: true` |
| **abort（新增）** | `shanhai task cancel <taskId> --force` | ① 模型调用中——放弃该 Promise 结果（AbortController）；② 工具执行中——尽力终止（子进程 kill；进程内函数不可中断则等待返回但丢弃结果）；③ 立即迁移 | Cancelled，`graceful: false` + `abortedDuring: {callNo, callKind, phase}` |

**边界（显式声明）：**
- abort 的粒度是 **Runtime 放弃等待**，不是副作用回滚——已发出的外部副作用不撤销、不补偿；Trace 如实记录中止发生在哪个调用中；
- abort 到达时任务在两次原子调用之间 → 行为等同 graceful；
- `Queued → Cancelled`（abort/graceful 到达 Queued 任务）= 立即；
- `Paused → Cancelled`（graceful 或 abort 到达挂起任务）= 立即，关联 ApprovalRequest 置 `decision=superseded`（不产生 approved/denied 假裁决）+ 删 PauseSnapshot；
- abort 与 graceful 竞争：先落库者生效（SQLite 单写者串行化）；
- **进程模型假设：** abort 只能中止**本进程正在执行**的任务；另一进程 Running 中的任务，abort 写 `abortRequested` 持久化标志（TaskRecord 增列），执行进程在下一个原子调用边界检查并执行中止——跨进程 abort 延迟上限 = 最长原子调用时长。**Paused 任务无执行进程**，cancel（任一级）直接迁移——这是 V0.2 显式化的第二处进程模型假设。

**A6 增补：** `task_cancelled` 载荷扩展（`mode: graceful|abort`、`cancelReason` 枚举、`abortedDuring?`、`abortRequestedBy?`）；TaskRecord 增列 `abortRequested`（0/1）。

### 4.4 持久化记忆与可信度状态机（白泽最小形态，V0.2 重构）

#### 4.4-1 memoryPolicy 扩展（A1 增补）

| 取值 | 语义 | 第二阶段实现 |
|---|---|---|
| `working`（缺省） | 仅任务内上下文（V1 行为） | 已有 |
| `persistent` | 任务间持久记忆 | 新增：`{type:"persistent", writePolicy:"task_output", maxEntriesPerTask:10, retentionDays:90, injection:"off"(默认)|"context"}` |

**injection 默认 off（V0.2 采纳反方建议）：** 默认只写不注入（记忆仅 report 可见）——攻击面最小默认配置；显式声明 `"context"` 才注入运行时上下文。这从「失败后备预案」升格为**默认安全姿态**。

#### 4.4-2 MemoryRecord 表（V0.2 修订：evidenceCount 单维驱动）

| 字段 | 类型 | 约束 |
|---|---|---|
| `memoryId` | TEXT PK | uuid v4 |
| `agentId` | TEXT | **作用域 = agentId 级（跨版本共享）**——白泽是 Agent 级认知，不是版本级 |
| `agentVersionId` | TEXT | 写入时绑定的版本（**仅溯源锚点**，不限定注入作用域） |
| `taskId` | TEXT | 证据回链（必填——无证据不记忆）；「独立印证」= **不同 taskId**（P1-3-2 定义落定） |
| `kind` | TEXT | `episodic`（第二阶段仅此值） |
| `content` | TEXT | 过脱敏管道（§4.6 同规则；脱敏管道为记忆的**前置不可削依赖**，见 §4.10） |
| `contentDigest` | TEXT | SHA-256 去重键 |
| `evidenceCount` | INTEGER | 支持证据数（**状态机唯一驱动维度**） |
| `evidenceCountAtLastTransition` | INTEGER | **状态迁移基线快照**（V0.3 R-2：迁移落库时与状态变更**同事务**写入——否则引入新崩溃不一致窗口，重蹈 R-1 覆辙；恢复边判定锚点） |
| `contradictionCount` | INTEGER | 反例数（注入该记忆且任务终局 Failed 的次数） |
| `status` | TEXT | 可信度状态机（下） |
| `createdAt` / `lastUpdatedAt` | TEXT | 内容不可变；仅状态/计数列可更新 |

**confidence 数值维度删除（V0.2，P1-3-1 采纳「最小修复」）：** 状态机由 evidenceCount / contradictionCount 两个整数计数器机械驱动，无数值更新函数即无主观参数。

#### 4.4-3 可信度状态机（4 态 + 恢复边，V0.2 修订）

```text
candidate ──(evidenceCount ≥ 2，来自不同 taskId)──▶ active
active ──(contradictionCount ≥ 1)──▶ degraded
degraded ──(evidenceCount − evidenceCountAtLastTransition ≥ 2，独立 taskId)──▶ active   ← 恢复边（V0.3 R-2 基线列，机械可判）
candidate/active/degraded ──(retentionDays 到期 | contradictionCount ≥ 3 | 人工下线)──▶ retired
```

**恢复边可判性（V0.3 R-2 修复）：** V0.2 的「degraded 后新增 ≥2」在纯累计计数器下无法区分降级前后证据——惰性校正判不出该边（P1-3-1 的换形复发，反方 R-2 指出）。V0.3 以 `evidenceCountAtLastTransition` 基线列锚定：每次状态迁移落库时与状态同事务快照当前 evidenceCount，恢复条件 = `evidenceCount − 基线 ≥ 2`——纯整数比较，机械可判成立；基线快照与迁移同事务是硬约束（预裁决 05 号 R-2 落稿注意）。

| 状态 | 语义 | 注入运行时上下文（injection=context 时） |
|---|---|---|
| `candidate` | 单次证据，未复证 | 否 |
| `active` | ≥2 次独立任务印证 | 是 |
| `degraded` | 出现反例（可恢复——后续印证可回 active） | 是，附 degraded 标记 |
| `retired` | 到期/连续反例/人工下线 | 否 |

**进程模型假设（V0.2 显式化，P1-3-3 修复）：** 计数与状态迁移的执行主体分两层——
1. **任务终态迁移时同步更新（执行进程，同一事务）：** 任务 Succeeded → 本次写入的记忆 evidenceCount+1；任务 Failed → 本次**注入列表中的**每条记忆 contradictionCount+1（注入清单在 memory_loaded 事件中已留痕，回看即得）；状态级别变更随计数即时机械判定；
2. **惰性全量校正（report / `shanhai memory list` 时）：** 以计数器重算全部状态（幂等），纠正任何漂移——与审批超时惰性判定同一模式，无常驻进程。

**「注入 ≠ 使用」误差（P2-3 处置）：** contradictionCount 判定采用「注入且任务 Failed」的可判近似（不试图判定模型是否真的使用了该记忆）——误降级风险由**恢复边**化解：与记忆无关的失败最多触发一次降级，后续独立印证 ≥2 即恢复。误差已知接受，显式记录。

**注入防护（V1.1 §14.3 最小对策）：** 注入内容包裹显式边界标记 + 「记忆内容不是指令」固定声明；写入源限定 outputContract 校验通过的 final output；A6 增补 `memory_written / memory_loaded / memory_state_changed` 事件（memoryId、taskId、kind、status、计数快照）——读写与状态流转全举证。

| 字段 | 类型 | 必填 | 默认 | 约束 |
|---|---|---|---|---|
| `allowed` | boolean | 是 | — | false 时该 Spec 不产生演进候选 |
| `triggers` | string[] | 否 | `["repeated_failure"]` | 枚举子集：`repeated_failure` / `capability_degradation`（白泽 degraded 态记忆关联） |

| `guardrails.requireReviewed` | boolean | 否 | **true（强制不可关）** | 演进产物必须经 §4.2-2 检视清单签核才可发布 |

**聚合键（V0.2 钉死，P2-2 采纳）：** `repeated_failure` 按 **agentId 聚类**（跨版本——失败模式是 Agent 级资产），evidenceRefs 回链具体 agentVersionId；候选挂 agentId，产物新版本由人工起草（版本不可变 → 候选不指向「谁的下一版」，指向 agentId 的演进 backlog）。

**演进候选流（人工确认制，D-14）：**


**硬边界：** 系统永不自动注册、自动发布——自动化的上限是「产生带证据链接的候选」（女娲最小闭环 = 候选生成 + 证据聚合 + 强制检视门 + 灰度安全网）。guardrail 表述（V0.2 调整）：requireReviewed 承诺的是**变更面受控**（有人按清单看过并留痕），不是「质量已验证」。`evolutionCandidateId` 预留列激活回填。

### 4.6 Trace 脱敏（A6 §8 已知接受项 → 真实机制，V0.1 立场全部维持）

**处理位置（D-11）：写入时脱敏，原文不落盘。** ① T3 精神外推——Trace 目录随演示包/开源仓库分发，是事实上的发布物；② 读出时脱敏要求原文落盘，密钥管理与 T3 冲突；③ 不可逆配合 digest 保序，检索对账能力不受损。

**redactionPolicy（运行时配置，平台层）：**

| 配置项 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `rules[].pattern` | string(正则) | 见下 | 命中即替换为 `[REDACTED:<ruleId>]` |
| `rules[].scope` | string | `payload` | `payload`（自由文本载荷层）/ `all` |
| `preserveDigests` | boolean | **true（不可关）** | digest/信封字段永在脱敏排除表 |

**叙事义务翻转（A6 §8 修订）：** 「Trace 已按配置规则脱敏，规则可枚举、命中可审计；脱敏是缩小暴露面的工程措施，**不是**绝对安全承诺（规则覆盖有边界，S3 发布安全断言独立成立）。」

### 4.7 灰度发布（A5 指针模型扩展，V0.2 修补发布路径）

**双指针 + 权重分派（D-12）：**

| 字段（Agent 表增列） | 类型 | 默认 | 约束 |
|---|---|---|---|
| `canaryVersionId` | TEXT NULL | NULL | 只能指向同 agentId 的 **Released** 版本；不得等于 currentVersionId |
| `canaryWeight` | INTEGER | 0 | 0–100；0 = 无灰度（缺省 = 第一阶段行为） |

**`release --no-pointer` 新语义（V0.2，P1-2 修复）：** V0.1 缺「发布但不移指针」路径，导致「先 canary 后 stable」流水线结构不可达。V0.2 增补：

- `shanhai agent release <agentId> <versionId> [--no-pointer]`：默认移指针（V1 行为不变）；`--no-pointer` → status→released 但**不移 current 指针**，专供 canary 入口；
- A5 §1-6 修订：指针变更的显式语义集 = `release`（移）/ `release --no-pointer`（发布不移）/ `rollback` / `promote` / `canary set/clear`（后者只动 canary 指针）——原则「指针变更 = 显式操作 + 审计事件」**不变**，枚举扩展；无任何隐式漂移；
- **canary 正常入口：** `review → release --no-pointer → canary set --weight N`（约束 canary ≠ current 现在结构可达）；`promote` = current 指针移至 canary 版本 + canary 清零；
- 审计事件：`version_released` 载荷增 `noPointer: bool`；新增 `version_promoted` / `canary_configured`。

**分派规则（版本绑定原则不变）：** 任务创建入口按 canaryWeight 概率分派 stable/canary 指针 → agentVersionId 固化进 TaskRecord；TaskRecord 增列 `assignmentSource`（stable/canary/explicit）；分派结果记入 `task_created` 事件载荷（assignmentSource + 当时双指针值）——灰度期间任一任务可回溯「为什么进了金丝雀」。

**CLI：** `canary set/clear`、`promote`、`report <agentId> [--since]`（按 assignmentSource 分组通过率对比，C2 聚合口径复用；**数据不足（金丝雀样本 <20）时输出 `insufficient-sample` 状态而非空判据**——V0.2 诚实注记，单机量级下判据常不可达，系统不假装给了答案；**V0.3 R-5：report 旁挂「受工具升级影响的 Spec」只读单列**——Spec 声明等级 < 当前登记等级的存量引用清单，与 staleQueued/stalePaused 同一可见性模式）。

**晋升/回退判据（机械输出，人裁决）：** promote 建议判据 = 金丝雀组契约通过率 ≥ stable 组 − 5pp 且样本 ≥ 20（阈值可配；insufficient-sample 时显式提示）。回退 = `canary clear`（立即，审计）。

**边界：** Deprecated 不可为 canary 目标；canary 指向版本被 deprecate → 按 P2-6 同规则拒绝（先 clear 或换目标）。

### 4.8 OTel 真接入（条件触发制——V0.1 立场维持）

**触发条件（量化，满足其一才实施——D-15）：** ① 单库 Trace 文件 >10,000 或 T1 单查询 P95 >500ms；② ≥2 个 Runtime 实例或首个远程 Agent；③ 用户/外部 APM 显式需求。

**满足前的义务（批次四交付）：** 触发指标进 report 旁挂只读健康面板；本节投影层设计作为归档设计资产，触发后直接实施。

**投影层设计（现在冻结）：** JSONL+SQLite 唯一真源，OTel 是投影（事件 → OTLP span/log 双流，`gen_ai.*` 属性名已对齐 A6 §2）；导出失败只记告警，**不阻塞任务执行**；T1/T2/T3 断言**永不下沉** OTel 后端。

### 4.9 多 Agent 协作（V0.2 再裁：仅留数据锚点，D-16 修订）

**V0.2 裁定（P3-4 采纳，比 V0.1 更狠）：** 第二阶段只交付 `parentTaskId` 列（TaskRecord 增列，NULL = 根任务）——委托数据模型的唯一锚点。V0.1 的「委托治理规则文档」（深度上限、风险作用域、显式 input 回填）**一并延后第三阶段**：无实现载体、无验证面的规则文档是「文档规定无代码执行」的死角声明（反方用语），不写。第三阶段引入编排器时，治理规则随实现一起规格化。

## 5. 关键流程（正常/异常/边界）

**F-1 审批正常流（V0.3 修订，R-1）：** 模型请求 L3 工具（Running 中）→ ToolExecutor 识别 L3 + approvalPolicy 允许 → 写 PauseSnapshot（先持久化）→ 写 ApprovalRequest → `Running → Paused`（Trace: task_paused + approval_requested）→ **run 进程正常退出**（exit code 提示待审批）→ 审批者 `approval list`（含绑定版本摘要 + 超时计数单列）→ `approve`（校验 §4.1-4-3）→ **只写 decision=approved + Trace(approval_decided)，任务保持 Paused** → 前台 spawn `task run --resume` → [resume 进程] 校验 → **`Paused → Running` 迁移**（Trace: task_resumed）→ 同进程反序列化 snapshot → 从 nextCallRef 继续执行 → 终态。
**F-2 审批异常（V0.3 修订，R-1）：** ① 审批者看到时任务已被 cancel（superseded）→ approve 结构化错误 + 审计；② 审批期间版本被 deprecate → 不影响（任务绑定 agentVersionId 固定；approve 校验 request 与 TaskRecord 版本一致，双保险）；③ 超时无人审 → 惰性判定按 onTimeout 迁移；④ approve 后模型后续轮次再请求 L3 → 新 ApprovalRequest 独立审批；⑤ **run 进程在写 snapshot 后、Paused 迁移前被 kill** → 任务留 Running → 恢复扫描 CrashRecovery（正确终局）+ 顺带删孤儿 snapshot（R-4，与 §4.1-4 规则 1 同口径；kill 更早落在 snapshot 写入前则无孤儿可删，仅 CrashRecovery 终局）；⑥ **approve 崩溃于写 decision 后 spawn 前（或 --detach 后无人续跑）** → 任务停留 Paused（合法长驻）→ `task run --resume` 手动续跑仍可达终态（R-1 修复的核心场景）；⑦ resume 时 snapshot 缺失/损坏 → 结构化错误 + 任务留 Paused + 审计（操作者 deny 或人工处置）。
**F-3 跨进程中止边界流：** 进程 A `cancel --force` → 目标在进程 B Running → A 写 abortRequested 标志 + 审计 → B 在原子调用边界读到 → 执行中止迁移 → A 返回「已登记，生效依赖执行进程」——两段式诚实语义。**目标在 Paused → 直接迁移 + superseded + 删 snapshot（无执行进程）。**
**F-4 脱敏写入流：** 事件构造 → 对载荷自由文本执行规则集 → 附 redacted 摘要 → digest（原文口径）→ 写 JSONL → 写索引（双写次序不变）。
**F-5 灰度分派流：** `task create` → 读双指针 + 权重 → 分派 → 固化 agentVersionId + assignmentSource → 落库 → task_created 留痕。
**F-6 演进候选流（V0.2 修订）：** FailureRecord 落库 → 惰性聚合（agentId 聚类，evidence list/show 时）→ 达阈值生成 EvolutionCandidate → 人工检视 → 起草新 Spec → 注册 → review（检视清单）→ release --no-pointer → canary set → 判据 → promote——全链已有机制组合，无新执行路径。
**F-7 记忆计数流（V0.2 新增）：** 任务终态迁移事务内 → Succeeded：本任务写入的记忆 evidenceCount+1；Failed：注入列表逐条 contradictionCount+1 → 状态级别变更即时机械判定 → report/list 时惰性全量校正（幂等）。

## 8. 取舍说明

1. **审批只做工具级**：任务级挂起与「先 --draft/--reviewed 测试再正式跑」等价，做了即伪需求——牺牲与 V1.1 玄武全量审批的对齐进度，换范围收敛；
2. **挂起即退出（而非 run 进程长驻等待）**：24h 审批窗口内要求执行进程存活是落地硬墙（反方 P0-1 论证）；牺牲 approve 后需 spawn 续跑进程的一步操作显式性，换 CLI 单机模型的完全一致——无未声明的长驻假设；
3. **脱敏写入时不可逆（无保险库）**：牺牲事后取证原文能力（digest 仍可对账），换 T3 一致的零密钥简单性；
4. **Evolution 人工确认制**：牺牲自动化演进演示效果，换不可变底线绝对安全；
5. **记忆 evidenceCount 单维（删 confidence 数值）**：牺牲数值化精细度，换「机械可判」的成立性（P1-3 教训：没有可钉死的更新函数就不要数值）；
6. **OTel 条件触发制**：牺牲「九项全落地」形式完整性，换真源单一性；
7. **多 Agent 裁至一列**：牺牲鲲鹏最小面，换「无验证面的规则文档不写」的诚实性。

## 9. 特别要求清单

**9.1 最容易被忽略的三个问题（V0.2 更新）：**
1. **审批挂起后的执行续跑**（V0.1 的 P0-1 盲区）——「Paused → Running 之后谁执行」在两进程 CLI 模型下必须显式建模；V0.2 以挂起即退出 + PauseSnapshot + approve-spawn-resume 闭环（§4.1-4），DoD-② 端到端用例是硬门槛；
2. **审批界面的版本锚定**——审批者看「当前指针版本」而任务绑定创建时版本；approval list 强制显示绑定 agentVersionId + contentHash，approve 再校验 request 与 TaskRecord 版本一致（界面 + 机器双保险）；
3. **脱敏 × digest 的次序**——digest 必须脱敏前按原文计算，否则跨任务对账（灰度 report、记忆去重）全部失配；实现顺序错误不会被单任务单测暴露，需跨任务对账断言。

**9.2 最可能失败的三个场景（V0.2 更新）：**
1. PauseSnapshot 序列化保真不足（上下文裁剪/计数器丢失导致续跑后行为漂移）——缓解：DoD-② 端到端 + snapshot 完整性校验；残余：语义级漂移（续跑后模型行为不同）不构成断言失败，如实记录；
2. 脱敏规则误伤结构化字段破坏 T1/T2——排除表白名单 + 第一阶段验收脚本重跑硬条款（不过即设计失败，不留灰色态）；
3. 记忆注入被诱导为指令——默认 injection=off（默认攻击面为零）；显式开启者的残余风险已知接受 + 边界标记 + 来源限定。

**9.3 当前方案最依赖的三个假设：** §7 之 #5（snapshot 保真）、#2（排除表充分）、#1（三分风险谱够用）。

**9.4 最值得被反方挑战的三个设计点（V0.2 提出、V0.3 全部结清）：**
1. **approve/resume 责任分离** → 已随 R-1 在**状态机层面**结清（迁移权归 resume 进程，审批者只裁决）；第三阶段多审批人时再升格（反方立场 + 决策官确认）；
2. **L2→L3 失败路由静默堆积** → 失败路由维持（隐式改道违反默认拒绝），可见性按 R-5 report 单列解决；调用点拦截已按 R-3 回退第一阶段行为；
3. **injection 默认 off 价值减半** → 决策官确认**维持 off**（安全默认优先，价值证明由实验 Spec 显式声明 `injection:"context"` 承担，首批真实使用数据后再重估；终审时正式冻结）。

**9.5 资源/时间/人员减少时的削减**：§4.10 重排后的削减顺序（依赖显式）；不可削底线：审批（含 P0-1 修复）+ Reviewed + 脱敏管道 + T1/T2/T3 零回退。

**9.6 规模扩大时的瓶颈：** ① SQLite 单写者——并发审批写、多实例 trace_index 串行化（第三阶段 PostgreSQL 既定路径）；② 审批人单点；③ Trace 文件数线性增长（OTel 触发线为此设）。

## 11. 与规格 V1 的兼容迁移路径（V0.2 修订）

**存量数据（SQLite）：**
1. 全部 schema 变更 = 新表（ApprovalRequest / **PauseSnapshot** / MemoryRecord / EvolutionCandidate）+ 现有表 ADD COLUMN（TaskRecord ×4、Agent ×2、AgentVersion 零变更）——`ALTER TABLE ADD COLUMN` 原地支持，**无数据回填**（新列默认值即第一阶段语义）；
