## 2. 新发现问题（分级）

### R-1（P1）approve 与 `--resume` 的状态机互斥 + F-1 同型崩溃窗口——D-18 修复的残缺半步

**矛盾本体：** §4.1-4 规定 approve 执行「decision=approved + **Paused → Running 迁移** + spawn 续跑」；同一节规定 `--resume` 前置校验「**status=Paused** ∧ 存在 decision=approved 的 request ∧ snapshot 存在」。两者不能同时成立：approve 迁移后任务已是 Running，`--resume` 的 Paused 校验必然失败——按字面规格，**spawn 出来的续跑进程会在自己的前置校验上被结构性错误拒绝**。文档自带的 `resumedBy = approve-spawn | manual-resume` 双值也印证 manual-resume 路径在当前语义下不可达。

**崩溃窗口（F-1 同型）：** approve 在「Paused→Running 迁移落库」与「spawn 续跑进程」之间崩溃（或 spawn 失败/--detach 后忘记手动续跑）→ 任务停留 **Running 且无任何执行进程** → 下一次任意 `task run` 启动即触发恢复扫描，将其误杀为 `Failed:Runtime(CrashRecovery)`——**已获批准的任务被当作崩溃遗留处决**。V0.2 崩溃矩阵覆盖了「snapshot 后迁移前」，漏了「迁移后 spawn 前」。

**修复（一处语义移动，同时消解两个问题）：**
- **approve 只写 `decision=approved`（任务保持 Paused）**，可选自动 spawn；
- **`Paused → Running` 迁移移入 `--resume` 进程内部**：resume 校验 Paused ∧ approved ∧ snapshot 完整 → 同进程内完成迁移 + 反序列化 + 继续执行；
- 效果：① 矛盾消失；② 崩溃窗口消失（任何时刻崩溃，任务要么 Paused（合法长驻，等 resume）要么已在执行进程手中）；③ approve/resume 责任分离从「审计字段层面」升为「状态机层面」的结构事实——`resumedBy` 两值都真实可达。

### R-2（P2）degraded→active 恢复边在纯计数器模型下不可机械判定

§4.4-3 恢复边条件 =「**degraded 后**新增独立印证 ≥2」，但 `evidenceCount` 是生命周期累计值，计数器本身不携带「降级时点基线」——惰性全量校正以计数器重算状态时**无法区分「降级前积累的证据」与「降级后新增的证据」**，恢复边判不出来（恰是 V0.1 P1-3-1 问题的换形复发）。

**修复（任一）：** ① MemoryRecord 增 `evidenceCountAtLastTransition` 基线列（状态迁移时快照，恢复条件 = evidenceCount − 基线 ≥ 2）；② 或恢复边条件改为纯累计口径（牺牲精确性换可判性）。建议 ①，一列成本。

### R-3（P2）L2→L3 运行期调用点「按快照 L2 放行」是对第一阶段防御纵深的未声明倒退

第一阶段 A2 §4-2 原文是调用点**按当前登记等级**闸门拦截（`risk_level_blocked` 可达）。V0.2 反转成放行，且该倒退**没有出现在 §4.11 的 A2 增补清单里**——规格文本与设计文本脱节。实质风险：「版本固定原则优先」保护的是 **Spec 语义**稳定性，不该外推到「**工具本体已升级为危险**仍在飞任务按旧等级执行」。这是安全阀，不是语义锚。

**修复（二选一）：** ① 恢复第一阶段行为（调用点按当前登记拦截）——推荐，与「等级只能升不能降」登记原则同向；② 若坚持放行，须独立论证并显式写进 §4.11 A2 增补行 + A2 §4-2 修订注记。当前「设计正文改了、规格增补没跟」按 F-1 教训条款（改一处必须全链一致）是不合格态。

### R-4（P3）孤儿 PauseSnapshot 清理规则缺失

「kill 落在 snapshot 后、迁移前」分支：任务留 Running → CrashRecovery 终局——但该任务**从未进入 Paused**，不触发「离开 Paused 时即删」；snapshot 残留。补：恢复扫描/终态迁移时顺带删除该 taskId 的 snapshot。

### R-5（P3）L2→L3 静默堆积的可见性（对 §9.4-新挑战② 的处置建议）

**支持增补** report 旁挂「受工具升级影响的 Spec」只读单列——与 staleQueued/stalePaused 同一模式、成本极低。建议随 R-3 一并落稿。
