## 1. 审查总览

初稿的**结构纪律是成立且高质量的**：锚点激活原则（不推翻冻结结构）、默认即第一阶段（零迁移）、每批 DoD 机械可断言 + 54 存量零回退、对自身弱点的预判（§9.1/§9.4 自列挑战点）都体现了第一阶段教训的真实吸收。

但存在**一个 P0 级断点**：**审批流的执行续跑进程模型完全缺失**。方案最可能不是失败在「脱敏破坏 T1/T2」这类它重点设防的接触面，而是失败在批次一实现第一周就会发现的问题——`Paused → Running` 之后，**谁来继续执行这个任务**。这在两进程 CLI 模型下无解于现有设计，且与 A3 §6 已白纸写明的「Checkpoint 属第二阶段」承诺直接冲突，而全文没有 Checkpoint 的任何设计。这恰好违反了初稿自己立下的条款（§3-1「每条新机制写明进程模型假设」——F-1 教训条款）：九项机制里只有 abort 写了进程模型假设，审批续跑与记忆状态机迁移两项没写。

第二梯队问题是**四处「语义级矛盾/不可实现」**（P1）：deny 语义双重定义、「演进产物先 canary」结构上不可达、记忆可信度未到可实现粒度、削减顺序违反自身依赖。

## 2. 分级问题清单

### P0-1 审批挂起任务的执行续跑进程模型缺失（最可能的单点否决项）

**问题描述：** §4.1 F-1 流程写到「approve → Paused → Running → ToolExecutor 执行该次调用」为止，但从未回答**哪个进程执行这次调用**。逐层推演：

1. 两进程 CLI 模型（`task create` / `task run`，README 文档化工作流）下，`task run` 进程若要在 approve 后继续执行，必须**长驻轮询数据库**等待裁决——默认超时 24h，意味着设计隐含「run 进程可挂起等待 24 小时」，该假设未声明，且与其自设的 F-1 教训条款（每条新机制写明进程模型假设）直接冲突；
2. 若 run 进程在等待期间崩溃或被操作者 Ctrl-C 退出（24h 窗口内几乎必然发生）：恢复扫描不碰 Paused（正确），但**没有任何机制能恢复执行**——任务永久卡死在 Paused，approve 之后也无人续跑；
3. 即便补一个「显式续跑命令」，续跑所需的**执行态在 Paused 时无处持久化**：模型对话历史不落库（TaskRecord 只有 input）；A2 §2.1 明定调用级 attempt 计数器「运行期内存，不落 TaskRecord」——从崩溃中恢复执行连计数器都要从 Trace 反推，未设计；
4. A3 §6 白纸写明「不做断点续跑（**Checkpoint 属第二阶段**）」——即执行态检查点本就在第二阶段范围内，而本设计全文无 Checkpoint 设计。这不是可以「WP-2B 自行决定」的实现细节，是审批流能否成立的方案级前提。

**影响：** 批次一第一项能力在实现时即撞墙：要么偷偷做成常驻进程（违反 CLI 单机模型、引入 F-1 同型未声明假设），要么审批流只能演示「approve 时 run 进程恰好还活着」的玩具场景。

**修复要求（V0.2 必须补齐，任选其一并写入规格）：**
- (a) run 进程内等待模型：显式声明「run 进程长驻轮询、等待上限可配、等待中崩溃 → 任务停留 Paused，由 `task run --resume <taskId>` 显式续跑」+ 挂起时点的执行态快照设计（对话历史、调用计数器、next callRef 的持久化载体）；
- (b) 挂起即退出模型：「Paused 时 run 进程退出，`approve` 命令负责 spawn 续跑进程」——同样需要执行态可序列化；
- 无论哪种，**批次一 DoD 必须增加端到端用例：run 进程于 Paused 态被 kill → approve/续跑命令 → 任务继续执行至终态**。这条不过，审批流不算成立。

### P1-1 deny 语义双重定义，approval_denied reasonCode 不可达（或引入挂起循环）

**问题描述：** §4.1 T-A4 定义「deny → Paused → **Cancelled**（任务终局）」；同节又定义 reasonCode `approval_denied` =「拒绝/超时 deny 后**模型再请求同一调用**时返回」。两者矛盾：deny 已使任务进 Cancelled 真终态（A3 不变式①无出边），模型永远不会再运行，「再请求同一调用」的窗口不存在——该 reasonCode 是**不可达死路径**。

若设计师真实意图是**调用级 deny**（拒绝该次调用、任务继续），则会打开更糟的洞：模型 resume 后再次请求同一 L3 工具 → 每次请求独立生成新 ApprovalRequest（F-2 ④）→ 任务再次挂起 → 审批者被迫逐轮审批同一动作（挂起循环 + 审批疲劳），且 `approval_denied` 是否计入 `consecutiveDenialCount` 未定义——计入则归因漂移进 Policy(PolicyBlocked)，不计入则模型可无限循环。

**修复要求：** 二选一并全链一致：维持「deny = 任务级终局」则删除 `approval_denied` reasonCode（死枚举，A2 §5 P2-1 删 `budget_exhausted` 的先例）；改为「调用级 deny」则必须补「同调用键的 L3 请求在 deny 后任务内记忆拒绝（不再生成新 ApprovalRequest）+ 计数口径」。当前文本两头各取一半，WP-2B 无法实现。

### P1-2 「演进产物发布默认先 canary」结构上不可达

**问题描述：** §6 裁定「evolution 产物发布默认建议先 canary，report 判据成为演进安全网」。但按 A5 §1-3 与本设计 §4.2/§4.7 的组合：`release` **默认同步移 current 指针**（直接进 stable）；而 `canaryVersionId` 约束为「指向 Released 版本且**不得等于 currentVersionId**」。于是把一个新版本放进 canary 的唯一路径是：先 release（指针已移，stable 已经全量切过去——灰度的意义已丧失）→ 再把它设为 canary（此时它就是 current，被 ≠current 约束拒绝）。**不存在「发布但不移指针」的路径，「先 canary 后 stable」的流水线在字面规格上走不通。**

**修复要求：** 补一条 `release --no-pointer`（或 canary 可指向刚 Reviewed 版本的特例边 `reviewed → canary-released`）语义 + 对应审计事件；并回答它对 A5 §1-6「指针移动只允许经 release/rollback 两个显式语义」的修订幅度。这是 §6 自己提出的跨机制交互，裁定与结构冲突说明该交互没有被真正推演过。

### P1-3 记忆可信度机制未到「WP-2B 可直接实现」粒度

**问题描述（四点叠加）：**
1. **confidence 更新函数未定义：** 初始 0.5，active 门槛 ≥0.7——从 0.5 到 0.7 的增量规则（每次独立印证 +0.1？0.2？）全文没有。「阈值机械可判」的宣称不成立：没有更新函数就没有阈值可言；
2. **「独立任务」未定义：** 同 agentId 不同 agentVersionId 的任务印证算不算独立？记忆写入时绑定 agentVersionId，而注入作用域（哪些任务会被注入该记忆：同 agentId 全版本？同版本？）也未定义——这同时决定 T1 锚点语义与攻击面大小；
3. **迁移触发的进程模型未写：** degraded 判定（「引用该记忆的任务终局 Failed」）由谁、何时计算？任务终态回调还是 report 时惰性聚合？违反自设的「每条新机制写明进程模型假设」；
4. **状态机无恢复边：** `degraded → active` 不存在。一次与记忆无关的任务失败（注入≠使用，见 P2-3）即永久降级，后续再多次印证也无法挽回——一票否决设计的正当性未论证。

**修复要求：** V0.2 补齐四点；若置信度更新函数难以钉死，最小修复 = 干脆去掉 confidence 数值、只用 evidenceCount 驱动状态机（数值留展示列），把「机械可判」做实。

### P1-4 削减顺序违反自身依赖：脱敏可削，而依赖脱敏的记忆不可削

**问题描述：** §4.4 明定记忆 content「**过脱敏管道**（§4.6 同规则）」；但 §4.10 削减顺序中「脱敏」位于可削序列（灰度之后、中止之前），而**记忆基线根本不在削减清单里**（只有「记忆可信度高级迁移」可削）。按此顺序执行到「削脱敏」时：要么记忆写入未脱敏内容（违反 §4.4 自己的规则），要么削减顺序实际不可执行。

**修复要求：** 二选一：把「脱敏管道（可空规则集）」标注为记忆的前置不可削项（规则集可裁、管道不可裁）；或把记忆整体移入可削序列。依赖必须显式，不能靠读者自己推。

### P1-5 Reviewed 环「审什么」未定义——质量门空心化，殃及 Evolution guardrail

**问题描述：** reviewGate 三档中，`assertions` 档跑的断言 = `evaluationPolicy.assertions` = **输出契约断言**——而这在每次任务运行期已被强制校验（contract_checked）。对一个版本跑一组测试任务验证「输出符合输出契约」，不产生任何运行期已不存在的新信息；`manual` 档则没有定义人工检视的检视对象与清单（审 Spec 文本？审 mission 边界？审工具风险声明？）。结果：**Reviewed 状态不承载任何可说明的判定内容**。这不只是 P2 级的语义单薄——Evolution 的 `requireReviewed` 强制不可关，其安全价值全部抵押在 Reviewed 环的判定含金量上；门是仪式，guardrail 就是仪式套仪式。

**修复要求：** V0.2 给 review 一份最小检视清单（哪怕 3–5 项人工检查点：非职责边界变化、风险等级变化、预算变化、工具集变化——**对比同 agentId 上一 Released 版本的 diff 驱动**），并把 `version_reviewed` 事件载荷改为携带该清单结果。否则应诚实降格：承认第二阶段 Reviewed 仅是「流程签核」而非「质量判定」，同时重估 Evolution guardrail 的表述强度。

### P3 级建议（5 项，不阻断）

1. 超时 deny→Cancelled 维持（见 §5 立场），但建议在 report 旁挂「审批超时计数」单列——不进 C2 失败率（支持），但治理惰性信号应可见，不该只藏在 Trace 里；
2. `cancelReason` 枚举细化：`approval_denied` / `approval_timeout` / `abort` / `superseded` 应互区分，否则 C2 与审计口径无法分离；
3. approve 命令应校验「request.agentVersionId == TaskRecord 绑定版本」（防跨任务误用 requestId），与 §9.1-2 的界面锚定互为双保险；
4. 委托「治理硬规则」（深度上限、风险作用域独立、显式 input 回填）无实现载体、无验证面——建议随编排器一并延后第三阶段，第二阶段只留 parentTaskId 列（比 D-16 现案再进一步裁剪，消除「文档规定无代码执行」的死角声明）；
5. digest 原文口径存在低强度「猜测—验证」预言机残余（对 digest 验证疑似原文猜测）；已知接受即可，建议在 A6 §8 修订注记中显式记录。

## 4. 成立部分（明确确认，避免重审浪费）

1. **Paused 不进恢复扫描**——与 F-1 收窄判别准则（「仅迁移有执行副作用悬空的中间态」）逻辑严格一致，论证成立；P0-1 是它旁边的洞，不是它的错；
2. **脱敏：写入时执行 + 排除表白名单 + digest 原文前置 + 第一阶段验收脚本重跑硬条款**——机制组合成立，DoD「不通过即设计失败、不留灰色态」的表态是全文最硬的防线，保留；
3. **灰度：创建时分派 + agentVersionId 固化 + assignmentSource 留痕**——版本绑定原则无损外推，成立；
4. **OTel 条件触发制 + 断言不下沉投影**——诚实且守真源单一性，成立；
5. **多 Agent 整体裁第三阶段的方向**——成立（建议再按 P3-4 裁掉治理规则文档）；
6. **默认即第一阶段 + 全部 schema 变更 = 新表/ADD COLUMN 零回填**——兼容路径成立且被迁移章节逐条兑现；
7. **§9.1 三个自列忽略点全部真实**，其中版本锚定方案（approval list 强制显示绑定版本+contentHash）成立。

**对 §9.4 三个自列挑战点的反方立场：**
- 超时默认 deny→Cancelled：**支持现设计**（超时是治理惰性非任务失败，不污染 C2），附 P3-1 条件（旁挂计数保信号可见）；
- Reviewed 可选（直发保留）：**支持保留直发**，但真正的问题不是可选/强制，而是 P1-5「审什么」空心——先修内容再谈强制；
- 多 Agent 整裁：**支持**，且建议裁得更狠（P3-4）。

## 5. 特别要求回答

1. **最可能失败的环节：** 批次一审批流实现启动时的执行续跑问题（P0-1）——不是概率风险，是设计方案中该前提为空。
2. **一旦不成立影响最大的假设：** 「Paused 是持久化长驻合法状态」隐含「执行进程可在裁决后继续执行」——不成立则审批流整条（含 T2′、L3 分治、superseded 语义）全部悬空。
3. **无明确责任人的环节：** ① Paused→Running 后的执行主体（P0-1）；② 记忆状态机迁移的计算主体与时机（P1-3-3）。
4. **理论可行、现实难落地：** ① 24h 审批窗口内的 run 进程存活；② promote 判据 N≥20 的样本规模（单机 CLI 量级不可达）。
5. **不必要的复杂度：** ① specVersion "2" 双版本兼容（P2-5，v1 内可选字段扩展可能更便宜且无哈希副作用）；② 委托治理规则文档（无实现无验证，P3-4）；③ confidence 数值维度（P1-3-1，evidenceCount 单维可能已够）。
6. **只能保留一半时保留什么：** 审批流（修复 P0-1 后）+ Reviewed 环（修复 P1-5 的检视清单后）+ 脱敏管道 + T1/T2/T3 零回退 + 批次一全部 DoD。砍：灰度、Evolution、OTel 监测、记忆（降为设计资产归档）、多 Agent。理由：第二阶段的差异化价值在「安全治理可举证」，不在功能广度。
7. **如何证明 V0.2 优于 V0.1：** ① P0-1 修复后新增的「Paused 态 kill 进程 → 续跑至终态」端到端用例进入批次一 DoD 并可被冷读者走查复述；② P1-1/P1-2 的语义矛盾消失（规格文本中不存在不可达路径与不可达流水线）；③ 削减顺序与依赖图逐项对得上。三者皆可机械检查，不依赖信任。
